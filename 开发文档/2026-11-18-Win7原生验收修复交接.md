## 一、SQLite JSON1 缺失

### 根因与回归边界

持久层把一组编号编码成单个 JSON 参数，由 SQLite 的 `json_each(?)` 展开；计划比较还展开库内 JSON 列，历史触发器使用 `json_extract` 和 `json_set`。按 `core/`、`data/`、`web/`、`schema.sql` 检索这三项，`4eb3cf3e0` 为 0 个文件，`5eda3b292` 及本次失败版本均为 36 个文件。其中 34 个仓储模块使用了 `json_each`。批量查询还承担超过一千个编号时的正确性约束。[计划比较](../data/repositories/workbench_run_repo.py#L390) · [1,252 个编号的回归用例](../tests/workbench/test_batch_list_summary.py#L228)

SQLite 3.35.5 的 JSON1 是编译选项。项目只在导入时检查最低版本为 3.35.5。Mac 项目的 `.venv` 与 Win7 打包环境的 Python 和 SQLite 版本均相同，前者执行三个函数成功；Windows 现场直接检查成品 DLL，确认与构建 Python 的 DLL 字节一致，执行 `SELECT value FROM json_each('[1]')` 报 `no such table: json_each`。项目锁定的 Python 3.8.10 Windows 离线安装器携带同版本、不含 JSON1 的 SQLite。这解释了同一代码在 Mac 的大集合回归通过、在 Win7 的第一条工种就失败。[项目版本门槛](../core/infrastructure/sqlite_udf.py#L18) · [离线材料清单](../packaging/win7/offline-manifest.json) · [CPython 3.8.10 Windows 构建配置](https://github.com/python/cpython/blob/v3.8.10/PCbuild/sqlite3.vcxproj#L101) · [SQLite 官方编译说明](https://www.sqlite.org/json1.html#compiling_in_json_support)

| 现场入口 | 原始错误发生在哪里 | 业务影响 |
|---|---|---|
| 空库值班台 | 读取外协来源时，即使目标为空也执行 `json_each('[]')`。[查询](../data/repositories/workbench_outsourcing_source_repo.py#L225) | 页面壳能打开，数据区显示“读取失败” |
| 新增工种 | 创建前按编号查 `OpTypes`，单个编号也使用 JSON 数组。[查询](../data/repositories/workbench_resource_table_repo.py#L49) | 新建返回 HTTP 500；复杂样例停在第一条 `CS-OP-01` |
| 保存新日历日期 | 先 upsert，再按日期回读新标识。回读失败，外层事务回滚。[写入顺序](../core/services/workbench/resource/calendars.py#L297) · [回读查询](../data/repositories/workbench_calendar_query_repo.py#L80) | 日历写入返回 500，后续跨窗口冲突验收走不到 |
| Excel 物料预检 | 校验输入行之前先按物料编号读取现状。[物料查询](../data/repositories/workbench_material_file_repo.py#L25) | 缺名称、负库存样例收到 500，用户看不到应有的逐行错误 |

**写回执是第二个必测位置。** 在同版本、未启用 JSON1 的 SQLite 内存库中，加载项目的表和触发器能成功；对普通 `calendar.upsert` 回执执行 `EXPLAIN INSERT` 和实际 `INSERT` 均报 `no such function: json_extract`。SQLite 准备插入语句时就解析触发器，早于判断该 action 是否属于“采用”。启用 JSON1 的 Mac 同版本运行同一插入成功。普通工作台命令的领域写入和回执共用事务，回执失败会回滚领域变更。此项是审查时的独立内存实验，上表是 Windows 日志中实际先触发的错误。[触发器](../core/infrastructure/workbench_history_schema.py#L46) · [命令事务](../core/services/workbench/commands.py#L101) · [回执写入](../data/repositories/workbench_command_repo.py#L41) · [事务回滚](../core/infrastructure/transaction.py#L175)

## 二、旧契约与新实例的启动时序

**复现条件。** 在独立测试副本占住默认 5000 端口，正常启动并留存该测试实例的旧契约。正常退出后，只在该测试目录放回旧契约，再启动同一 BAT。现场日志 `elapsed_ms=2120` 已决定启动后台，`3179` 记下 `readiness=blocked:healthy_without_owner_proof`，`3180` 结束，等待阶段只经历 1.043 秒。后台随后健康，专用 Chrome 未由启动器打开。旧契约是测试者有意放回的；正常停机留下旧契约这一前提没有现场证据。

**根因与改动位置。** 启动器先读锁、契约和端口，再请求 HTTP 健康。后台依次取得锁、绑定实际端口、发布新契约并开始服务。一次读取可能拿到旧的身份信息和新的健康响应。`healthy_without_owner_proof` 本能防止重复启动或误连其他实例，可在“已拉起后台、等待就绪”的阶段，等待循环也把它作为终态直接返回。现场记录足以确认误判分支；没有逐次采样能确定究竟哪一次 GET 跨过了切换点。[锁和契约读取](../assets/aps-launcher.ps1#L122) · [归属判断](../assets/aps-launcher.ps1#L264) · [等待终止条件](../assets/aps-launcher.ps1#L303) · [后端发布顺序](../web/bootstrap/entrypoint.py#L289)

**修复判据。** 区分启动前的复用判定与本次已拉起子进程后的就绪等待。后者遇到可过渡的证据不一致时，在原有 45 秒时限内重新读取锁、契约和健康身份；确认同一实例才开 Chrome。保留对明确的其他所有者、其它数据库、超时的处理。已有用例覆盖静态拒绝和模拟 `starting → ready`，值得补的是本次实测的“旧快照 → 新健康响应 → 新契约”时序。[现有归属用例](../tests/app_runtime/test_launcher_startup.py#L191) · [现有等待用例](../tests/app_runtime/test_launcher_startup.py#L223)

Win7 复验要记录后台 PID、实际监听端口、启动器最终状态及专用 Chrome 是否由启动器打开，同时复核重复启动复用一个后台。以正常控制台或 Explorer 打开 BAT。部分早期副本的 stop 返回 1，重定向模式还出现过 `process_list_unavailable` 和 `WinError 6`；这组现象保留各自日志，待能独立复现时再归因。[Chrome 停止结果](../web/bootstrap/launcher_chrome.py#L110)

## 三、正式打包入口返回了错误的成功状态

**现场与边界。** 正式脚本声明 `#Requires -Version 5.1`，Win7 来宾的 PS 2.0 报 `ScriptRequiresUnmatchedPSVersion`，脚本体没有执行。外部驱动等待 `cmd.exe` 退出，记录 `formal exit=0`，新构建目录中没有当次 ZIP。BAT 只是透传 `%ERRORLEVEL%`，ZIP 校验写在被拒绝的脚本内部。没有单独记录 `powershell.exe` 的退出码，所以目前只确定外层的成功信号失真。PS 2.0 的兼容出包与正式脚本都调用同一 `onedir` 构建，这个问题与 SQLite 缺失分开修。[BAT 入口](../build_win7_portable.bat#L7) · [脚本前置条件](../.limcode/skills/aps-package-win7/scripts/package_win7.ps1#L1) · [正式便携包构建](../.limcode/skills/aps-package-win7/scripts/package_win7.ps1#L520)

在可被 PS 2.0 执行的外层明确校验正式入口所需版本，向调用方返回非零并说明原因。验证分两次：在 PS 2.0 下记录错误文本和调用方退出码；在 PS 5.1 下从干净的隔离构建目录走正式 BAT，核对退出码、当次生成的 ZIP、包结构和冷启动。原测试者给外置驱动增加的“检查 ZIP 是否存在”只是当时的排障措施，目录里有历史同名文件时不足以判断本次成功。

在 Win7 SP1 x64、PS 5.1 的打包机上，从独立源码目录用 `cmd.exe` 逐步运行。每步确认成功再继续，最后一行紧接正式入口，以观察外层返回码：

```bat
python scripts\prepare_win7_offline.py verify
call setup_win7_build.bat
call build_win7_portable.bat
echo %ERRORLEVEL%
```

在现有 PS 2.0 来宾需要继续业务验收时，参考旧报告中的实跑路线：激活本轮构建环境，运行 `build_win7_onedir.bat`，将已核验的 Chrome 109 放入成品目录的 `tools\chrome109`，再用 `scripts/portable_release.py prepare` 和 `archive` 生成 ZIP。先保留未运行的干净成品，再在另一解压副本做业务写入。构建报告中注明所用路线。[归档工具参数](../scripts/portable_release.py#L89) · [正式流水线中浏览器、冒烟和归档的顺序](../.limcode/skills/aps-package-win7/scripts/package_win7.ps1#L525)
