# 重构风险与分流

按本次目标检查相关风险。以下信号用于选择证据和实施方式，不是阻止只读扫描或要求用户重新授权已批准工作的固定关卡。

## 行为边界

涉及新增能力、改变返回含义或修复现有故障时，明确区分功能变更与等价重构。用户已同时授权多类工作时可按依赖分开实施与验证；未授权的行为变化只提出建议。

## 验证是否足够

依据关键路径、外部契约及实际风险判断，不用固定行覆盖率或测试文件数量代替判断。只读扫描可报告验证缺口；实施需要时在已授权范围补必要刻画测试。静态配置、类型声明或纯搬移选择适合的差异和引用检查，不为了形式写无价值测试。

## 跨模块关系

跨模块并不自动拒绝，先查依赖方向、公开契约和职责。现行架构事实用 `cs-arch` 核实；目标态方案写 design 或 roadmap，不能先把新方案写成现状。实质边界变化说明影响并取得必要确认，原范围内的调用方更新可直接完成。

## 风格与实际收益

没有实际影响的口味项不包装成缺陷；用户明确要求格式或命名整理时可以完成该任务。不要自动先立 decision，再对全项目执行格式化。性能问题需要实际触发条件与适当测量，不能只凭行数判断收益。

## 生成产物与外部代码

优先定位生成源、模板或项目扩展点，避免修改下次生成会覆盖的文件。外部代码根据实际维护方式、许可和用户范围处理；不能仅凭 license header 判定禁止修改，也不自动建议另建 wrapper 掩盖问题。

## 范围与分批

文件多、代码长或候选多时，按模块和风险分批覆盖，记录已读与未读范围。没有证据证明不可完成时不以固定文件数、行数或候选数拒绝；不把分批变成让用户重复选目标。

## 零发现与少量发现

实际有几条就报告几条。零发现说明范围内没有足够证据支持调整；一两条局部问题可以直接按局部通道处理，不凑满完整方案门槛。

## 真正需要暂停时

说明具体证据、无法继续决定的目标/风险以及已完成部分。已有证据和授权继续有效；问题解决后只核对受影响条件，不机械重跑所有检查。未授权修改、真实环境缺失或无法判定关键行为时，交付限制，不能虚报通过。
