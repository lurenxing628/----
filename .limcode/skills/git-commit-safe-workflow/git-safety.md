# Git 范围与编码参考

## 普通提交

先检查 `git status --short`、`git diff --cached --name-only`、本轮差异及任务起点。已有暂存内容不等于本轮授权内容；只暂存、提交明确属于本次任务的路径或补丁。不要用全部暂存、重置或清理命令消除他人的现场。

多行中文正文先由编辑器或补丁工具写入可信 UTF-8 文件，再用 `git commit -F <消息文件>`。可用系统临时文件；若放在 Git 内部，通过 `git rev-parse --git-path COMMIT_MSG_TMP.txt` 得到真实路径，不直接假定 `.git/` 为目录。并发提交使用各自唯一临时文件。

提交后核对真实提交的路径、diff、提交消息和剩余 `git status --short`，避免将工具成功退出误当成范围正确。

## PowerShell 编码排障（仅该平台适用）

先识别 PowerShell 版本和报错，旧版本可能不支持 `&&`。避免在复杂内联字符串、here-string 或 `python -c` 中反复叠加中文和转义；使用已经核对的 UTF-8 消息文件。外部 Git 命令检查 `$LASTEXITCODE`，失败后不要继续当成功处理。

乱码先区分终端显示与 Git 对象正文：读取 `git log -1 --format=%B` 的原始字节，以 UTF-8 strict 解码，再查看真实文字。解码通过只证明字节合法，不证明中文语义正确；从乱码继续复制会扩散损坏。

- Git 正文正常而终端显示异常：处理显示设置，不改提交对象。
- 正文损坏：准备可信替换文本并说明影响的提交；仅在已获对应历史修订授权时执行。
- 标题重复或 `Co-authored-by` 不合偏好：不自动 amend，也不使用 `commit-tree` 绕过注入；先核实用户希望改变什么。

## 历史修订

重写前留备份引用，明确提交范围及是否已发布。核实当前工作区、暂存和目标提交，不把排障授权扩大为 amend、rebase、强推或删除历史。用户已经明确批准相同动作及范围时无需再问。操作后核对消息、父链、内容和剩余工作，报告新的提交标识。
