# cs-feat-impl

## 启动必读

启动、授权与续作遵守根目录 `AGENTS.md`；读取或复用 `.codestable/attention.md`。路径、状态与收尾按需查 `.codestable/reference/shared-conventions.md`，缺辅助材料不阻断只读调查或已授权局部工作。

到这一步用户已经在方案上签过字了，你的活是把方案变成代码。容易出问题的不是写代码本身，而是**实现路上发现方案没覆盖到的情况时怎么办**——硬冲下去就把方案当摆设了。下面的规则区分实现细节和实质方案变化：已授权范围内连续完成，业务取舍、外部约定或风险明显变化时再确认。

> 共享路径与命名约定看 `.codestable/reference/shared-conventions.md` 第 0 节。
> `cs-feat-ff` 不进入本技能：fastforward 没有 design / checklist / acceptance，完成后只写 `{slug}-ff-note.md`。

## 写代码时的三条姿态

具体规则是这三条姿态的落点，理解姿态比记规则重要。

### 1. 默认写最少的代码

只写当前步骤明确要的东西。不顺手加"以后可能要"的可配置项、抽象层、参数开关、防御性兜底。判据：写完一段觉得"是不是还得加点 X"，先判断 X 是否为当前正确性或已授权目标所需；必要的错误处理和验证照常保留。多出来的代码不是中性的，是后人维护的负担。

### 2. 只动该动的，不顺手"改善"邻居

改某个函数时只改那个函数。同文件里别的函数风格丑、命名怪——除非和本次改动直接冲突，否则别碰。新代码风格匹配当前文件已有写法。混进的"顺手改"会把功能 PR 稀释成"一坨综合改动"，review 成本翻几倍。值得改的按下文"顺手发现"格式记成后续 issue。

孤儿处理：你这次改动让某个 import / 函数变成死代码 → 删掉。**不是**你改动造成的死代码 → 留着记成顺手发现。

### 3. design 没说的事别自己拍板

方案没有指定的内部实现、必要错误处理、测试和具体文件落点，由实现者依据现有代码保守决定并验证。只有改变业务含义、公开接口、安全边界、已声明的不做项或明显扩大范围时，才回方案说明影响并请用户确认。

## 启动检查

### 1. 方案文件够不够撑实现

frontmatter：`doc_type=feature-design` / `feature` 一致 / `status=approved` / `summary` 非空 / `tags` ≥ 2。

**标准 design**（节 0/1/2/3/4）：
- 第 0 节有内容；第 1 节含"明确不做"和复杂度档位
- 第 2.1 名词层用"现状 → 变化"两段式，每个新增/变更接口至少一个示例 + 来源位置
- 第 2.2 编排层开头有主流程图，"现状 → 变化"齐全，流程级约束已记
- 第 2.3 挂载点按"删了它 feature 是否消失"判据，没把内部代码改动误列进来
- 第 3 节有关键场景清单 + 反向核对项（不含测试代码 / framework 选型）

缺少决定正确性的目标、约束或验收条件时，回设计阶段补齐。仅有格式或元数据缺项且事实已明确，可在已授权文档范围内补正，不因模板缺项机械退回。

**注意**：标准 design 第 3 节"验收契约"只说"做完后什么应该成立"，不说"具体怎么做"。改动文件清单 / 函数级落点 / 测试代码归 implement 自决，不要因为 design 里没写就退回去要求补。

### 2. {slug}-checklist.yaml 在不在

- 文件存在，`feature` 字段一致
- `steps` 非空（design 已产出，paradigm 维度切片，步数按实际需要）；`checks` 非空
- 不存在时依据已批准方案补齐必要执行清单；缺少决定正确性的方案内容才回设计澄清

### 3. 读取必要上下文

- 方案 doc 全文（标准 design 重点：第 1 节、2.1/2.2/2.3/2.4、3）
- `{slug}-checklist.yaml`、需求来源（用户描述 + brainstorm note）、`.codestable/attention.md`
- 第 2.1 节接口示例的来源位置——读相关函数即可

### 4. 确定起步位置并告知用户

新任务从第 1 步开始；接续任务先核对实际代码和验证记录，再从未完成步骤继续。记录明确时无需重复确认；记录与现场冲突时先核实。

design 给的 `steps` 是 paradigm 维度切片（编排骨架 → 计算节点 → 持久化 → 测试），**具体每步改哪个文件由你执行时决定**。可以在原范围内细分子动作并更新进度，无需为每个内部动作再问一次。若前置重构扩大范围或改变约定，说明影响后再确认。

**design 第 2.5 节微重构的衔接**：

- 如果 2.5 结论是"做微重构（拆文件）"或"做微重构（重组目录）"，checklist 第 1 步就是它——**独立跑完**，按 2.5 节"行为不变怎么验证"那条核对：
  - 拆文件：编译绿灯 + 现有测试通过 + 对外接口签名零 diff
  - 重组目录：编译绿灯 + 现有测试通过 + diff 仅限文件移动 + import 路径更新（**没有任何函数体改动**）

  **不要合并到下一步**——一旦混在一起，行为变更和结构变更就分不开，出问题回滚不到干净中间态
- 如果 2.5 原结论是“不做”但出现新的结构风险，按下方反射检查判断是否是必要局部调整或实质范围变化，不自动因拆分信号停工
- 2.5 已有 convention 候选时保留其来源与验证结果，最终收尾按当前授权统一处理，不在多个阶段重复询问

## 实现期间的几条核心约束

### 按依赖推进 steps

按真实依赖执行，保留每步退出信号与完成状态；原范围内可细分或合并能共同验证的内部动作，更新记录而不机械重排审批。

结构搬移与行为变更需要独立证据时分开验证；不得跳过退出信号或把未完成步骤标 done。

### 不做方案外的改动

发现值得重构的点（参考 `.codestable/reference/shared-conventions.md` 第 7 节"写代码时的反射检查"），只要**不在本次功能影响面内**就记成后续 issue：

```markdown
> 顺手发现：{文件:行号} {问题简述}。不在本次范围，记录待后续 issue。
```

顺手改的代码不在方案里，验收对不上；后人 git blame 也分不清是为本次功能还是顺手。

### 术语守护

**标准 design**：新增业务概念和公开名称对照方案第 0 节及现有代码，避免同名异义或一义多名。普通局部变量、辅助函数和测试名称不要求逐个写入方案。真正新增或改变业务概念时，再查重、更新方案并确认语义。

代价：术语冲突意味着同概念两个名字 / 同名字两个概念——后者会让搜索完全失效。

### 检查特殊分支是否有依据

必要的输入校验、错误处理和真实边界条件应正常实现并验证，不能只因出现 `if` 就退回设计。为绕过错误而猜测兼容、吞掉异常或改变业务规则的分支，需要先定位原因；涉及实质方案变化再与用户确认。

### 代码质量反射检查

除上面流程约束外，还有一组针对代码质量的反射检查——看 `.codestable/reference/shared-conventions.md` 第 7 节。

核心：**不是"超过 N 行必须拆"，而是"遇到 X 情况就停下来问自己"**。每条对应 AI 默认会走进去的坑（往大文件继续追加、往大类加方法、补丁分支、复制粘贴、第 4+ 个参数、往万能 util 堆东西）。

反射检查按职责和风险判断；必要局部调整可在原范围内完成并记录。涉及独立重构、业务或公开契约变化时，再说明影响并确认：

- **能用"只搬不改行为"解决**（拆函数 / 拆文件 / 移动定义，编译器全程绿灯，对外签名零 diff）→ 必要时记录独立 step，验证搬移与原行为后继续；范围扩大时先确认
- **超出"只搬不改行为"边界**（要改函数签名 / 改返回值结构 / 改调用关系语义 / 模块拆合）→ 若是当前功能必需，说明约定与影响并取得必要确认；无关调整记录为后续 `cs-refactor`，不能为维持旧方案添加掩盖根因的绕路

## 写完后输出统一汇报

所有步骤完成后按任务规模说明下面适用内容。用户要求分阶段审核时停等；已经授权完整实现与验收时，继续完成适用验收，不重复索要同一授权。

重点是实际改动、验证证据和未完成项。可省略无关栏位，不为凑模板重复报告。

结果格式按需查同目录 `reference.md`。

没有完成的检查如实列出，不把等待用户反馈写成已经通过。

## 测试用例怎么落

标准 design 第 3 节"关键场景清单"每条 = 一个可验证行为约束。你的活是把每条变成可观察证据：单测 / 集成 / 手工操作 / 类型编译期保证。

具体怎么测、用什么 framework、mock 怎么搭——design 没规定，自决。但你得在 `steps` 里写清楚"哪一步落哪个测试"，汇报里逐项核对每条场景都有证据。

**测试通过 ≠ 验收场景满足**——前者只说明你写的用例过了，不说明每条场景都有用例覆盖。

类型系统保证的（如 TypeScript 签名直接排除某种调用），汇报里说"类型签名已落地，编译期保证"。

## 退出条件

- [ ] 所有 steps 的 status 都 `done`
- [ ] 完成汇报已输出；约定的人工作业或审核未完成时明确标为待确认
- [ ] 没有未处理的"需要叫停"信号
- [ ] 第 3 节关键场景每条都有证据 / 测试覆盖
- [ ] 没有"顺手发现"被偷偷修掉（都进 issue 列表）
- [ ] 没有超出已授权业务范围的改动；具体文件落点与实际差异已记录

---

## 退出后

说明实现和验证的实际状态。已授权完整流程时衔接 `cs-feat-accept`；仅要求实现或要求逐阶段审核时，说明下一步，不自动扩写验收报告。

有值得保存的长期项目事实时，在最终收尾合并提示一次；已授权归档直接完成，未授权不自动追加，也不在 implement 和 acceptance 重复询问。

## 容易踩的坑

- 代码只写了一部分就发完成汇报——汇报只在全部完成后发一次
- 汇报里写"修改了相关文件"而不列 file:line
- 看到方案外的代码顺手改了
- 引入新类型 / 概念但没回去更新方案 doc
- 用无证据的特殊分支掩盖根因或暗改业务规则
- 用户明确要求逐阶段审核，却擅自跨过该审核
- 关键场景清单一条都没落证据
- 把 paradigm 维度 steps 当 file:line 读——steps 是切片策略不是改动清单；原范围内细分可以自行记录，扩大范围须重新对齐
