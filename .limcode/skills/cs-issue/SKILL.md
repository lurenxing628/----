# 故障处理入口

## 启动

在项目内执行本技能时，按需读取 `.codestable/attention.md`；本轮已读且未变化则复用，内容丢失或文件变化时重读。它补充而不替代适用的 `AGENTS.md`。文件或目录缺失时说明限制，不自动初始化，也不阻止只读调查或已授权的小范围工作。只有用户选择完整 CodeStable 流程时，才补齐该流程实际需要的材料。

先核对用户要“分析”还是“修复”，按当前代码、运行信息和实际数据判断，不让缺少辅助报告阻断调查。

## 三种路径

1. **只读调查**：用户问根因、现象或风险时，读取必要证据并回答，可参考 cs-issue-analyze；不改代码、不写报告、不自动进入修复。明确要求记录问题时才使用 cs-issue-report 写文档。
2. **已授权的小范围修复**：根因明确、有文件证据、影响局部且无新增高风险时，说明根因和改动范围后直接进入 cs-issue-fix。无需先询问是否走“快速通道”，也不强制写 report 或 analysis。
3. **复杂或高风险修复**：需要迁移数据、改跨模块约定或方案有实质取舍时，收集问题事实、分析根因和方案，再取得必要确认后实施。用户明确要求完整 CodeStable 流程时沿用 report -> analysis -> fix-note。

## 执行规则

- 路径可以随证据调整。进入调查时根因不明，后来已明确且风险小，不必为保持旧分流决定继续填写无用文档。
- 已有批准方案并要求修复时，不再次询问开始许可；只在实质扩大范围、风险变化或必须用户操作时暂停。
- 普通审查不自动变成修复，不顺便优化无关代码。
- 修复要核对原触发路径、期望结果和直接影响范围；未运行或需现场验证的部分如实列出。
- 现有 CodeStable 项目写一份 `{slug}-fix-note.md`；没有该目录体系时在最终答复中保留根因、改动和验证记录，不自动初始化。

## 记录位置

完整流程沿用 `.codestable/issues/YYYY-MM-DD-{slug}/`，其中 `{slug}-report.md` 记录问题事实，`{slug}-analysis.md` 记录根因与已选方案，`{slug}-fix-note.md` 记录实际修复和验证。不要重复创建同一问题的记录。

## 结束

完成已授权范围后报告实际结果、剩余风险和必要的后续动作。不把未完成的验证写成通过，不把一句重复确认当作结束的前置条件。提交、发布和额外归档需要对应授权。
