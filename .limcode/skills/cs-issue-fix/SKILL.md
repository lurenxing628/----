# cs-issue-fix

## 启动必读

启动、授权与续作遵守根目录 `AGENTS.md`；读取或复用 `.codestable/attention.md`。路径、状态与收尾按需查 `.codestable/reference/shared-conventions.md`，缺辅助材料不阻断只读调查或已授权局部工作。

根因和方案已由真实证据核实，修复已获当前任务授权（可来自 analysis 或局部调查），你的活是按方案改代码、验证效果、写下修复记录。

fix 阶段最容易出问题的不是改代码本身，而是**改的过程中冒出的"顺手"冲动**——顺手优化、顺手重构、顺手加抽象。每项单独看说得通，但合在一个 PR 里让别人分不清"这次到底为了修 bug 改了什么"。

> 共享路径与命名约定看 `.codestable/reference/shared-conventions.md` 第 0 节和 `cs-issue` 的“记录位置”。

## 两种入口

### 标准路径（有 analysis）

1. **方案已确认**——读 analysis，确认 `doc_type=issue-analysis` 且 `status=confirmed`，第 5 节用户选定了哪个方案
2. **上下文读全**：analysis 全文 + report 全文 + analysis 第 1 节定位的所有代码 + `.codestable/attention.md` + 沉淀目录搜索：
   - `python .codestable/tools/search-yaml.py --dir .codestable/compound --filter doc_type=trick --filter status=active --query "{关键词}"`——确认修复方式不违背已有库用法 / 模式
   - 同样命令换 `--filter doc_type=explore`——确认修复点和已有证据不冲突
3. **说明起点**——用户已确认方案并要求实施时，说明文件范围后直接开始，不再次询问同一授权。仅有分析请求或出现新增高风险动作时才等待确认。

### 快速通道（无 report / analysis，局部调查后直接进入）

进入此入口需要真实代码证据和明确修复授权，不要求先经过报告阶段。

1. **明确陈述根因**："`{文件}:{行号}` 的 {具体代码} 存在 {问题描述}"，附实际证据，不把要求用户确认当作替代根因核实。
2. **给修复方案**——改哪里、怎么改（一两句话，不写完整分析文档）
3. 用户已明确要求修复，且改动小、根因明确、没有新增高风险时，说明方案后直接实施；只读检查不授权修改，范围扩大或风险变化时再确认。
4. 按启动规则读取或复用 `.codestable/attention.md`；缺失不自动初始化。
5. **补搜沉淀目录**——快速通道也要查一遍 `compound/`（trick + explore），避免误把已知边界条件当新问题

## 实现期间的约束

### 只改已确认范围内的文件

标准路径的修复范围来自 analysis 第 5 节"推荐方案"的"影响面"。快速通道范围来自已授权问题与核实的方案。必要的相关文件落点可自行确定；无关问题不顺手修改，实质范围变化再确认。

发现范围外值得改的记一条"顺手发现"不改代码：

```markdown
> 顺手发现：{文件:行号} {问题简述}。不在本次修复范围，可后续另开 issue。
```

为什么这么严：顺手改的代码不在分析里，验收对不上，git blame 分不清哪些改动是为这个 bug。

### 改动最小化

修复针对根因，不引入与当前问题无关的抽象、接口或模式。必要且局部的内部整理可随修复验证；改变公开契约、模块职责或实质扩大范围时再确认。

为什么：bug 修复天然窄场景，引入新抽象意味着只有这一个使用点支撑——典型过早抽象。

### 代码质量反射检查

修 bug 看似动作小但 AI 写修复代码一样会漂——大文件再塞特殊处理、大类再加方法、为绕开边界加 `if` 分支。反射检查见 `shared-conventions.md` 第 7 节。

反射信号用于判断职责和影响。修复必需的局部整理可一并实施和验证；独立重构记为后续建议，新增风险或扩大范围时再确认。

### 连续完成已授权范围

同一范围内的改动和验证连续完成，过程中简短报告实质进展，不每改一处就停下等回复。新增数据风险、关键约定变化、实质扩大范围或需要用户操作时才暂停。结果模板按需读取 reference.md。

## 验证清单

修复改完后逐项核对：

- [ ] **复现步骤验证**——标准路径按 report 第 2 节走一遍；快速通道按已核实的最小触发方式走一遍，问题不再出现
- [ ] **期望行为验证**——标准路径按 report 第 3 节验证；快速通道按已明确的期望行为验证
- [ ] **影响面回归**——标准路径按 analysis 第 4 节"潜在受害模块"验证；快速通道至少验证本次改动直接影响的入口
- [ ] **前端改动浏览器验证**（如涉及）——按 `.codestable/attention.md` 的硬要求执行，不能只 typecheck
- [ ] **相关测试通过**——有测试覆盖到修复区域就跑一遍

---

## 修复未生效时：日志调试升级

走完验证清单仍**问题复现**或行为与期望不符——**别在原有猜测上反复试错**，切换到日志调试模式重新收集运行时证据。

为什么切换：反复试错本质是猜测在原假设下还有什么可能性，但如果原假设就错了再猜也是绕圈。日志强制看实际运行时数据，往往一眼看出原假设哪里偏了。

日志调试步骤、用户取日志提示词、循环限制见同目录 `reference.md`。

## 写 {slug}-fix-note.md

在已采用 CodeStable 的项目内，验证后写一份简短 `{slug}-fix-note.md`，记录根因、改动、实际验证与限制，不重复生成分析报告。未采用该流程且用户只要求小范围修复时，在最终答复中记录即可，不自动初始化。标准和快速模板按需读 reference.md。

---

## 退出条件

- [ ] 所有改动文件已提交或列清单
- [ ] 适用验证已完成；未完成或需用户实测的项目明确列出，不把限制写成通过
- [ ] 已按项目约定保存修复记录，或在未采用该流程时给出完整结果说明
- [ ] 没有未处理的"顺手发现"（都进后续 issue 列表）
- [ ] 没有范围外改动（或已和用户确认）
- [ ] 实际结果及剩余限制已交付；需用户现场确认时标明待确认，不虚报完成，也不空等无必要的回复

## 收尾提交

按 `shared-conventions.md` 第 4 节"scoped-commit"规则执行。本阶段：

- **提交范围**：修复代码 + `{slug}-fix-note.md` + 本次一并更新的 report / analysis（快速通道通常没有 report / analysis）
- 报告实际修复、验证和记录状态；提交只在本轮明确授权时执行，不固定追问。

---

## 退出后

标准路径按实际情况说明 report、analysis、fix-note 与验证的状态，未完成项不称为闭环。

快速通道说明实际修复和验证结果、fix-note 位置及未验证部分。

只在确有必要时合并提出一次后续建议，不逐项追问；本轮未授权的归档或提交不自动执行：

1. 暴露了值得复用的坑点 → "沉淀 learning？（`cs-learn`）"
2. 沉淀出长期约束 / 规约 / 技术决定 → "归档决定？（`cs-decide`）"
3. 这个 bug 暴露了项目通用的硬约束 / 命令陷阱 / 环境设置（一两行能讲清、CodeStable 技能每次启动都该知道）→ "记到 attention.md？（`cs-note`）"
4. 已明确授权提交时按收尾提交规则执行；不重复索要相同授权

建议：把 issue 目录文件和代码改动放同一次提交方便追溯；"顺手发现"另开 `cs-issue-report` 处理别塞这个 PR。

修复中发现问题实际是功能缺失（不是 bug）→ 建议另开 `cs-feat`，别在 issue 工作流里偷偷做新功能。

---

## 容易踩的坑

- 修完没走验证清单就宣告"修好了"
- 顺手改了 analysis 范围外的代码
- 未说明影响就改变公开约定或实质扩大范围
- `{slug}-fix-note.md` 没建就宣告完成
- 发现影响面回归有问题但写"轻微影响可忽略"——要修到干净
- 前端改动只 typecheck 就报通过
- 把仍需用户实测的结果写成已经确认完成
- 修复未生效继续原假设上反复猜测试错，不切换到日志调试
- 日志调试结束后没清理临时 log 就提交
- 未经本轮明确授权自行提交
- 用户没明确同意就 `git commit`
