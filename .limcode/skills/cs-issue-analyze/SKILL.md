# 故障根因分析

启动、授权与续作遵守根目录 `AGENTS.md`；读取或复用 `.codestable/attention.md`。路径、状态与收尾按需查 `.codestable/reference/shared-conventions.md`，缺辅助材料不阻断只读调查或已授权局部工作。

兼容阶段入口：由 `cs-issue` 的只读、局部、完整三种路径选择；不重新分配用户已经明确的任务范围。

## 输入与续作

- 依据当前代码、日志和实际数据调查；问题报告提供线索，不代替证据。
- 有 report 时读取相关事实与复现信息；缺报告、元数据或模板章节不阻断具体故障调查。
- 已有 analysis 时核对关键事实是否仍然有效，从缺失证据继续，避免重做已完成调查。
- 按问题检索相关架构约定、需求边界和 compound 决定；不扫描全部历史文档。

## 分析

1. 定位触发入口、关键定义与调用方，产品定位遵守项目 symbol-locator 要求。
2. 还原触发路径：输入和状态如何流转，在哪个环节与期望分叉；不能只根据症状猜根因。
3. 用真实代码、运行证据或可复算结果验证根因候选，区分已证实、待核实和无法复现。
4. 评估直接影响、同类入口、数据完整性及严重程度，不把理论可能性写成已发生故障。
5. 给出推荐修法与验证方式。只有存在实质不同的可行方案时才比较备选，不强制凑两种或三种方案。

## 交付与衔接

- 只要求分析：交付结论、`file:line` 或运行证据、修复建议和未验证范围即可；不写文件，不等待用户确认“分析准确”才结束。
- 明确要求保存分析或已选择完整流程：在现有 issue 目录写 `{slug}-analysis.md`，模板按需读 `reference.md`。沿用 `doc_type: issue-analysis`、`issue`、`root_cause_type`、`related`、`tags`；记录定位、失败路径、根因、影响和实际候选方案。
- `status: confirmed` 只用于修复方案已经确定且有对应授权的记录；待决定时保持 `draft`，不得虚构用户确认。
- 用户已经授权修复、根因明确且风险局部时，进入 `cs-issue-fix` 连续完成；新增数据风险、关键约定变化或重大取舍时再取得必要确认。
- 用户仅授权分析时，发现根因不自动授权修改。报告存在不等于方案已获实施授权。
