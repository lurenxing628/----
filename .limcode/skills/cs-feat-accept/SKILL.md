# cs-feat-accept

## 启动必读

启动、授权与续作遵守根目录 `AGENTS.md`；读取或复用 `.codestable/attention.md`。路径、状态与收尾按需查 `.codestable/reference/shared-conventions.md`，缺辅助材料不阻断只读调查或已授权局部工作。

先按用户要求选择范围：仅“检查”“审查”时默认只读；“出验收报告”只授权报告；明确要求完成验收闭环或已授权完整功能流程时，执行下面的文档回写与适用验证。修正代码偏差仍须有实施授权，不由“验收”一词自动推定。

完整验收闭环核对四件事：

1. **核对实现有没有偏离方案**——逐层对照 `{slug}-design.md`，发现偏差明确记录；已获修复授权时修正并重验，否则报告未通过，不为了勾选完成而自动改代码
2. **把 feature 归并到整体架构**——对照方案第 4 节，实际去更新架构中心目录下的相关 doc
3. **能力落档到 requirement**——draft req 对应的能力实现完成后升级为 current（保留愿景，追加变更日志）；从未写过 req 的能力 backfill
4. **完成状态回写到 roadmap**——方案 frontmatter 有 `roadmap` / `roadmap_item` 字段且适用验收真正通过时，才将 items.yaml 对应条目改为 `done` 并同步主文档

漏掉任何一件的代价：架构 doc 过期下个 feature 读到错信息；req 和实际能力脱节；roadmap 规划层和实际进度脱节，下次推进会重复跑流程。

**完整验收闭环需要报告，普通只读检查不自动落档**。后人查"上次这个功能验收时确认了哪些行为"，没报告就只能翻 git diff 重新推断。

> 共享路径与命名约定看 `.codestable/reference/shared-conventions.md` 第 0 节。
> `cs-feat-ff` 不进入本技能：fastforward 不写 design / checklist / acceptance，完成后以 `{slug}-ff-note.md` 作为轻量闭环。

## 跟 design 的章节强依赖

本技能整套对照表按 design 当前章节编号硬编码。**design 升级章节名 / 编号时本技能必须同步**，否则下面所有"第 X 节"指针都指错地方。

**标准 design 章节快照**：

- 第 0 节：术语约定
- 第 1 节：决策与约束（需求摘要 / 复杂度档位 / 关键决策 / 前置依赖）
- 第 2 节：名词与编排（2.1 名词层 / 2.2 编排层 / 2.3 挂载点 / 2.4 推进策略 / 2.5 结构健康度与微重构）
- 第 3 节：验收契约（关键场景清单 + 反向核对项）
- 第 4 节：与项目级架构文档的关系

## 启动检查

1. **核对当前实现**——依据当前代码、相关验收要求及必要历史确认功能是否存在；git status 干净或最近提交没有相关改动不代表未实现。发现实现缺失时只读/报告模式记录未通过，不自动跳入实施；已有实施授权才继续补齐。
2. **验收依据明确**——完整流程核对 `doc_type=feature-design`、`feature`、批准状态及相关章节；仅检查时用现有明确要求，缺失依据列为限制，不为标签数量机械阻断
3. **`{slug}-checklist.yaml`**——完整流程核对 feature、steps 和 checks。记录与代码不一致时先核实；未完成实现保持未通过，不为只读检查补材料或机械退回。恢复时保留仍有效的状态
4. **核对范围内上下文**——完整验收读取方案与 checklist；定向检查读取对应要求和场景。架构只读与实际变化有关的章节，依据当前实现和必要 diff/历史核验，不把所有引用文档一并全量加载。
5. **断点恢复**——`{slug}-acceptance.md` 已存在且部分填好 → 从下一个未完成节继续，仅在相关实现、验收条件和证据未变化时复用已 `passed` 的项，变化部分重新核验；汇报"上次做到第 X 节，从第 Y 节继续"

## 验收报告模板

完整验收报告逐节填写；不适用项注明理由，不为凑齐节数制造文档或检查。完整 9 节模板见同目录 `reference.md` 的"验收报告模板"；报告路径在 feature 目录下（位置看 `.codestable/reference/shared-conventions.md` 第 0 节）。

报告 9 节固定为：接口契约核对、行为与决策核对、验收场景核对、术语一致性、架构归并、requirement 回写、roadmap 回写、attention.md 候选盘点、遗留。

---

## 核对节奏

按所选范围逐节核对；获准回写清单时记录真实状态，通过为 `passed`，失败为 `failed`。只有实际修正并重验后才能改回 `passed`。报告可以如实记录失败而完成交付，但不能把失败验收宣告通过；只读或仅报告模式不改清单。

第 1/2 节最容易暴露偏离，先做。第 2 节挂载点反向核对**必须实际 grep + 沙盘推演**，不能凭印象勾选。第 5/6/7 节是写文件的动作，不是自评。

## 退出条件

下列清单对应完整验收通过。只读或仅报告任务以交付实际结论和未验证范围为结束，不执行未授权回写；发现失败时可结束报告，但保持验收未通过。

- [ ] 验收报告 9 节都填完
- [ ] 第 1/2 节核对全部勾选，无未处理偏差（含挂载点 grep + 拔除沙盘推演）
- [ ] 第 3 节场景核对全部勾选，前端已浏览器验证
- [ ] 第 4 节术语一致性无遗漏
- [ ] 第 5 节归并：每条有明确结论，需要更新的 doc 已实际写入
- [ ] 第 6 节 req 回写有结论：跳过 / 未变 / 已 backfill / draft→current / 已 update
- [ ] 第 7 节 roadmap 回写有结论：跳过（非 roadmap 起头）/ 已更新（items.yaml + 主文档同步，yaml 通过校验）
- [ ] checklist 所有 checks 都 `passed`
- [ ] 约定需要的用户终审已确认；尚未确认时明确保持待终审，不虚报通过

## 退出后

按实际结果说明已验证、未通过、待现场确认及已写入的文档，不套用一律完成的话术。

按 `shared-conventions.md` 第 3 节把确有价值的后续项合并提示一次，不逐项追问；已授权项直接执行，未授权项不自动追加：

1. 复用价值的坑点 / 经验 → "需要沉淀 learning 吗？（`cs-learn`）"
2. 长期约束 / 技术选型 → "需要归档决定吗？（`cs-decide`）"
   - design 第 2.5 节已有候选 convention 时核实是否仍有效，与其他后续项合并提示，不另开一轮追问
3. 接口变更 / 用户可见行为变更 → "需要更新指南吗？（`cs-guide`）"
4. 库公开接口（组件 / 函数 / 命令）变了 → "需要更新 API 参考吗？（`cs-libdoc`）"
5. 第 8 节有 attention.md 候选 → 合并列出建议；用户明确同意后用 `cs-note` 归类、查重，不逐条追问
6. 只有本轮明确授权提交时才执行 scoped-commit；否则不自动提交

收尾提交规则看 `shared-conventions.md` 第 4 节。提交范围：功能代码 + 方案 doc + 验收报告 + 本次实际更新的架构 doc / req doc / roadmap items.yaml + 主文档。

---

## 容易踩的坑

- "测试都过了" → 测试通过 ≠ 验收场景满足，要逐条核对第 3 节
- "我肉眼看了一下" → 按清单走，逐项勾选
- 把尚未处理的接口偏差写成验收通过，或未获授权就修代码
- 挂载点反向核对只看清单不 grep——漏记的挂载点溜进项目，后面拔不干净
- 第 3 节前端改动只 typecheck 没浏览器跑过
- 第 5 节归并写"整体不影响架构"一句话带过，没逐条核查
- 架构 doc 需要更新而只写"建议以后更新"——归并是当下动作不是建议
- 第 7 节只改 items.yaml 没同步主文档，两份不一致
- 只读检查擅自回写 roadmap，或验收失败却把条目标为 done
- 约定的人工作业尚未完成却宣告验收通过
- 用户没明确同意就 `git commit`
