# 排产时间小数秒在保存、采用与读取之间保持一致

状态：源码修复与宿主回归通过；待新冻结包 Win7 实机复验。

此前算法生成合法的小数秒时间，但采用校验和多个读取端只认整秒。5000 工序候选因此出现不能采用、交付风险未知，以及页面输入丢失精度。

统一使用 core/shared/local_datetime.py 解析无时区本地时间。整秒序列化不变，非零小数秒使用六位精度；原 SQL TEXT 字段和 schema 32 不变。候选指纹、正式计划写入、试调草稿/归档、零工时证明、计划查询、交付风险、日历、报表均保留微秒。日期无效、时区偏移、超过六位小数仍拒绝。

前端用规范化时间字符串比较先后，避免 JavaScript Date 的毫秒精度把 1 微秒区间误判成零。编辑开始时间与计划范围保留原始文本；只改资源时不改时间。任务详情按需显示小数秒。现场手工报工及外协收货输入仍按原整秒业务合同，不扩展无关输入接口。关键链间隔用精确整数分钟向下取整，避免 59.999999 秒被舍入成一分钟。

主代理独立验证：time-backend.xml 123 项；time-frontend.xml 4 项；downstream-time.xml 27 项（有交叠，不能相加）；Chrome109 原生试调编辑、1 微秒和错误日期操作通过。日志位于 evidence/Win7Fixes/20260926/tests。新增测试已登记进中央必测组，真实浏览器测试保持显式选择。
