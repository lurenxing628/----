# 复杂样例验收发现的问题

基线为 `b8cc5301`。本记录目前是宿主 Python 3.8 真实业务接口与排产证据。Win7 独占窗口已交接，SP1 x64 / PowerShell 2.0 / 离线 Python 3.8 构建环境已确认；最终冻结程序和功能实机验收尚未完成。

## 普通批次准入遗漏范围外执行占用

真实两批计划采用后，第一批有未完成报工，只选第二批时原预览仍允许受理；计算随后因正式计划范围外缺少可信剩余安排而失败。旧事件的预计资源释放已经过期也存在同根因。原 `piece_admission_issues` 仅检查分件批次，普通批次遗漏了 worker 必须消费的完整执行范围。

改为 `candidate_admission_issues`，在现有预览和受理共用的 `_resolve` 中复用 worker 的只读输入准备。已有阻断时不重复准备。没有放宽执行保护、猜测剩余安排、创建新保护层或更改计算逻辑。

8 项针对性测试通过，包含真实 HTTP 预览/新旧受理拒绝、数据库与任务派发不变、合法连续报工补齐后再次正常受理和真实 worker 完成。原拒绝及失败记录保留。

## 独立分析遗漏最终输出预算

5000 工序真实计划的独立分析曾返回 HTTP 200、canonical JSON 9,018,489 字节，超过既有 8 MiB；合并值班台已经正确保留清单并显示分析超限。独立分析和候选比较借用候选响应组装方法，遗漏了值班台的最终预算。

两个独立入口在最终 envelope 上复用 `payload_size`，超限按现有 API 边界返回 413。真实大说明/大存量名称及非有限数字用例证明旧行为错误，修复后 22 项相关测试通过。预算不提高，来源不截断。

分析副本中的名称、身份和计划时间与已有任务重复。仅去掉这些重复字段，并让实际分析面板一次建索引复用任务；完整执行状态、实际时间、依据、质量缺口、工时、风险和记录引用保留。清单、详情和历史仍有完整来源。5000 条执行行和任务逐字段核对，真实 React 标题和 10000 个导航处理一致；只读重组 canonical 合并响应为 8,338,623 字节。完整流程报工后的真实 HTTP 大小和 Win7 界面仍需复验。

## 样例初始化记录首回并发覆盖

旧进度文件用普通写入创建，两线程和两进程都能同时成为创建者，覆盖相同准备记录。改为同一记录首次排他创建、后续正常保存；无需另外的锁文件、线程或重试。5 项创建/更新/竞争测试以及真实 seeded→完整小样例接续通过。CLI 在竞争失败时明确提示已有记录。

## 验收程序的容量适配

整次运行 `partial` 不等于其完整原算法候选不完整。比较预算耗尽跳过其它候选时，完整方案被采用和试调误挡的共同判定修复见 [专项记录](../2026-10-10-partial-candidate-adoption/fix-note.md)。

第二版 5000 工序正式计划因带历史比较投影触发整份 workspace 的单次读取限额。验收程序正在复用已有按时间范围分段查询和导出，每段保持自己的快照、范围与派生投影；全部工序身份和原时间另做完整核对。不能把局部风险或局部快照当成完整全局结果。

## 已确认的产品边界

没有可信剩余安排的未完成报工会保护整个相关正式执行范围，当前不支持其后的再次排产，即使只选其它批次。样例保留真实分次报工，并验证准确拒绝和原计划/报告不变。自制连续组没有现行写入入口，不作为已支持能力。
