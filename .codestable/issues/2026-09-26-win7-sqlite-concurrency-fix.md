# Win7 并发读取导致回执重放失败及排产领取中断

状态：修复与定向回归进行中；真实 Win7 冻结包复验另由总验收记录提供。

## 原因与证据

原 `4df78c53` 的 Win7 验收确认：同一请求的已提交回执重放仍进入 `BEGIN IMMEDIATE` 写事务，1000 工序压力期间在 COMMIT 出现 `database is locked`；5000 工序压力期间，批次读取事务覆盖较慢的账本投影和 JSON 指纹计算，排产领取事务 COMMIT 失败后尚未开始计算就进入保守对账停用路径。原请求中断、执行器持续不可用。既有证据保留在原工作目录的 `codestable/issues/2026-09-26-win7-stress-sqlite-commit-lock.md` 和 `evidence/Win7Acceptance/20260926/`，不改写原失败结论。

## 修复范围与不变量

1. 普通数据库命令先通过一次 SELECT 读取不可变的已提交回执；命中时仍核对 action、context_ref 和规范化输入哈希。未命中才进入写事务，并在写锁内再次查重。回执损坏、真正不确定的 COMMIT 仍按原请求编号查询恢复，不自动重做业务写入。
2. 批次纯查询先在一个读事务里读齐表、身份、工艺和账本事实；结束事务后计算派生投影、指纹、排序和页面结果。详情的身份解析也来自这份快照。会继续读库的预览与写入校验保留原事务语义；已有外层事务不被偷偷提交。全量投影及页外无效数据的拒绝语义不变。
3. 仅把领取阶段遇到的明确 SQLite BUSY/LOCKED 标为待核实重试。旧连接已结束事务并关闭，新连接核对作业仍未开始、没有执行器/候选/最终回执、原受理与输入一致，且运行锁仍属于本进程；下一领取写事务再检查一次。最多三次领取尝试，退避时不持数据库连接。计算和结果 COMMIT 的不确定性不进入这条重试路径。
4. 进一步对 5000 工序事实读取剖析发现，工序永久身份查询的 JOIN 计划会反复扫描全部 operation 身份。固定从已限定的 `BatchOperations` 主键集合查起，再用既有 `(kind, source_key)` 索引匹配身份；不新增索引、不缓存事实、不跳过 schema 与缺失身份校验。

没有切换 WAL、延长 SQLite 超时、删除锁文件或放宽输入/授权校验。保持 Python 3.8 / Win7 兼容。

## 定向验证

- `tests/workbench/test_commands.py` 与 `test_commands_replay_lock.py`：30 通过。真实 DELETE 模式下另一连接持读锁或写预留锁时已提交回执仍可重放；三类同 key 内容冲突仍拒绝；首次只读未命中后另一连接提交时，事务内二次查重只返回一个结果。
- commands、批次、物料、工艺阶段命令回归：459 通过。Python 3.8.10；未据此宣称真实 Win7 压力通过。
- 批次分层与既有账本/模板/文件/workflow：252 通过（其中 5 项新增）。新测试在快照读完后让第二连接真实修改数量与身份并提交，再禁止原连接全部 SQL，确认页面、详情、选择、指纹仍完全来自原一致快照。
- 领取安全边界：24 通过，覆盖 COMMIT 已成功但丢失应答、回滚失败、三次耗尽、领取后证据变化、原受理回执损坏、运行锁丢失等情况下不会重复计算；结果 COMMIT 在提交前/后报同样的锁错也只计算一次，分别保留保守中断或真实完成结果。
- `test_plan_operation_refs_query_cost.py`：10001 工序和重复输入编号的实际 SQLite VM 指令上限回归通过，约束分块查询不会退回反复扫全表。
- SQLite 连接策略对相同 400 个工序的实测查询由约 0.219 秒降至 0.000756 秒；[查询计划](2026-09-26-win7-sqlite-concurrency-evidence/query-plan-comparison.jsonl) 记录两者返回等价，以及新的主键与既有部分索引查找路径。
- 同一合成 100 批次/5000 工序数据库在宿主 Python 3.8.10 / SQLite 3.35.5 上交替读取三对，新旧 scope 都使用优化后的 JOIN，旧 scope 持锁为 0.982/1.052/0.970 秒，新 detached 为 0.147/0.155/0.146 秒，约缩短 85%；新总响应约 1 秒，六次完整指纹一致。[原始分解记录](2026-09-26-win7-sqlite-concurrency-evidence/profile-final-alternating.json)。这是宿主测量，不能代替 Win7 压力验收，也不能把受并行负载干扰的早期时长当容量保证。
- 真实领取竞争与既有 `test_run_runtime*.py`、`test_run_jobs*.py`：90 通过（274.04 秒），包含真实 DELETE 读锁导致 claim COMMIT 回滚、写预留锁导致 claim BEGIN 失败、退避中停机、计算阶段锁错四项新增回归；前两项都确认关闭旧连接、新连接领取、只计算一次、保存四候选且执行器继续可用。原 5000 工序 / 20000 候选明细容量测试也通过。与上述 guard 组合为 114 个排产相关用例通过。

上述跨领域多组回归有交集，不相加为独立用例总数。

## 剩余边界

持续的数据库占锁或证据不一致仍会停止执行并保留原请求供对账。这是避免重复计算的安全边界，不是无限等待机制。本修复缩短批次读锁，不承诺所有大数据投影已经完成 CPU 性能优化；需使用实际 Win7 冻结包重跑原 1000 / 5000 工序并发场景，观察服务器错误、排产结果和后续运行能力。
