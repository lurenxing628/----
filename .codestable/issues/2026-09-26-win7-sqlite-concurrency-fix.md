# Win7 并发读取导致回执重放失败及排产领取中断

状态：修复与定向回归进行中；真实 Win7 冻结包复验另由总验收记录提供。

## 原因与证据

原 `4df78c53` 的 Win7 验收确认：同一请求的已提交回执重放仍进入 `BEGIN IMMEDIATE` 写事务，1000 工序压力期间在 COMMIT 出现 `database is locked`；5000 工序压力期间，批次读取事务覆盖较慢的账本投影和 JSON 指纹计算，排产领取事务 COMMIT 失败后尚未开始计算就进入保守对账停用路径。原请求中断、执行器持续不可用。既有证据保留在原工作目录的 `codestable/issues/2026-09-26-win7-stress-sqlite-commit-lock.md` 和 `evidence/Win7Acceptance/20260926/`，不改写原失败结论。

## 修复范围与不变量

1. 普通数据库命令先通过一次 SELECT 读取不可变的已提交回执；命中时仍核对 action、context_ref 和规范化输入哈希。未命中才进入写事务，并在写锁内再次查重。回执损坏、真正不确定的 COMMIT 仍按原请求编号查询恢复，不自动重做业务写入。
2. 批次纯查询先在一个读事务里读齐表、身份、工艺和账本事实；结束事务后计算派生投影、指纹、排序和页面结果。详情的身份解析也来自这份快照。会继续读库的预览与写入校验保留原事务语义；已有外层事务不被偷偷提交。全量投影及页外无效数据的拒绝语义不变。
3. 仅把领取阶段遇到的明确 SQLite BUSY/LOCKED 标为待核实重试。旧连接已结束事务并关闭，新连接核对作业仍未开始、没有执行器/候选/最终回执、原受理与输入一致，且运行锁仍属于本进程；下一领取写事务再检查一次。最多三次领取尝试，退避时不持数据库连接。计算和结果 COMMIT 的不确定性不进入这条重试路径。
4. 进一步对 5000 工序事实读取剖析发现，工序永久身份查询的 JOIN 计划会反复扫描全部 operation 身份。固定从已限定的 `BatchOperations` 主键集合查起，再用既有 `(kind, source_key)` 索引匹配身份；不新增索引、不缓存事实、不跳过 schema 与缺失身份校验。

没有切换 WAL、延长 SQLite 超时、删除锁文件或放宽输入/授权校验。保持 Python 3.8 / Win7 兼容。

## 剩余边界

持续的数据库占锁或证据不一致仍会停止执行并保留原请求供对账。这是避免重复计算的安全边界，不是无限等待机制。本修复缩短批次读锁，不承诺所有大数据投影已经完成 CPU 性能优化；需使用实际 Win7 冻结包重跑原 1000 / 5000 工序并发场景，观察服务器错误、排产结果和后续运行能力。


## 真实 Win7 第一版重测与预览耗时修复

修复包 0b9a682f 的 1000 工序重压：4 路并发读取，实际负载 300.266 秒，2266 次请求零错误；3 次独立排产和 9 次幂等重放通过，共保存 12 个完整候选。正常停止含 Chrome、SQLite/FK/业务表未改动检查、不同 PID 的真实重启及候选哈希回读均通过。

同包 5000 工序、8 路读取的第一轮未通过：1326 次请求中，排产预览出现一次 30 秒超时，没有 HTTP 500；观察器因此停止后续写入，保留全时长读取。离线数据库确认 0 个受理任务、0 个候选，100 批/5000 工序未变，完整性和外键检查通过。原失败报告位于 evidence/Win7Fixes/20260926/stress/level-5000/，不能改判通过。

继续定位发现：Python 3.8 的 dataclasses.asdict 对不可变原子值仍反复调用 deepcopy；5000 工序读链三次转字典产生大量重复工作，8 个批次读取线程会同时消耗计算资源。追加改动：

- ExecutionProjection/ProductionReport 快照保留标准 dataclass、容器与其他对象复制语义，对 str/int/float/bool/bytes/None 直接返回不可变值。可变报工历史、撤销记录、写入上下文仍深复制，不能通过返回 DTO 修改原对象。
- 没有写入上下文工厂（或明确关闭上下文）时，报工读取复用基础读取器已检查大小的同一组 DTO，不再重复序列化原样数据；添加上下文时继续检查最终大小。两条大小上限拒绝分支均有实际回归。
- 原始事实指纹转换对 str/int/bool/None 快速返回，日期、非有限浮点和 BLOB 的原编码不变。
- 批次只读路由最多同时进行两路完整查询；其他请求在开始 SQLite 事务前排队，不截断、缓存或替换数据。排产预览和 worker 不占这个额度。8 路真实 Flask/SQLite 并发回归确认峰值两路、等待者无数据库读锁、写入可提交，8 个结果完整且各自保持快照一致。

主代理独立回归：serialization-regressions-fixed.xml 110 passed；read-budget-fixed.xml 86 passed（有交叠，不合计）。5000 工序预检和批次查询的输出 JSON 长度及 SHA256 与原实现相同，见 tests/serialization-equivalence-5000.json。宿主剖析只是定位依据，最终效果必须重新冻结 EXE 并以相同 30 秒请求限制、1000/5000 原负载重测，不提高超时门槛。

## 第二轮 Win7 5000 工序：GIL 交接争用

890405a2 实机功能验收 185 项请求及重启后 4 项通过；1000 工序 4 路/300 秒压力 2951 请求零错误，3 个作业/12 个候选及重启、离线检查通过。5000 工序 8 路/600 秒仍失败：1187 请求中 71 个批次 GET 超过原定 30 秒，3 个作业均完成，12 个候选及真实重启哈希、SQLite/FK、业务数据未变检查通过。该轮失败报告保留在 stress/level-5000-890405a2/。

在同一实际导出的 5000 工序库上，Python 3.8.10 查询独占约 0.995 秒；加入一个持续纯 Python 计算线程后约 45.42 秒，其中 SQLite Cursor.fetchall 占 38.78 秒。SQLite 逐行释放再获取 GIL，计算线程反复抢先执行，符合 Python 官方记录的 [GIL convoy 问题](https://bugs.python.org/issue7946)。详见 tests/contention-5000.json。1 毫秒切换仍约 30.82 秒；0.1 毫秒约 5.37 秒（含剖析开销）。这不是数据库锁失败或候选存储增长。

51892b35 曾采用两层约束：大批次只读扫描限制为一路，以 FIFO 等待队列保证先到请求不会被新请求越过；服务持有期间将解释器切换间隔设为 0.1 毫秒。此解释器调度方案已因下述实机失败撤回，只保留 FIFO 读取额度。

独立宿主持续计算与 8 个同时读取的比较：两路读取/0.1 毫秒仍最慢 61.30 秒；单路容量实验最慢 21.65 秒。0.01 毫秒为 18.86 秒。该宿主改善未能在 Win7 重压下成立，不能据此宣称修复完成。

## 最终方案：冻结包的只读计算进程

51892b35 的 5000 工序重测仍出现读取超时，首个排产在 600 秒观察截止时仍运行；停止读取负载后才完成，后两轮没有受理。失败后的 60 秒诊断借用 timeBeginPeriod(1) 将 Win7 当前计时粒度从 15.6 毫秒改到 1 毫秒，也没有解决争用；finally 已调用 timeEndPeriod(1)，实际记录确认恢复 15.6 毫秒。该干预单独记录为 DIAGNOSTIC_INTERVENTION.json，不参与任何通过结论，程序中不包含计时器调整。

现改为冻结 Windows 包使用 spawn 独立计算进程：

- 主线程的作业执行器继续独占调度锁，并负责领取、结果新鲜度核对、唯一候选写入与最终事务；子进程不领取作业、不分配正式版本、不打开原生产数据库。
- 主执行器用 SQLite Backup API 生成本次独有的一致副本；子进程只读打开副本，仍运行原内存快照、完整输入校验、四候选算法及结果验证。结果与进度仅经本次进程管道返回，主进程收到结果并确认子进程正常退出后才进入原提交路径。
- 输入过期、子进程异常退出、管道中断、父进程结果提交不确定都不重做计算。父进程退出时专用管道 EOF 使只读子进程退出；正常停止仍等待已有作业完成并回收子进程后才释放宿主所有权。临时目录仅清理本次创建的副本，先回收子进程再清理。
- 两个入口调用 multiprocessing.freeze_support，并在 __mp_main__ 导入时禁止自动创建 Flask 应用。源代码单进程执行与原核心接口保持可测；冻结 Windows 宿主显式注入隔离计算器。
- 撤回 sys.setswitchinterval，不改变系统计时器、电源、HTTP 30 秒限制、SQLite 事务模式或排产算法。

process-isolation-extended.xml：14 通过（包含现有 FIFO 查询用例）。真实 spawn 回归覆盖完整候选保存且业务数据不变、幂等终态不再次建子进程、计算中修改原资料后父进程拒绝保存、子进程输入过期错误码保留、异常退出与父提交失败不重算、进度处理失败回收子进程、调用方事务拒绝、父进程突退出看门狗、宿主停止等待回收、两个入口的 spawn 导入无建库副作用。真实 Win7 冻结包压力结论仍需重新生成证据。
