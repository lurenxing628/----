## 修复范围

1. SQLite 已提交回执采用只读重放；仅可证明未开始的排产领取竞争允许有限重试；完整读取快照离开数据库事务后再计算投影。
2. 批次大查询按先来后到逐个执行；冻结 Windows 包将候选计算放到独立只读进程，主程序仍独占领取、数据新鲜度检查和结果事务。子进程异常不自动重算，正常退出与父进程异常退出均有回收约束。
3. 排产小数秒在候选、正式计划、试调、交付风险、导出及前端编辑间保持；补齐非法日期、边界及零时长处理。
4. 修正启动器 CRLF、中文路径、PID/BOM 与进程识别；采用 Win7 支持的原生进程查询以避免停止流程长时间阻塞。
5. 修正候选甘特标签覆盖固定页头，以及打印轴边界、长任务标签、空白提示页和打印后界面状态恢复。
6. 大型试调采用后的正式计划只在单次只读事务内复用已经核验的来源，减少重复解码和校验；保留跨请求重新验证和既有 8 MiB 完整响应保护。

具体代码依据见同目录的 SQLite 并发、小数秒精度和启动器修复记录。

## 界面验收中的边界与脚本修正

- 完整 5000 项初始/当前对比超过 8 MiB 时明确拒绝；采用真实范围控件读回全部五段，没有放宽大小和超时阈值。
- 未填写实际设备和人员的报工被标为记录不完整；通过“补齐”操作填写后变为完成，原记录身份、数量和时间均保持。这是已验证的业务规则。
- 新校准候选未覆盖已有正式安排时，预检正确返回 `official_scope_not_covered`。加入已有 CAP-001 的完整范围后，15 项正式安排成功采用；5 条校准样本身份和模板来源逐项核对。
- 上次候选采用及维护操作的已确认回执须在页面点击“完成”或“确认结果”后，才继续新操作；没有通过删除浏览器存储规避保护。
- 初次正式打印脚本误选风险页，后续在真实正式甘特页完成原生打印并保留原失败报告；没有把失败报告改为通过。
- Chrome 109 的后台自动刷新响应体在页面跳转后可能无法由调试协议再次取回。最终系统管理验收在每个真实 UI 操作后立即读取并验证其 JSON 正文，继续监听全部请求的 HTTP/页面错误；实际下载文件另经 VMware 共享目录收集、哈希和内容核验。此前采集不完整报告保留。
- 日志导出中的一条恢复后退出备份拒绝记录，时间对应实际恢复后的正常停止保护；目标是避免在“须重启”阶段再次打开数据库。测试启动未使用 BAT，所以诊断包如实标出 launcher.log 缺失；正式 BAT 启动另外验收。
- 正式安装核验曾因 WMI 进程路径不完整而保守停止；辅助脚本增加按 PID 重新查询，对仍活跃但路径未知的进程继续拒绝。Windows 路径核验按大小写不敏感的规范化路径比较，不把合法的小写数据库路径误判为换库。这些调整均为外部验收脚本，不改变被测包。
