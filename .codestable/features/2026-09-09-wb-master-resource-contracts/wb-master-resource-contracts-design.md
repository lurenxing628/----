# 主数据真实维护

## 0. 术语与来源

沿用总体合同的 EntityRef、WriteContext、CommandInput 和 CommandResult。永久引用标识对象，写令牌绑定短期编辑上下文，回执证明一次已提交意图。现有 ResourceTeams、OperatorMachine 独立保留，不冒充新设备组或人员工种技能。

## 1. 决策与范围

- 完整范围仍是工种、设备、人员、供应商、物料、日历及其批量/文件操作、D06显式关系。按运营后端评估与能力清单接入，不删减原型入口。
- 首个子步骤是永久引用、删除后旧引用失效、原子命令回执及冲突保护；随后再开放正式读写入口。
- 复用领域服务与 TransactionManager。新命令在最外层 BEGIN IMMEDIATE 中校验最新事实、执行领域动作、落回执，不解析旧HTML判断成功。
- 引用独立存储，数据库触发器覆盖新旧代码的插入/更新/删除。删除后再建同编号得到新引用；SQL REPLACE 也按新实例处理。普通更新保持引用并提高内部修订号。
- 命令回执不可变，与普通SQLite业务变更同事务；意外提交错误标为结果待核实，按request_key读取回执。短期令牌不持久保存。
- 原有未展示字段、人员设备授权、跨夜日历及引用保护保留；新增语义必须真实存储。
- 明确不做：不改排产算法、不改历史生产事实、不提前下线旧页，不将一段基础代码标为全部主数据已完成。

## 2. 编排与挂载

现状：主数据服务使用嵌套事务，旧HTTP多为表单；公开token在进程内，不提供重启后稳定实体身份。

```text
v20预检/强制备份 -> 引用及回执元数据
  -> 真实资源查询 + 永久引用 + 短期写上下文
  -> 输入草稿 -> 服务器规范化 -> 幂等回执优先查询
  -> 最新事实检查 -> 领域动作与回执同事务 -> 重新读取真实实体
```

- 元数据SQL由 `core/infrastructure/workbench_metadata_schema.py` 定义，与 `schema.sql` 通过测试对齐，接入现有迁移链。普通GET不补引用或修复元数据。
- `WorkbenchEntityRefs` 保存kind、内部实体键、随机引用、存活与修订号；删除保留失效引用，防止旧引用指向后来重建的数据。关系变化用完整资源快照指纹补充检查。
- `WorkbenchCommandReceipts` 保存request_key、动作/上下文、规范化输入指纹、不可变结果和回执引用。
- 仓储负责SQL；命令服务负责事务和结果判定；路由负责参数及公开DTO；前端沿原型DOM/控件。取消草稿不写库。
- 新表和触发器只在测试副本迁移验证；生产启动仍依赖原有预检、强制备份和维护锁，不绕过保护。

## 3. 验收契约

- v19到v20保留所有业务表字段/行；空库和迁移库一致；失败不留下部分升级。
- 引用重启稳定；更新保持、删除重建不复用；旧领域写路径同样维护引用；查询不静默补缺。
- 同键同输入只提交一次、回执相同；同键异输入冲突；过时上下文不能覆盖新事实；并发重复提交无双记录。
- 业务成功但回执写失败时整体回滚；提交结果不确定不假报未提交；重连后可查询。
- 完整资源字段、显式关系和全部原型可达操作接入真实持久化，隐藏字段不丢失。
- 双尺寸双主题、逐项手输点击、复杂数据/错误场景；原型、原有暂存和生产数据边界保留。

## 4. 架构关系

扩展workbench-shell的持久身份及命令合同，完成后回写架构/需求及本项状态。计划查询及系统维护可以复用，但各自完成度单独登记。
