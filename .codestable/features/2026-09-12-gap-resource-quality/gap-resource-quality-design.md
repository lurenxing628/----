# 插空换型与稀缺资源选择

## 0. 术语

“插空换型增量”指插入前后最终换型次数之差，不等于实际换型小时。“稀缺需求”只指短窗口内其他未完成工序的显式合格机人组合，不是新资格规则。

## 1. 目标和授权

2026-09-12 用户在全面研究后授权实施全部改进。本项仅处理贪心解码器的插空换型与机人选择，不提交、不运行全仓门禁、不打开业务库。遵守 Python 3.8、Win7 和离线约束。

现有反例：相同完工时间的可行插槽，按机器末尾工种选机得到 4 次换型，按插槽两侧工种可得 2 次。两道各 1 小时工序，一道可选两组资源、另一道只能用一组；保留稀缺组可使相同批次顺序的总工期由 2 小时降到 1 小时。

## 2. 接口和运行流程

保持 `last_op_type_by_machine` 的尾部映射及已有 `last_end` 守卫。默认运行态使用兼容 dict 的 `MachineTypeState`，追加每台机器真实 `(start, end, op_id, op_type)` 有序记录；普通借入 dict 的历史路径不改。

`update_machine_last_state` 接收可选 `start_time`、`op_id`，保留所有真实插槽记录，即使插空没有推进机器末尾。`estimate_internal_slot` 找到最终合法槽后，用插入前后两条已知工种记录计算换型增量：新增两条相邻关系的次数减去被替换关系的次数。排序口径与最终换型统计一致。未知工种跳过；动态 descriptor 输入保持既有评分路径，不新增字段回调。

`initialize_resource_quality(state, sorted_ops, resource_pool)` 在种子加载后、dispatch 前建立本轮待排需求。需求只从可证明的原生字段和显式资格池得到；外协、未知资格和自定义转换不补造机人组合。短窗口优先每个 `(batch_id, piece_id)` 的下一道工序，最多 64 组。

自动选机人保持完工时间第一、实际换型增量第二；只在这两项真正并列时比较其他短窗待排头中“全部合格组合都会被当前机人组合占用”的数量，再沿用负荷、主操/技能与稳定 ID 顺序。只失去部分组合、仍有剩余替代组合的头计零，不冒充已被堵住。机器与人员的联合覆盖按集合并集算一次。固定资源不重选，现有资格、日历、停机、前置和窗口约束不放宽。完成、失败、阻塞从后续稀缺需求中移除。这是局部保守提示，不承诺任意数据的全局质量改善。

每个短窗对已存资格生成的全剥夺计数按机人组合复用；同一组合在不同当前工序查询时另行扣除当前头，完成或阻塞使窗口 revision 改变后清空计数。该计数只派生自本轮私有资格记录，不证明外部原始输入未变，可能改变选择时仍需下述完整认证。

只有可能改变当前选择的稀缺比较才重新核对原生资源池内容、短窗头和当前工序字段。若已存两组合提示同分，无论它们仍有效还是认证失败后同归零，都不会改变原排序，因此直接保持原 tie-break；这不表示输入已认证，也不提前更新停用诊断。随后只要提示出现分差，仍必须完整认证；同长度原地修改会明确停用，记录 `resource_pool_changed` 或 `operation_input_changed`，不使用旧资格推测。内部 `penalties` 方法本身仍保留每次完整认证及停用诊断的原合同。`revision` 仅标识本地完成/阻塞事件，不能独自证明外部输入不可变。普通尾部追加在实际时间尾工种与原末态一致时不进入反射和邻接计算。

实际插入需要的工序 ID/类型只对 exact `SimpleNamespace` 直接逐次读取原生实例字典，再按原 exact 正整数/字符串及 `strip()` 合同校验。内置类不可修改，实例特殊同名键不改变访问协议；不缓存可变字段。子类、普通类、descriptor 或自定义属性访问仍走原有 `inspect.getattr_static` 路径，不新增回调或转换。

SGS 增量评分的另一并行改动通过 `MachineTypeState.certificate(machine_id)` 获得不可变内容证据；自动派工候选不使用缺少稀缺需求失效条件的旧分数。

## 3. 验收边界

- 真实 GreedyScheduler 重现并改善换型 4→2，种子时间/资源完全不动；末尾状态守卫保持。
- 同批序的两道任务重现并改善总工期 2→1 小时；固定资源、人员独占与资格仍成立。
- 普通 dict/动态字段保持原回调和错误顺序；稀缺未知资格不猜测。
- frozen seed、piece 前置与单件工作量不改变；失败需求不继续保留资源。
- 指标不宣称真实换型小时减少：仍用现有固定 setup_hours；本项只改善换型次数代理。
- 只报告针对性验证；并行脏工作区不声称 clean-worktree proof。

## 4. 架构关系和文档范围

新增类型与纯需求计算留在 `core.algorithm_runtime`，不反向依赖 algorithms/services。scheduler 在种子加载后初始化，run_state 负责生命周期，internal_slot/auto_assign 消费；保留现有公开排产接口与持久化结构。与并行 SGS 所有权改动共同使用同一份运行态，派工状态的分件浅复制仍共享资源质量证据。

本子项产物是当前目录的设计、检查清单与验收记录；共享架构总入口及整轮综合验证由主代理统一归并，避免并行覆盖。关联 `scheduler-global-optimizer` 的 `optimizer-quality-efficiency-20260912` 条目及本轮清单 B，不新建 UI、配置或数据库表。
