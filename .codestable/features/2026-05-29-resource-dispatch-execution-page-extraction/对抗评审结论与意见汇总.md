# 资源排班"执行类功能独立"——对抗评审结论与意见汇总

> 文档性质：决策评审记录（非正式 design）。记录从"多角度论证 → 出方案 → 多角度对抗 → 修正结论"的完整过程与全部意见。
> 关联文档：同目录 `resource-dispatch-execution-page-extraction-design.md`（status=draft，已按第 8 节重定向为 refactor）、`-checklist.yaml`。
> 日期：2026-05-29

---

## 0. 一句话结论（先看这个）

**"把现场反馈从资源排班模块拆出来"这个方向是对的，但第一版的具体方案被对抗评审打出三道硬伤。正确做法是把它劈成两件独立的事：**

- **✅ 现在就做：拆代码**（把 1398 行单文件 JS 按子域拆成多文件，页面/URL/导航全不变）——收益主要来自开发者减负；"80%"这类比例只能作为主观估算，不能当成可验证事实。
- **⏸️ 暂缓再做：拆页面**（新建独立"现场记录"页）——用户价值还没被证据支撑，且成本被低估，待验证后再立项。
- **❌ 不做：甘特图改跳转**——与本主题无关，移出。

**核心教训：不要把"开发者减负"（技术债）和"用户体验优化"（产品改动）捆在一个 feature 里搭售。**

## 1. 背景与现状

### 1.1 诉求来源

用户希望把"现场反馈以及其他一些功能"从资源排班模块独立出去，理由是这个模块"对人的心智负担太重"。

### 1.2 资源排班页现状（已验证）

`scheduler.resource_dispatch_page`（`/scheduler/resource-dispatch`）是一个超级页面，前端 `static/js/resource_dispatch.js` 已达 **1398 行 / 62KB**，模板 25KB，一个页面承载 6 大功能：

| # | 功能块 | 性质 |
|---|---|---|
| 1 | 排班查询（人员/设备/班组 × 周/月/自定义） | 看计划（只读） |
| 2 | 汇总卡片（任务数/工时/超期/跨班组/外协/跨天） | 看计划（只读） |
| 3 | 现场记录（开工/暂停/完工/异常上报） | 录实际（写入） |
| 4 | 实际情况 Excel 导入（模板/预览/确认） | 录实际（写入） |
| 5 | 日历矩阵（跨天任务按自然日拆分） | 看计划（只读） |
| 6 | 甘特图 + 班组人员/设备/跨班组任务表 | 看计划（只读） |

### 1.3 关键代码事实（已下代码层验证）

- **现场记录写入事实相对独立**：`OperationExecutionEvents` 表按 `op_id` 聚合，当前应用层写入链路只新增记录（本轮未发现 update/delete 入口）；schema 硬约束 `source_table='schedule'`、`effective_plan_role='adopted'`、`scenario_id IS NULL`，在数据层就锁死"只认正式采用方案"。但任务卡读取、可写判断、写入入口的任务定位、排班页现场状态列仍依赖资源排班查询链路，不能说后端完全解耦。
- **后端边界已基本分好**：`scheduler_resource_dispatch_execution_routes.py`、`operation_execution_feedback_service.py`、`resource_dispatch_execution_service.py` 已是独立文件。主要债务在**前端单文件 JS + 同一 HTML 模板 + 同一 URL 入口**。
- **roadmap 早有意图，但不是拆页证据**：`.codestable/roadmap/aps-three-gap-directions` 支持"在资源派工上下文里"做车间反馈入口；其中"异常反馈独立拆分"说的是功能条目粒度，不等于立刻拆成独立主页面。
- **已有需求文档**：`.codestable/requirements/shop-floor-execution-feedback.md`（现场记录的愿景需求）。

## 2. 第一轮：多角度论证（6 路 subagent）

派出 6 个角度独立思考"该不该拆、怎么拆"，主代理汇总去重。

| 角度 | 核心结论 |
|---|---|
| 领域边界（DDD） | 功能 3/4（录实际）属于独立有界上下文（执行域），应独立；功能 1/2/5/6（看计划）是同一上下文，保留。违反 CQRS 读写分离。 |
| 代码耦合可行性 | 后端服务层边界已正确，拆分友好；最危险耦合点是 `get_dispatch_payload` 内的 `_enrich_rows_with_execution_state` 把现场状态注入排班行。 |
| 用户角色与心智 | 看计划面向计划员/班组长/管理者；录实际面向车间录入员。读写混在一页是心智负担来源。 |
| 演进/缺陷热点 | 第一轮观点认为现场记录近期改动和返修较密集，是高频变更区域；具体故障数量未在最终复核中稳定复现，不再当作结论事实。 |
| 迁移落地方案 | 给出"先抽公共层→搬现场记录→搬导入→改导航"的分阶段方案。 |
| **对抗视角（反方）** | **真正负担是 1398 行单文件，不是"功能放一页"；现场记录与排班是同一工作流，硬拆成两页会切断用户动作、制造新债务。** |

**第一轮仲裁**：五路支持拆、一路反对。下代码层验证后得出"双方都对，在说不同层"：
- **代码要拆**（治开发者负担）；
- **页面别粗暴一刀两断**（治用户负担需谨慎）。

由此形成第一版方案：**"先拆代码、再拆入口、不动 API"三步走**，并写成正式 design 文档（draft）。

### 3.2 三路独立攻击收敛到同一结论

产品、成本、规范三个攻击手用**完全不同的证据**得出**同一句话**：

> **拆 JS 文件（开发者减负）对；拆成独立页面（用户减负）是把未经验证的用户问题，捆绑在低风险技术改造上搭售。应解绑。**

- **产品证据**：需求原文更支持"在资源派工上下文里填写"，暂不支持立即拆成独立主页面；"纯录入角色"缺少一手证据。
- **成本证据**：只做拆 JS 的收益更确定；拆页会争取待验证的用户价值。"1.5 天 / 2-3.5 天"、"80% / 20%"都只能作为主观估算。
- **规范证据**：跨文件共享命名空间和 boot 启动顺序会改变调用组织方式，按 CodeStable 应走 `cs-refactor`；且一个 feature 混了两个目的，范围不纯。旧草案写作 `window.RD`，新 refactor 统一改用更明确的 `window.__APS_RESOURCE_DISPATCH__`。

### 3.3 对抗中被挡回的部分（夸大处）

- **"拆页后现场状态不实时刷新=退步"**：部分成立但可接受。`_enrich_rows_with_execution_state` 每次 `loadData` 都实时读库，只是"录完跳回需手动刷新"，加一句提示即可，非致命。
- **"回滚承诺虚浮"**：略夸张。git revert 单提交即可回滚。但原文"第1步可删文件回滚"表述确实错（第1步是改文件非新增），应改为"靠 git revert 回滚"。

## 4. 最终意见（分两步走，禁止捆绑）

### ✅ 4.1 现在做 —— Refactor 1：前端按子域拆文件（不拆页面）

- **做什么**：把 `resource_dispatch.js` 拆成 `shared / core / execution / boot` 四段，但**排班页同时引入这些文件，页面长相、行为、URL、导航一律不变**。
- **诚实定性**：这**不是**"零风险微重构"，而是一次**中等规模、需走 `cs-refactor` 流程**的重构（因需要显式定义跨文件共享契约和启动顺序）。"约 1-2 天"只是主观估算，有非零出错概率，需如实交代。
- **配套**：同步更新 §3.1-C 列出的 6 个硬编码读文件名的测试。
- **收益**：开发者以后改现场记录只看更清楚的执行子域文件，卸掉主要维护负担；几乎不碰用户、不碰路由、不碰打包、不碰导航。
- **回滚**：靠 git revert 单提交（不是"删文件"）。

### ⏸️ 4.2 暂缓 —— 独立"现场记录"页 `/scheduler/resource-execution`

- **先不做**。理由：用户价值缺证据（需求文档支持"在资源派工上下文里填写"），且引入 version 矛盾、Win7 打包、手册、导航四类成本。
- **立项前置条件**：先确认车间用户真有"被版本/方案概念干扰"的痛点（哪怕访谈一两个真实用户）。
- **真做时必须先填的 5 个坑**：
  1. 跳转链接**绝不透传 version**（只透传日期 + 人/设备/班组）；
  2. 页面**只读显示"当前对应 v几"**，砍选择器≠让用户不知道版本；
  3. **不进主导航**（只能从排班页跳入，避免空筛选进入更迷惑）；
  4. 补 `web/routes/domains/scheduler/scheduler_route_registrar.py` 的 `_ROUTE_MODULES` 和 `build_win7_onedir.bat` 的 `--hidden-import`；
  5. 拆系统手册 + 改 `regression_page_manual_registry.py` 数量断言 + 改 `page_manuals_scheduler_outputs.py:210` 的"四种视图"文案。

### ❌ 4.3 删除 —— 甘特图改跳转

与本主题无关，彻底移出，若需要另起 feature。

## 6. 方法论备注（这次评审的可复用经验）

- **对抗最值钱的产出不是"反方说不该做"，而是揪出方案内部自相矛盾**（如"透传 version" vs "砍选择器"——分两节写时都对，合起来是 bug）。
- **跨视角收敛 > 单视角强观点**：产品/成本/规范三路用不同证据指向同一结论，可信度远高于任何单一 agent。
- **警惕"捆绑销售"**：把低风险高确定性的事（拆 JS）和高风险待验证的事（拆页）塞进一个 feature，会用前者的安全性掩盖后者的真实成本。拆开评估，分别决策。

## 7. 第三轮复核：5 路 Codex Subagent + Claude Code（2026-05-29 追加）

> 本轮目标：不是重做 design，而是对本文件已有结论再做一次独立对抗。
> 本轮实际参与：5 个 Codex Subagent（产品需求、前端耦合、后端版本/写入、测试/打包/手册、CodeStable 流程）+ 1 个 Claude Code CLI 外部评审。
> 总结论：**支持 §4 的大方向，但要求把若干表述改得更诚实、更可证明。尤其是：只拆 JS 也不是"测试零修改"的无痛重构，必须单独走 `cs-refactor` 并把测试适配写进范围。**

### 7.1 六路复核意见汇总

| 角度 | 结论 | 主要意见 |
|---|---|---|
| 产品需求 | 支持现结论 | 需求和 roadmap 更支持"从资源派工/资源排班上下文进入现场记录"，不能直接证明应立即拆成主导航独立页。但"拆页违背需求"应改软：目前只是**缺少立即拆页的证据**，不是证明以后永远不能拆。 |
| 前端耦合 | 支持现结论 | `resource_dispatch.js` 是单 IIFE，`state`、`currentQueryString()`、初始化顺序都跨看计划/录实际共享；拆文件确实能减轻开发者负担，但不是零风险，必须明确 `shared/core/execution/boot` 的加载与启动顺序，并使用明确命名空间 `window.__APS_RESOURCE_DISPATCH__`。 |
| 后端版本/写入 | 支持现结论 | 历史 `version` 透传到写入页会触发 `can_write_feedback=False`，按钮或导入会不可用；但"导入静默失败"不严谨，应写成"后端明确拒绝，现有前端会显示错误提示"。现场记录写入事实相对独立，但任务卡读取和排班页状态列仍依赖资源排班链路。 |
| 测试/打包/手册 | 支持现结论，但修正数字 | 硬编码读取 `resource_dispatch.js` 的风险属实，Win7 `hidden-import` 风险属实，页面手册/导航成本属实；但"约 113 个测试函数"无法复现，点名 6 个文件里约 49 个 `test_`。更宽口径统计会受文件名、引用链和测试筛选方式影响，不能当作结论事实。`404` 也应写成可能表现，未打 Win7 实包前不能断言。 |
| CodeStable 流程 | 支持现结论 | 当前 design/checklist 仍按"拆独立页面"推进，已经和 §4 冲突。不要按当前 checklist 开工；只拆 JS 应另走 `cs-refactor`，拆页待用户价值验证后另起 feature 并重写 design/checklist。 |
| Claude Code 外部评审 | 部分支持 | 支持"先拆 JS、不拆页"方向；新增指出本文件 §4.1 自身也有矛盾：一边说"页面行为不变/既有测试未修改即通过"，一边又要求更新硬编码读 `resource_dispatch.js` 的测试。拆 JS 的退出信号必须改成"用户行为不变，但测试需要适配拆分后的文件结构"。 |

### 7.2 本轮要求修正的口径

1. **"拆页违背原始需求"改为更准的说法**：
   需求原文更支持"在资源派工上下文内完成现场记录"，暂不支持立即拆成独立主页面；但这不是证明未来永远不能拆页。

2. **"纯录入角色是臆想"改为"缺少一手证据"**：
   现有材料没有证明"车间录入员"已经是一个稳定、独立、需要直达入口的真实用户群；后续若要拆页，需要先访谈或观察真实填写人。

3. **"导入静默失败"改为"会被后端拒绝并提示错误"**：
   历史版本不可写这点成立，但现有链路不是完全没反应；更准确的风险是"用户看起来进了填写页，却因为版本不可写而不能完成录入/导入"。

4. **"现场记录是独立子域"要拆成读写两句话**：
   写入的现场事实通过 `OperationExecutionEvents` 独立保存，并锁定 `schedule / adopted / scenario_id=None`；但任务卡读取、排班页现场状态列仍与资源排班查询链路相连，不能说后端完全解耦。

5. **"相关测试函数约 113 个"标为证据不足**：
   本轮复核无法复现这个数字。更稳的写法是：点名 6 个文件中有约 49 个 `test_`；其他宽口径统计受筛选方式影响太大，不继续写成事实。真正关键不是总数，而是多个测试把 `resource_dispatch.js` 当成单文件事实源。

6. **"打包后新页面 404"改为可能表现**：
   `build_win7_onedir.bat` 手写 `--hidden-import` 的风险成立；但未做 Win7 实包验证前，只能说"可能导致冻结包中新路由未注册或启动导入失败，404 是可能表现之一"。

7. **"80% / 20% 收益"、"1.5 天 / 2-3.5 天"降级为主观估算**：
   这些数字表达方向有用，但仓库里没有可验证标定，不能写成事实。

8. **"只拆 JS"也不能承诺既有测试未修改即通过**：
   这点是本轮最重要的新增发现。`tests/operation_execution_feedback_test_support.py` 把 `RESOURCE_DISPATCH_JS` 写死为 `static/js/resource_dispatch.js`，多个测试读取这个单文件后断言文案、DOM 属性或行为契约。只要把执行逻辑搬出该物理文件，测试就需要改为读取多文件或改常量。正确退出信号应是：**用户可见行为不变，自动化测试随文件拆分做等价适配后通过**。

### 7.3 更新后的处置建议

- **不要按当前 `resource-dispatch-execution-page-extraction-checklist.yaml` 开工**：它仍包含新增 `/scheduler/resource-execution`、主导航入口、页面手册、双向跳转、摘除排班页执行 UI 等内容，已经和 §4 的最终意见冲突。
- **如果只做当前最稳的一步，应新建 `cs-refactor` 任务**：范围限定为 `resource_dispatch.js` 按子域拆分，排班页 URL、导航、页面形态和用户操作不变。
- **新的 refactor spec 必须写清楚测试适配**：不是"未修改测试通过"，而是"用户行为不变，但测试需要从单文件读取改为多文件读取/共享测试支持函数"。
- **拆页暂缓，不进入主导航**：未来如果重启，先问一个最小验证问题：真实填写现场记录的人，是"先在资源排班页找到任务再顺手填写"，还是"希望直接进入一个只看待填写任务的现场记录页"？
- **甘特图改跳转仍移出本主题**：若要做，另立 feature，不与拆 JS 或拆页混在一起。
