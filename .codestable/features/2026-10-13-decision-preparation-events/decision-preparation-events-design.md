# 第4阶段：准备需求与切换事件

## 0. 术语

- `OperationEffort` 是该次调度使用的工序标准需求分解。`required_standard_hours` 对应真正交给排槽的标准需求；准备、加工与资源占用各有明确单位和来源。
- `runtime_requirement_v1` 表示运行时共同需求事实。`archived_operation_standard` 表示旧档已有的工序标准；旧档缺少实际执行／准备分解时保留具体缺项。
- `setup_state` 为 `pending / retained_in_execution / already_completed / external / unknown`。待新排、执行保留、完成种子、外协和事实缺失分别表达；准备是否已经发生依据保存执行事实。
- 工种切换是同设备完整序列中相邻内制非零时工序的工种变化事件。它与每道工序计取的准备标准工时分别呈现。
- 选批目标量、执行剩余量、分件自身量和共同工序量沿现行需求规则。外协以周期单列；日历效率换算后的占用由共同资源指标承担。

## 1. 决策与约束

第3阶段已通过主对话独立验收，无新增返修。主对话按审定主方案4.4及相关4.2／8派发本阶段完整实施、验证和文档闭环；完成后交回独立验收，第5—8阶段等待。沿用用户授权，普通实现选择连续处理。

共同需求构造是准备／加工事实的唯一生产者，实际排槽、保存证据、候选汇总、差值、明细和导出消费同一分解。每个永久工序只计一次；分件自身工序分别计取。执行、冻结和已完成种子保留实际安排及需求来源；历史事实缺分解时保持缺项。

产品沿默认单机档位，兼容Win7 x64、Python3.8和离线Chrome109资产。使用既有候选／试调JSON和完成事务保存新增证据，按实际存储需要决定字段落点。原标准、评分、选择规则和采用职责保留准确来源；本阶段处理成本事实和展示，顺序相关换型时间求解沿独立算法需求。

## 2. 名词与编排

### 2.1 现状与变化

现状：`core/algorithm_runtime/internal_slot.py:69` 的 `validate_internal_hours` 计算setup加unit乘实际batch量，并供正式排槽使用；`schedule_input_builder.py` 把可重排工序变成算法输入。工作台 `run/input.py` 在真实执行保护、外协周期、冻结及种子处理后得到 `algo_ops_to_schedule`。分件适配改变自身工序的实际目标量。旧 `decision_impact._effort` 只展示保存标准及AJ目标，未保存该次运行的实际需求分解。旧 `_count_changeovers` 排序设备安排后计相邻工种变化，候选统计直接调用它，事件明细尚缺。

变化：把同一实际需求分解放在现有需求／运行时叶子，形成一次运行的需求账；保存时绑定永久工序引用，候选依据自己实际安排和未排集合进行归属。新旧归档通过共同投影消费保存事实；标准旧事实与缺失runtime分解分别表达。切换共同生成器同时提供事件和计数，原评价及同义调用者迁入此入口。

逻辑合同示例：新排内制工序setup=2h、unit=0.5h、实际目标量=6时，准备2h、加工3h、required=5h，和排槽标准需求相等。分件自身目标量1按同一函数计取；共同工序仍按其实际共同目标只计一次。保留的旧执行种子缺准备分解时，显示其真实状态／目标／剩余量和已知标准，同时runtime小时缺项。

```text
OperationEffort {
  operation_ref, source, quantity_basis, target_quantity, remaining_quantity,
  execution_target_quantity, execution_quantity_basis,
  setup_standard_hours, processing_standard_hours, required_standard_hours,
  setup_state, effort_basis: runtime_requirement_v1,
  requirement_role, external_cycle_days?, data_gaps
}

ChangeoverEvent {
  machine_ref, previous_operation_ref, next_operation_ref,
  previous_type, next_type, next_start, conflict, completeness, drill
}
```

已保存种子需求的 `target_quantity / quantity_basis` 绑定原分解目标，本次AJ执行目标另存 `execution_target_quantity / execution_quantity_basis`，余量仍来自本次真实执行。已保存10件／7h、本次目标改20件时，原需求仍10件／7h，同时明确执行目标20件；缺旧runtime原目标时为null／unknown，已知执行目标仍可显示。

正式基准before侧也使用本次受理AJ展示执行目标和剩余量，原需求目标及标准小时来自该工序最后采用的原来源。原来源标准缺项时保持缺项；本次归档标准在所选侧独立可读。

事件例：设备完整序列A工种→B工种，B在查看窗起点开始，窗口内仍计A→B并保留A作前驱；B→B计0，设备首道计0。工种以保存身份判断，同ID不同工序名称仍是同工种，不同ID同名仍是不同工种。相交安排保留冲突和统计覆盖。

### 2.2 主流程

```text
实际输入＋保存执行／分件规则
  → 共同OperationEffort＋实际排槽／保留种子
  → 完成事务保存需求账＋候选实际安排归属
  → 归档事实适配＋同设备完整序列切换
  → 同scope候选／基准汇总、明细、甘特和CSV／XLSX
```

现状的标准公式、试调原需求和切换计数分散在各入口。变化后所有实际新排标准分解使用共同生成者，种子或旧档来源缺项明确；切换先对完整序列建立关系，再按后一道开始落入左闭右开窗口。查询不从总耗时猜准备，不读取当前工艺回填旧归档。

准备汇总区分待执行、实际新排、普通未排、合法暂缓、原样保留和完成／执行种子；加工和剩余需求保留可追到工序的范围。同需求完整候选准备总量相同直接显示相同；减少来自漏排／暂缓时列具体工序和剩余需求，差值采用准确中性说明。

### 2.3 挂载点

- 实际排槽与工序需求构造：提供运行时需求账，保留原排程行为；共享事实属于调度职责。
- 运行及必要试调完成保存：新证据与候选／来源在原事务一起保存，正式归档按原来源读取。
- decision总览与准备／切换明细查询、现行导出路由：共同scope、筛选分页、快照及覆盖。
- 方案对比准备／切换分区与前端构建登记：紧凑表格展示、设备／工序双方甘特定位和完整返回。
- 原评价／候选／试调同义需求或切换读取：迁入共同入口，保留实际公共语义。

移除准备页查询／组件可卸除新增明细展示；共同需求和切换生成者被调度与原评价消费，属于系统共享规则，撤回单页时继续保留。

### 2.4 推进策略

1. 需求与事件共同源头：实际排槽量、种子角色、分件／外协及排序规则明确，关键回归证明原行为和新事实。
2. 归档及比较：保存新证据，适配旧档，完成准备／加工／切换共同汇总、差值、明细和导出。
3. 界面及既有消费者：两侧汇总、紧凑明细、筛选分页、甘特定位返回和旧同义入口统一。
4. 实际验证与文档：复用有效真实场景，补必要新运行，浏览器／原始导出／日常及离线构建通过，完成交接。

### 2.5 结构健康度

本阶段的必要重构是收敛标准需求与切换规则，清理被迁移的重复公式和计数。运行时叶子保持中立，不反向依赖工作台或Web。事务、身份和归档已有机制复用。职责拆分按需求账、事件、查询和导出组织；准备／切换概念分别表达，避免把资源占用小时当作标准需求或引入另一套优化器。

## 3. 验收契约

- C01：新排内制准备＋加工＝实际交给排槽的required；零工时、真实目标／剩余量与缺项状态正确。
- C02：执行中、已完成、冻结／保留种子保留原安排和执行规则，按保存事实给需求来源／准备状态；缺历史分解不猜测。
- C03：分件自身按实际量分别计取，共同工序只计一次；外协周期、合并组与内制标准工时分别表达。
- C04：新运行及必要试调证据按永久身份保存并由正式来源读取；旧档已知标准保持，缺runtime分解可定位，当前工艺修改不影响归档。
- C05：完整同需求候选准备相同；部分、普通漏排、合法暂缓的准备／加工／剩余需求逐项可追溯，差值与覆盖范围一致。
- C06：设备首道0、连续同工种0、相邻变工种1；事件和计数一致，点事件排除，重叠完整性明确，窗口前驱保留且按next_start裁剪。
- C07：候选／基准准备和切换汇总、逐工序及事件表、稳定筛选分页、甘特两侧定位与完整返回、CSV／XLSX原始值和scope一致。
- C08：相关回归、适用日常、Chrome109离线构建、真实隔离案例、浏览器交互、原始导出与文档同步通过，原7运行／34候选／正式v1及生成参数保留。
