## 0. 共同概念与批准依据

本阶段落实[主方案](../../roadmap/scheduling-decision-workbench/scheduling-decision-workbench-roadmap.md#72-历史趋势)第7.2节完整历史能力。第6阶段已通过主对话独立验收，第7阶段沿原批准范围恢复。

历史条目是一次运行或一次正式采用；结果来源是该条目保存的候选、试调场景或旧正式摘要。事件身份与结果身份分别保存。同一次运行多次采用在正式采用线保留多个事件，在运行线仍计一次。业务走势表示当时实际业务规模与结果；同条件改善须有充分归档证据。

## 1. 决策与约束

在共同工作台服务中增加只读历史投影，统一四来源。既有运行目录继续承担运行查找，历史走势沿同一个“排产记录”入口进入。指标、资源日历、工时、切换和交付复用第0—6阶段共同投影；保存指标沿其真实原口径显示。

生产条件逐实体逐字段比较，算法参数独立展示。时间戳、归档编号和版本编号是出处；批次、工序和资源的真实永久身份参与条件比较。缺表、缺列和原来源无法恢复时返回未知；明确空集合、0、False和有业务意义的null保留其意义。

资源缺省窗口为每条来源实际排产起点开始的固定7天，展示每条实际起止与容量分母；用户也可指定所有来源相同的绝对窗口。时间线筛选日期与资源窗口分别表达。

采用项目默认单机离线复杂度档位，保持Python3.8与Win7 x64。明确不做：历史重排、现场自动采用、用今日生产表补齐旧条件、第二次保存归档、密码学摘要、另一套指标计算或新测试治理框架。本阶段保留原数据库和永久身份。

## 2. 现状与变化

### 2.1 名词层

现状：运行目录只返回状态、来源和范围摘要；候选采用历史按候选读取，试调采用历史按场景读取；旧正式记录保存原摘要。真实入口为`core/services/workbench/run/history.py`、`core/services/workbench/run/candidate_history.py`、`core/services/workbench/trial/adoption_history.py`和`data/repositories/schedule_history_repo.py`。

变化：增加统一历史条目、历史筛选和历史对照。条目键由已有身份组成：`run:<run_ref>`、`adoption:<receipt_ref>`、`legacy:<ScheduleHistory.id>`。实际永久引用保留在`identity`中；采用本地时间、回执UTC提交时间和旧记录时间分别保留来源，显示与筛选使用明确的工厂本地发生时间。未保存或无效时间返回缺项。

`GET /api/workbench/v1/scheduling/decision-history`沿现有`ok/schema_version/data/meta/warnings`协议。请求包含：

| 参数 | 含义 |
| --- | --- |
| `timeline=run\|official` | 运行或正式采用时间线 |
| `date_from/date_to` | 时间线发生日期，成对、含两端日期 |
| `metric_keys` | 指标键列表，沿共同指标目录 |
| `comparison=observed\|same_conditions` | 业务走势或同条件对照 |
| `reference_run_ref` | 同条件对照的明确基准运行 |
| `selected_entry_ref` | 选中条目，跨页保留详情 |
| `range_start/range_end` | 成对共同绝对资源窗口，含起点、不含终点 |
| `resource_window_days` | 缺省固定窗口长度，默认7天 |
| `state/sort/order/page/size` | 状态、时间排序和20/50分页 |
| `condition_page/condition_size` | 选中条目的生产条件明细分页 |
| `snapshot_ref` | 同一次分页、读取和导出绑定的快照 |

响应包含`history_version/filters/entries/page/totals/metric_definitions/selection/comparison/trend/resource_window`。`selection.entry/reference`返回实际选中条目和基准；指标值沿共同`value/state/known_subtotal/known_count/unknown_count/total_count/scope/metric_version/reason`契约。`scope.batch_quantity`沿真实所选批次的`Batches.quantity`按件计量，返回数量、已知小计、真实覆盖成员及保存出处；范围总量与其缺项在页面和文件中保持一致。目录`label`为运行完整目录序号或正式版本名称，发生时间独立保存和展示，筛选与分页保留同一标签。趋势点与表格同源，图展示当前页；完整导出读取筛选全集。

生产条件按范围与业务策略、批次、工艺与需求、物料与外协、日历与停机、资源资格、执行与正式基准、冻结8类返回。每行含`category/entity/field/state/before/after`；两侧含值是否保存、实际值和`source.kind/ref/path`。整体状态为`equal/different/unknown`。算法配置独立返回同样可读的字段行。

示例：两条归档的应排数量均为48，但工序成员不同，生产条件为`different`并列出成员变化；生产条件相同而图权重变化，条件为`equal`、算法配置为`different`。两侧目标、指标版本、单位、统计范围与覆盖集合一致且指标充分已知时，返回具体同条件改善；缺任何必要事实时，返回对应缺项和实际观测值。

历史导出使用`GET /api/workbench/v1/scheduling/decision-history/export`，参数沿历史筛选，另含`format=csv\|xlsx`、`section=entries\|conditions\|configurations\|all`。CSV选择一个分区；XLSX的all保留历史条目、条件、算法配置、指标口径、范围和缺项。页码只影响屏幕，文件包含筛选全集；生产条件与算法配置文件对应当前选中条目和明确基准。

文件导出格式为2，独立于查询的`decision-history-v1`。CSV/XLSX条目分区共用长表：`记录类型`为指标值、范围引用或指标覆盖引用；历史标量和指标原值保持原列，引用按历史条目编号、指标键和引用字段关联，每个成员一行，保留1起顺序、对象类型和集合数量。原值`null`保留数量和成员空白的占位行，明确空数组保留`array`、数量0的占位行，原因继续取原指标/范围/窗口说明。范围成员每条历史输出一次，指标覆盖仅按所选指标输出；不把任意多个永久编号合成一个单元格。

共同列含`历史格式版本/导出格式版本/读取编号/读取时间`，响应头`X-Workbench-Export-Version=2`。`X-Workbench-Row-Count`计主分区实际数据行，包含指标值、引用成员和空/null占位；`all`再加生产条件和算法配置，指标口径、比较范围、数据缺项三张说明表继续不计。消费者按记录类型取指标值或重组引用集合；旧文件的JSON数组单元格已迁移为同源关系行。

### 2.2 编排层

```mermaid
flowchart LR
  A[运行 / 两类采用回执 / 旧正式摘要] --> B[只读来源目录]
  B --> C[保存来源与共同指标投影]
  C --> D[归档生产条件和算法参数对照]
  D --> E[筛选排序与快照]
  E --> F[历史图 / 数值表 / 来源详情]
  E --> G[筛选全集CSV与XLSX]
```

现状：各来源已有不可变归档和永久引用，读取结果页保持只读；已提交采用回执与旧正式摘要分开保存。

变化：目录统一事件身份，按所选时间线读取；请求内恢复来源一次，共享指标与条件投影；随后排序、分页与选择详情。运行以保存推荐作为默认结果，未保存推荐时明确结果缺项；正式采用以实际采用来源为准。旧正式记录若已有现代采用回执覆盖，目录只保留真实采用事件，原历史行仍保留可钻取出处。

同条件结论先检查生产条件，再检查目标和逐指标口径、覆盖集合与共同资源窗口；算法参数是实验维度。业务走势保留不同规模的已知值，并标明范围、窗口或容量分母变化；图线遇到未知或不可统一单位、版本和统计范围时断开。

首次独立读取可获取任意合法页面的新快照；界面连续分页与下载沿同一快照。范围或来源变化返回现有`409 snapshot_stale`并要求刷新；无效范围422、引用不存在404、损坏归档沿既有明确错误。新快照不会触发排产或写入。

来源钻取沿统一`return_decision_history_context`保存时间线、阅读模式、基准、指标、日期、资源窗口、状态、排序、分页、选中条目及快照。运行、候选、正式计划与甘特返回都消费相同上下文；快照过期时可刷新当前条件。

### 2.3 挂载点

- 新历史读取与导出路由登记。
- 现“排产记录”工作区中的历史走势入口。
- 工作台组合构建和启动组件登记。
- 来源页面中的历史返回上下文消费。

### 2.4 推进策略

先统一四源目录与公共契约，再接共同指标和条件对照；界面、导出共同消费服务。随后做针对性API、真实原件和受影响浏览器返回链验证，完成说明并交由主对话独立验收。第8阶段依赖第7阶段独立验收通过与派发。

### 2.5 结构健康度

各来源读取已按领域分离，保留现有接口。历史目录、指标、条件、查询和导出按各自职责置于历史模块；在既有决策大文件中仅增加路由/返回挂载。无需先做无关搬移。界面以共同查询上下文作为单一状态来源，减少每个来源页面重复恢复筛选。

## 3. 验收契约

- 四类实际保存来源进入正确时间线；同run两次采用在运行线计一次、采用线保留两个回执，来源身份与真实时间可钻取。
- 已归档生产内容相同、算法配置不同，生产条件相同且配置变化可见；改变实际成员或任一有效生产字段时列出变化。旧缺表/列/来源为未知，0与空集合保留。
- 相同条件、目标、指标版本及覆盖范围满足时显示具体同条件改善；条件变化或必要证据缺失时列出对应原因和实际观测值。
- 固定长度与共同绝对资源窗均展示真实容量、占用与分母；容量或范围变化有明确标记。
- 同一筛选集20/50分页稳定无重漏，空时间排末；快照改变显式拒绝连续读取；文件覆盖筛选全集，批次总量、覆盖、数值、空值、单位、身份与页面同源且表头唯一。零匹配可清除日期／状态筛选并保留时间线、基准、指标与资源窗；越页可沿原快照恢复第1页；当前页签可目视和键盘辨认。
- 历史→候选、历史→正式计划及甘特返回后恢复完整上下文；键盘能选择图点和表行，正常文字自然换行，图与表值相等。
- 失败、未完成和旧摘要保持保存状态与缺项；读取和导出不生成新运行、试调或采用，原数据和配置保持原样。

反向核对：不将重复采用计作运行次数，不以相同计数代替成员相同，不从当日表补旧条件，不把未知显示为零，不新增摘要与第二事实源。
