# 可分阶段投产的生产资料

## 0. 术语与批准依据

用户确认三项能力全部需要，并明确“100件只到够40件的料”采用先预览、确认拆分数量后再排产；执行排产页必须提供本次可选选项。上述决定来自当前会话，不重复审批。
工种说明加工能力，工序归属说明本次自制或外协，两者分离。工作时段是一天内实际工作的多个起止区间，中间空档不计产能。分批开工是批次数量拆分，不复用现有 piece_id（它表示单件工艺分支）。

## 1. 决策与约束

- 沿用 Win7 x64、Python3.8、离线单机与现有写入回执、完整快照校验。
- 旧数据保持原有运行含义；旧资料没有新字段时仍按整批齐套、单工种、单连续时段解释。
- 本次排产默认严格齐套；可选按工序分阶段放行。需要拆分件数时必须先预览需求、到料分配、两批数量并确认，不能在预检或计算时偷偷写库拆批。
- 物料需求可指定使用工序，并登记分次到料数量与日期。旧到料数量作为未分次登记的已有量保留；有日期的后续到料只在相应时间起可用。没有数量或时间的缺口明确阻止受影响工序及后续工序，不阻止已具备条件的前序工序。
- 本轮拆分按加工数量等比例分配材料需求；页面明确提示整批固定耗用需要先人工核对，不自动分配固定耗用。预览逐项列出分配，确认后不得双计同一到料。已有正式计划、执行或外协登记的批次沿用保护，不强拆历史。
- 同一工种可登记自制、外协或两者均可；实际工序始终明确选一种归属。设备可登记多个能做的自制工种；人员技能与设备操作授权仍需同时满足。
- 全局、个人日历和轮换班次均支持多时段。用户随后明确默认工作日为08:30–11:50、13:30–17:30，共7小时20分钟；未配置日期与新增表单采用这一默认，明确保存的旧班表不改。工作日历页提供修改默认工作时间，保存到本机数据库，影响未单独设置的日期；所有新界面复用现有工作台样式及组件，不另写样式或使用未适配的系统默认控件。起止用独立输入框；跨到次日明确显示/选择日期归属；重叠、倒序及超出一天跨度的配置拒绝。
- 文件保持业务原有粒度：设备一行、日历每人每天一行，可增添能力或时段列；不要求用户编写JSON或编程表达式。
- 不做采购下单、总库存自动扣减、自动决定内制/外协、自动拆批、不改已有正式计划、不提交或发布。

## 2. 名词与编排

### 2.1 名词层：现状 → 变化

现状：BatchMaterials只有整批需求和到料总数；Machines只有op_type_id；OpTypes.category固定internal/external；WorkCalendar、OperatorCalendar及班次只保存一对起止。事实来源为schema.sql及对应工作台维护模型。
变化：增加工序用料绑定、分次到料、确认拆批记录；增加设备工种关系和可双归属工种；日历保存结构化时段列表。API只新增明确字段，旧输入保留兼容。例：08:00–12:00、13:00–17:00仍是8小时，11:00起做2小时于14:00结束。

### 2.2 编排层：现状 → 变化

现状：批次整体齐套预检后整批进入计算；能力只按单工种匹配；日历用单窗口推进。
变化：选择本次物料策略 → 完整资料预检 → 必要时读取拆分预览 → 人工确认数量与用料分配 → 重新读取排产输入 → 逐道工序按材料可用时刻和真实资源时段计算 → 候选与采用重新验证同一份约束。
全部写入沿用原永久引用、短期写令牌、request_key回执和事务。资源/到料/班次在预览后变化时要求重新预览；只读预检不建记录。候选记录带上本次策略，历史结果按其原始快照读取。

### 2.3 挂载点

批次物料维护及拆分预览/确认入口；执行排产的物料策略选项；工种、设备维护与相应文件入口；全局/个人/轮换班次维护与文件入口；迁移注册、排产输入、候选保存/采用及计划日历和产能展示。

### 2.4 推进策略

先落实持久化和向前迁移契约，再分别实现班次计算与维护、工种能力全链路、分阶段物料和确认拆批，最后接入排产选项、组合场景和完整适用验证。

### 2.5 结构健康度

CalendarEngine、资源输入校验与文件适配已接近职责边界；新时段解析、能力集合、用料就绪计算各自归属独立的小模块，现有入口只编排。不为文件行数另造平行实现，不作无关搬移。

## 3. 验收契约

1. 100件需100份料、已有40份 → 只读预览40/60 → 确认后两批数量及物料需求/到料合计守恒；旧令牌、并发变动和重复确认不得重复拆分。
2. 前序用料已齐、后序明日到料 → 分阶段模式允许前序先做，后序不得早于到料；严格模式保持旧行为；策略随候选保存并在采用时核验。
3. 一台设备登记车削和铣削 → 两种工序均可候选，其他工种仍被排除；人员仍受技能及设备授权限制。
4. 同一工种登记自制及外协 → 路线、归属维护、导入和批次验证均可明确选择任一归属，实际排产不混用资源及周期。
5. 午休、多段夜班 → 推进、工作小时差、资源占用、产能、候选及采用一致，空档不能工作、工时不双计。
6. 旧数据库向前迁移保留原始行和既有计划，旧模板仍可读；损坏或残缺新结构不可伪装成旧数据正常回退。
7. 页面与文件可完成新增、修改、清除和往返；不需要用户写JSON、内部引用或编程字符串。

## 4. 架构归并

归并到现有资源、日历、批次及工作台排产职责；扩展现有workbench-production-workflows需求，不新增独立排产器。数据字典、系统速查表、用户说明及模板填写说明随实现同步。验收完成后保存实际通过证据，不声明dirty工作区为clean proof。
