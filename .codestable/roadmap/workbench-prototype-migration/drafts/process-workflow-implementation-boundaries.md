# 工艺三步迁移实施边界

2026-09-09，资源控件整合期间的只读接入梳理。此文是第 3 项的设计输入，不代表该项已实施或通过验收；规划基线 `workbench-capabilities.json` 不改写为实施状态。

## 可以复用的部分

- `core/services/process/part_service.py:138` 提供零件列表、详情、创建和更新，但普通创建后再解析不是整张表单的原子保存。
- `core/services/process/route_parser.py:277` 提供整串分词、工种及供应商上下文。未知工种、重复序号和宽松默认周期不能直接变成人工确认事实。
- `web/routes/process_excel_routes.py:224` 与 `core/services/process/part_operation_hours_excel_import_service.py:60` 有路线和工时 XLSX 能力。新增工作台必须返回结构化预检与回执，不从旧 HTML/flash 判断成功；CSV、范围导出和整批原子写入仍需接入。
- `frontend/workbench/app/ResourceWorkspace.jsx` 已有 `renderPart` 扩展点，继续复用统一控件及原型三步布局，不另起页面风格。

## 不可直接挂接的部分

- `PartService.reparse_and_save` 当前删除工序和外协组后重建，只按同序号保留部分工时。新预检必须显示明确差异，不能用这个路径覆盖旧外协规则和人工确认。
- `PartOperations.source` 不等于逐序人工确认记录；尚未找到等价确认历史、待建工种台账或三步阶段存储。不能根据原型的 `attr='done'` 推断后端已经完成。
- `PartService.update_internal_hours` 一道一次且有空值到零的旧语义，不能把它循环调用当成整页原子保存。
- 模板工序、模板外协组还没有独立永久引用，不能用序号、裸数据库 id 或批次工序引用代替。新增身份只能在迁移/写事务中创建，GET 不修补元数据。
- `part_service.py:435` 的旧路线参考快照只列供应商旧单工种；新预览需覆盖 v21 显式多工种及其变更，不允许预览过时后继续确认。
- `core/services/scheduler/batch_template_ops.py:76` 会补建缺失模板，需统一模板可用性合同，不能让待确认路线绕过新阶段控制。模板修改不反写既有批次与计划。

## 建议实施顺序

1. 主代理先定模板身份、阶段投影、预检输入与确认回执 DTO；保留旧模板的原始来源状态，不伪造人工确认。
2. 并行 A：模板身份/阶段存储及仓储；B：只读查询、解析适配及差异预检；C：原型三步组件和取消流程。三者独占文件。
3. 事实与预检合同稳定后，再并行阶段确认与文件编解码。写入统一走 `WorkbenchCommandService`，完整预览留服务器，确认只提交原预览引用；命令回执与变更同事务。
4. 主代理统一迁移注册、路由、宿主、构建、下游边界及真实浏览器/压测。旧解析器、共享入口不得由多位代理同时修改。

首个可验证范围是：新增模板身份且旧业务表不变；真实零件分页/详情；路线只读预检；三步界面取消不写业务表。确认与文件写入后续接入，不把此范围称作三步全功能完成。

## 设计需明确

- 旧模板无需被猜成“已人工确认”；其沿用规则及是否要求新确认，必须在新合同中明确。
- 单件工时真实零、未填写及全外协“不适用”分开，不用空值补零或猜工时。
- 人工归属与当前工种类别冲突时如何合法保存，不能自动改整个工种类别。
- 删除后同号重建、同序号换工种、并发转建未知工种、显式供应商能力变化、超时重放、中途回滚、旧批次与外协组保留均纳入测试。
