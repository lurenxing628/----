# Workbench 样板接回真实后端：总体方案

## 1. 背景与结论

目标是把当前样板完整接到仓库真实后端，保持界面布局、风格和操作流程；不是另做一套简化版，也不是将旧页面装进 iframe。全部功能接入、复杂数据测试、逐项浏览器输入点击、目视检查、旧页备份及最终下线都属于同一个交付目标。

用户已明确“好的，就按你的意见来,开干吧”，本方案进入实施。按既定顺序连续实现与验证，不重复索要同一授权；旧生产入口和真实数据的切换仍须通过既定备份及最终验收条件，不提前执行。

主要结论：

- Win7 不是推倒样板的理由。真实 Chromium 109 已通过15入口、60个初始主题/尺寸状态及关键原型交互测试，详见 [兼容评估](drafts/win7-runtime-assessment.md)。Win7真机、真实业务和容量验证仍未完成。
- 已清点206个能力族，其中1个统一详情入口为潜在未达项；一个能力族可能含多个字段和动作，不能把206当作最终单动作测试分母。机器清单见 `workbench-capabilities.json`，详细原型证据见 [能力清单](drafts/prototype-capability-inventory.md)。
- 后端基础CRUD、排产、计划读取、Excel、执行事件和维护服务可复用；逐次报工/更正、工艺确认、部分资源关系、候选采用闭环、校准采纳、值班台处置需要补能力。仅替换请求地址不能完成迁移。
- 推荐保留现有 Flask/Python 3.8/SQLite/本机Chrome109，复用样板已有React18和普通JS实现，在打包端预编译并本地交付。此选择与旧fusion roadmap的“不做SPA/不引入框架或构建工具”冲突，作为D01明确提交review，不偷偷修改旧文档。

## 2. 范围与取舍

### 2.1 必须交付

1. 14个index路由及独立方案试调：基础资料、批次、排产检查及真实运行、方案对比、计划甘特、交付风险、现场记录/实际甘特、执行复盘、报表、校准、值班台、主数据总览、系统管理，以及各自可达详情、页签、弹窗、导入导出。
2. 样板中的可操作按钮、缺实现而禁用的入口、明确声明待接入的报表/校准/维护能力；不会因当前是占位而从分母删除。业务保护而禁用的条件仍必须保留。
3. 真实持久化、失败/冲突/空态、跨页对象和范围一致、正式与候选隔离、取消零业务写入、重启后读回；所有数字可追溯到真实数据及计算口径。
4. 1920×1080为主要桌面验收，1392×924为窗口回归，浅/深双主题；Win7字体、输入法、100%/125%/150%DPI。保持表格密度、按钮对齐、必要分隔线、甘特边界/冻结列/窄条和焦点状态，不以统一白底或删控件解决问题。
5. 旧界面完整源码备份、数据保护方案、恢复演练；最终交付包只有新界面，旧GET入口按清单重定向或明确退役，不能继续隐藏运行旧界面。

### 2.2 不凭空扩大

- 不新增云服务、MES采集、设备控制、多用户权限平台、新目标操作系统或目标机Node/Python安装要求。
- 不迁移所有历史设计备选HTML；以当前实际挂载链为准，不以script已加载推断页面在用。
- 样板没有的旧高级设置、独立旧页面和旧专属列允许不搬，但必须逐条记录。见 `legacy-option-disposition.md`；不搬入口不等于删除存量配置、事件、外协组、班组、日历或服务。
- 不增加样板没有的拖动、撤销/重做、排产取消等能力来凑“完整”。必要加载/保存/失败反馈沿现有工作区补齐。
- 不重写排产策略来获得好看的候选指标；有必要的生命周期和执行事实接入改动，但算法质量、约束和已有失败守卫保持可回归。

### 2.3 review需要确认的决定

下表建议已随用户确认进入实施约束。出现未覆盖的新业务取舍或实质风险变化时再沟通；尚未实现的项仍不得在完成统计中算作passed。

| ID | 建议决定 | 影响与理由 |
| --- | --- | --- |
| D01 前端接法 | 同一本机Flask服务提供预编译的样板React18/普通JS资产；保留现有导航交互，不改成旧模板外观 | 最小化重写导致的视觉/行为漂移；显式替代旧fusion“无SPA/无构建工具”的本次相关限制，其他Win7/离线约束不变。若不同意，采用Flask/Jinja+普通JS同DOM复刻，重新估计工量但不减少验收 |
| D02 排产与采用 | 新工作台运行先持久保存待选方案集合，不自动替换正式计划；点击“采用”且服务端复核通过才生成正式版本 | 样板的预览/采用区分必须真实成立；旧run直接写正式结果不可原样挂到新按钮 |
| D03 已完成工序 | 保留真实已完成事实和既有重排保护；原“可重排”选项在真实数据模式不可执行并说明原因 | 不将已完成工序重新置未开始，也不改其真实时间/数量；若必须支持返工，应另设计新工序，不用此次UI开关覆盖旧事实 |
| D04 演示与重置 | 保留原位置的复杂/密集/管理样例入口，明确隔离为演示；生产读失败不回退样例。试调“重置”只放弃当前草稿，配置“还原”只恢复读取快照 | 不把样板重置映射为删除生产计划/历史；演示不能取得生产写令牌 |
| D05 报工与校准 | 逐次记录数量与有效加工工时，追加更正版本，整道完成由权威累计量/完整性得出；有效加工工时不包含准备、暂停和异常耗时 | 原事件跨度不是有效工时。校准建议按近20个合格整道完成样本、至少5个计算中位数；这是待确认的初始口径，不是源码已有规则。未知/旧数据不足不得生成可采纳建议 |
| D06 新资源语义 | 人员工种技能、供应商多工种、班次档、设备组、工艺确认建立显式记录；不借同名旧字段假映射 | 原有人员-设备授权独立保留；未知旧“停用/休假”不自动改成请假；班次档不得覆盖个人日期例外。低库存未配置判断依据时显示未知，不虚构阈值 |
| D07 报表目录 | 样板“其他报表”已承诺的超期/利用率/停机/正式Excel接入现有目录，用现有控件样式补生成/下载动作 | 保留报表能力，不恢复旧页面整套布局/独有筛选；旧页差集中必须区分“退旧入口”和“删报表能力” |
| D08 旧选项 | 按旧选项清单退役UI，保留未展示字段与后端规则；无新等价入口的旧书签明确说明退役 | 不在新界面暗藏“返回旧版”，不静默丢弃版本/筛选上下文，不清除用户原配置 |

## 4. 共享接口契约

详细合同见 [workbench-contracts.md](workbench-contracts.md)，是本方案的规范部分，与本文共同review。所有新路径/服务都是拟建，不能误称已有API；已存在的真实接口证据分别在两份后端评估中。

必须共同遵守：

- 所有页面使用服务端给出的稳定公开引用、同一计划身份/时间范围/数据时点；不暴露裸内部工序/排程/场景ID，不靠显示名称或数组位置定位。
- 查询、表格、图表、详情、跨页、导出共享`Scope`和`snapshot_ref`。0与未知、计划与实际、工序与批次、一次报工与整道完工分别表达。
- 写入绑定`write_token`和`request_key`；服务端重新校验身份、当前状态和范围。同请求重复执行不重复提交，旧快照冲突不静默重试覆盖。
- 新增真实能力走领域服务/事务，route只转换协议；不能把多次独立POST包装成一次原子保存，不能解析旧HTML/flash来判断业务成功。
- 前端只做呈现和输入草稿；正式版本、累计数量、校准结果、处置事实、备份健康由服务端决定。演示数据与生产数据不能互相兜底。

## 7. 验证、备份与下线

### 7.1 覆盖证据

- 每个能力族进一步拆`action_id`，登记正常/非法/失败/取消/冲突/空态及应有持久化。B=后端真实数据，K=浏览器输入/点击，V=主代理实际查看，P=刷新/重启读回。缺任一适用证据不得passed。
- 真浏览器验收使用本机隔离服务，不向用户生产库点按钮。逐项实际进入页面、点击控件、键盘输入，保留操作和截图关联；DOM注入、API直调、`fill`与逐键输入分别标识，不冒充已手工完成。
- 所有生成/导出文件核对字节格式、行数、字段、范围和关键值；不只验证下载事件或文件名。备份恢复/删除只用专门测试副本。
- 第一轮能力库为小规模精确案例；压测使用真实文件SQLite、真实请求和浏览器，不用几条数组数据冒充容量。

### 7.2 压测和目标环境

采用 [验证发布评估](drafts/verification-and-release-assessment.md)第6节的L0/L1/L2/L3方案：100工序功能集、2000工序常规集、10000工序重载集、50000工序容量边界；资源、历史版本、逐次报工和日志同步增长。L3是探索上限，不是预先承诺的可用容量。
