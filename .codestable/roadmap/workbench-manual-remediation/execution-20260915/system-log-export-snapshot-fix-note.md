# 系统日志查询后立即导出仍过期

## 现场与根因

主代理在 5002 真实页面读取运行日志，点击“导出这段日志 CSV”和“脱敏诊断 ZIP”均得到 `snapshot_stale`；点击“刷新清单”后立即导出仍失败，没有生成下载文件。

本子任务获准使用只读 GET 定向复现，得到 HTTP 409 / `snapshot_stale`。两次读取间，`aps.log` 从 32 条增为 34 条，新增两条 `factory.py:483` 发出的“慢请求”记录（409ms、415ms）；相同原日志的 8 个 key 因尾部索引变化而变化。日志读取本身产生慢请求日志，下一次导出又重读全部日志并重新比较指纹，因此自身使刚签发的快照立即过期。

原始调用链：`system_collection → collection → log_records`；CSV/ZIP 的 `system_log_export` 再调用同一个 `collection`，重新扫描文件并检查实时指纹。问题不依赖业务数据并发写入，也不是前端传错 token。

## 修复边界

- `web/routes/workbench/system_reads.py`：日志首次读取保留已筛选范围；携带原快照的翻页和导出从该范围读取。点击刷新、不带快照时重新读日志。
- `web/routes/workbench/system_log_snapshots.py`：在应用进程内保留不可变的、已经脱敏的窗口。继续通过现有 `bind_read_snapshot` 校验 token、筛选范围及内容指纹；不复用浏览器数据来拼文件。
- 快照有效期 15 分钟，最多 32 份、合计 64 MiB；淘汰或过期后明确要求刷新，单份超过容量明确失败，不静默截断。
- 绑定既有 `restored_context_ref` 数据代次（数据库路径与已确认成功的恢复记录）；恢复后旧日志快照失效，普通备份不使其失效。进程重启丢失暂存窗口，旧 token 不可继续导出。
- 备份清单、备份文件下载和写操作仍使用原实时校验；没有改公共读快照基础设施，没有新增表或写命令，没有过滤慢请求日志。
- 不需要前端构建；实际应用重启后加载新后端，用户刷新一次日志清单即可取得新快照。

## 验证

在既有 `tests/workbench/test_system_maintenance_api.py` 增加定向场景：真实 Flask 路由返回后由 `after_request` 追加慢请求日志。第一次读取 30 条，随后翻页、CSV、ZIP 都保持这次已读的 30 条；刷新后读取到新增的 4 条日志。

- CSV 的 30 条源内容完整；ZIP 内 `logs.csv` 与 CSV 下载逐字节相同；ZIP CRC 通过；诊断元数据的时间、范围与首次读取一致。
- 换范围、伪 token、缺少窗口、窗口过期、原 token 过期、缓存内容被替换均拒绝，失败响应不带文件下载头。
- 恢复数据代次变更拒绝旧快照；普通备份不影响。窗口数和字节数两种边界均测试淘汰，单份容量不足明确失败。
- 保留原脱敏、缺失来源提示、输入校验和备份/配置相关测试。原“追加日志后旧导出必须过期”的断言改为“旧导出保持原内容，刷新后的导出才包含新日志”，只改变日志导出的已读窗口语义。

执行 `.venv/bin/python -m pytest -q tests/workbench/test_system_maintenance_api.py`：`36 passed in 7.26s`。修改范围 Ruff 与 `git diff --check` 通过。没有执行全门禁、整仓测试、构建、浏览器或服务操作，没有写业务数据库；测试均使用隔离临时目录。

新产品模块需加入既有系统专项测试组依赖，由主代理统一登记。实际 5002 CSV/ZIP 下载文件的手动确认由主代理重启服务后完成。
