# APS 前端工作台页面级设计稿

## 1. 设计目标

这份稿子把 `aps-frontend-workbench` roadmap 继续往下落到页面层。

大白话说，当前系统不是没有页面，也不是没有功能。首页、排产分析、甘特图、资源派工、超期清单、资源负荷、计划和现场实际都已经有基础。真正要补的是一条清楚的做事路线：

1. 计划员打开首页，先知道今天有没有风险。
2. 看到风险后，可以直接进入对应页面，不需要自己猜下一步。
3. 到了分析页，先看推荐和异常，再看指标和技术过程。
4. 到了甘特页，第一版边看任务条边看任务详情，并能跳到资源负荷报表或资源派工；Top 资源负荷摘要第二阶段再做。
5. 到了资源派工页，能分清“看排班”和“计划员代录现场实际”。
6. 到了报表页，看完数字能跳回甘特、资源派工或延期说明继续处理。

本稿只设计页面怎么排、信息怎么放、入口怎么串。暂不改算法，不开放甘特拖拽写库，不把资源派工扩大成完整 MES。

## 2. 硬边界

- 继续服从 Win7 x64、Python 3.8、Chrome 109、离线交付。
- 不引入外部 CDN、外链字体、外链脚本和新的重型前端框架。
- 页面仍使用现有 Jinja 模板、`ui_macros`、`ui_contract.css`、`aps_gantt.css` 等本地能力。
- 甘特图第一阶段仍是只读结果查看，禁用拖动和拉伸交互，不出现保存、采用、提交正式计划入口。
- 普通用户可见文字只显示中文业务名，不直接显示 `scenario_id`、`plan_role`、`candidate_id`、`op_id`、`schedule_id`、`source_table`。
- URL、隐藏域、日志、服务端参数属于上下文传递层，可以继续使用 `scenario_id`、`plan_role` 等内部参数；测试“不外露”时，重点检查页面正文、表格、详情区、按钮文案、导出公开列和对外 payload，不把 URL 参数当普通页面文案。
- 候选方案、模拟预览、历史方案不能写现场记录；现场记录的开工、完工、手填、Excel 模板下载、Excel 导入和对应 API 都必须以后端 `available_actions`、`can_write_feedback` 和服务端校验为准。
- 延期说明只写“已确认事实、可能线索、证据缺口、建议动作”，不能写成“系统已确认唯一根因”。
- `docs/aps_frontend_workbench_mockup.html` 只作为布局参考，不能直接复制它的独立样式和演示数据；mockup 里的暂停、继续、报异常等车间按钮只是历史示意，第一版不得照抄实现。

### 2.1 Exa 外部对标补强原则

2026-05-31 追加 3 个 SubAgent 使用 Exa MCP 做外部对标，覆盖成熟 APS、MES 车间执行、项目管理 / 派工指挥台三类产品。结论是：当前方向不用推翻，但有几类细节要补硬。

- 成熟 APS 会把瓶颈、资源负荷、方案差异和交期风险放到工作台前面；本项目第一版要把这些做成入口和摘要，不追求复杂图表。
- 成熟 MES 写入现场实际时，不只看“是不是正式方案”，还会看账号权限、任务状态、后端动作和数据缺口；本项目第一版至少要把不可写原因用中文说清楚。
- 成熟项目管理软件会把基线差异、任务表、甘特、详情和筛选器联动；本项目第一版先做只读差异摘要和高亮定位，折叠式任务表、保存视图放到第二阶段。
- 外部对标资料多来自公开文档和产品页，不能当成真实登录后的完整界面证据；只把“方向明确、和当前硬约束不冲突”的内容写进第一版。

## 3. 总信息架构

### 3.1 顶层入口

当前顶栏已有：首页、排产、工艺、人员、设备、物料、报表、系统。

Claude Code 第一轮复核指出：如果只在页面内部加强跳转，Finding 08 的“顶层导航缺核心作业入口”仍然会留下。这里采用它的反驳意见：第一版就要让计划员在顶层一跳进入主工作流，但不要把顶栏塞成一排细页面。

建议把当前“首页”升级为“计划工作台”，默认仍指向 dashboard 首页值班台；同时做一个轻量下拉或同等的一跳入口。下拉用本地 HTML/CSS 实现，键盘可达，不引入新的菜单库。实现时用普通链接列表，配合 `:focus-within` 和 hover 展开；不能只做鼠标 hover，否则键盘和触屏用户打不开。

```text
[计划工作台 v] [排产 v] 工艺 人员 设备 物料 [报表 v] 系统
  - 首页值班台        - 执行排产              - 超期清单
  - 排产分析          - 批次管理              - 资源负荷
  - 甘特图（设备）    - 周计划                - 计划和现场实际
  - 甘特图（人员）    - 排产历史              - 停机影响
  - 资源派工
  - 计划和现场实际
```

| 入口 | 页面定位 | 首次落地建议 |
| --- | --- | --- |
| 计划工作台 | 每天做事的主入口 | 由原“首页”升级，默认进首页值班台，下拉直达分析、甘特、资源派工、复盘 |
| 排产 | 排产准备和执行入口 | 继续承接执行排产、批次管理、周计划、排产历史 |
| 报表 | 风险和复盘入口 | 下拉直达超期清单、资源负荷、计划和现场实际、停机影响 |
| 工艺/人员/设备/物料/系统 | 基础资料和维护 | 保持原入口，不抢计划员主流程 |

顶层导航要把“核心作业、基础资料、配置支持”分清。计划员每天处理风险、看甘特、看资源派工、看报表，优先从计划工作台进入；工艺、人员、设备、物料这些基础维护继续保留，但不要让计划员在这些菜单里找主流程。

如果第一轮实现不方便做下拉，最低要求也要把顶层“首页”文案改成“计划工作台”，并在页面标题区提供“分析、甘特、资源派工、复盘”的一跳入口。不能只把入口埋在二级页面内部。

### 3.2 工作台主流程

```text
首页值班台
  -> 今日待处理：超期 / 资源高负荷 / 方案待复核 / 现场情况待确认 / 基础数据缺口
  -> 排产分析：先看推荐方案和诊断行动
  -> 甘特图：看任务条、任务详情、资源负荷入口
  -> 资源派工：看排班、由计划员代录现场情况
  -> 报表中心：看风险汇总和复盘入口
  -> 计划和现场实际：核对计划与现场事实，再回到甘特或资源派工
```

### 3.3 跨页上下文

每个主页面顶部都要有同一类上下文条。用户不一定懂“版本、方案、预览”这些背后的技术含义，所以页面要用中文说清楚：

| 字段 | 用户看到的写法 | 说明 |
| --- | --- | --- |
| 版本 | 第 12 版 / 暂无排产版本 | 不显示内部 id |
| 方案 | 正式采用方案 / 原算法代表方案 / 重点工序优先代表方案 / 模拟预览（未命名） | 页面可带 `plan_role` 或 `scenario_id`，但可见位置只显示中文 |
| 日期范围 | 2026-05-25 ～ 2026-05-31 | 首页、甘特、资源派工、报表要一致 |
| 查询日期 | 2026-05-31 | 资源派工按周/月查询时要保留 `query_date` |
| 区间类型 | 按周 / 按月 / 自定义 | 资源派工和报表跳转时要保留 `period_preset` |
| 查询对象 | 全部人员 / M-03 / 张三 / B202605-018 | 用业务对象名，不露内部字段 |
| 写入状态 | 当前方案可写现场记录 / 当前只是预览，不能写现场记录 | 资源派工和现场记录必须显示 |
| 不可写原因 | 当前方案不可写 / 当前任务状态不可写 / 后端动作不可用 / 数据不足 | 不能只显示“不可写”三个字；后续用户已拍板短期不新增多人账号权限 |
| 容量来源 | 工作日历 / 班次 / 停机扣除情况 / 数据不足 | 资源负荷算得出来时要说明怎么算，算不出来时说明缺什么 |

内部值到中文展示要统一，不能每个页面自己翻：

| 内部值 | 中文展示值 |
| --- | --- |
| `plan_role=adopted` | 正式采用方案 |
| `plan_role=baseline_best` | 原算法代表方案 |
| `plan_role=critical_best` | 重点工序优先代表方案 |
| 有 `scenario_id` 但没有可读名称 | 模拟预览（未命名） |
| `guardrail_reason_type=plan_not_writable` | 当前方案不可写 |
| `guardrail_reason_type=task_state_blocked` | 当前任务状态不可写 |
| `guardrail_reason_type=action_unavailable` | 后端暂未开放这个动作 |
| `guardrail_reason_type=data_gap` | 数据不足，暂时不能判断 |
| `resource_type/scope_type=operator` | 人员视角 |
| `resource_type/scope_type=machine` | 设备视角 |
| `resource_type/scope_type=team` | 班组视角 |
| `period_preset=week` | 按周 |
| `period_preset=month` | 按月 |
| `period_preset=custom` | 自定义 |
| `view=machine` | 设备甘特 |
| `view=operator` | 人员甘特 |

下面这张表是后续实现和测试的硬输入。大白话说：用户从一个页面点到另一个页面时，不能只带版本号；方案、日期、批次或资源对象也要带上，否则用户看到的就可能不是同一套计划。

| 来源 | 目标 | 必带上下文参数 | 页面可见中文上下文 | 禁用条件 | 测试断言 |
| --- | --- | --- | --- | --- | --- |
| 首页值班台晚交待处理 | 超期清单 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`batch_id` 可选 | 第 N 版、方案中文名、日期范围、批次号 | 没有排产版本 | 跳转后版本、方案、日期不丢；页面正文不显示内部字段名 |
| 首页值班台查看甘特 | 甘特图 | `version`、`plan_role`、`scenario_id`、`start_date`、`end_date`、`view=machine/operator`、`batch_id` 可选 | 第 N 版、方案中文名、日期范围、甘特视图 | 没有排产版本或没有日期范围 | 甘特上下文条和首页一致，视图明确 |
| 首页方案待复核 | 排产分析 | `version`、`plan_role`、`scenario_id` | 第 N 版、方案中文名 | 没有候选方案 | 推荐卡和三方案摘要仍指向同一版本 |
| 首页现场情况待确认 | 资源派工 | `version`、`plan_role=adopted`、`date_from`、`date_to`、`query_date`、`period_preset`、`scope_type` 可选、`resource_id` 可选、`batch_id` 可选 | 第 N 版、正式采用方案、日期范围、当前资源或全部资源、写入状态 | 没有排产版本或没有日期范围 | 资源派工上下文条和首页一致；只允许正式采用方案下发现场记录写入口 |
| 首页资源高负荷 | 资源派工 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`query_date`、`period_preset`、`scope_type`、`resource_id` 可选 | 第 N 版、方案中文名、日期范围、当前资源或全部资源、写入状态 | 没有排产版本或没有日期范围 | 资源派工上下文条和首页一致；模拟/候选方案不可写现场记录 |
| 首页风险汇总 / 常用工作区 | 报表中心 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`query_date`、`period_preset` | 第 N 版、方案中文名、日期范围、查询区间 | 没有排产版本 | 报表中心入口卡保持同一版本、方案和日期范围，能继续进超期、资源负荷、计划和现场实际 |
| 排产分析推荐卡 | 甘特图 | `version`、`plan_role`、`scenario_id`、`start_date`、`end_date`、`view=machine/operator` | 当前查看方案、显示范围、视图 | 没有可查看排程 | 甘特上下文条和分析页一致 |
| 排产分析诊断卡 | 超期清单 | `version`、`plan_role`、`scenario_id`、`batch_id` 可选 | 当前方案、批次或风险类型 | 没有诊断数据 | 详情区显示事实、线索、缺口、建议动作 |
| 排产分析诊断卡 | 延期说明 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`batch_id` 可选 | 当前方案、批次或风险类型 | 没有诊断数据或没有日期范围 | 第一版复用超期清单路由，但 `target_page=delay_diagnosis`，用于区分“解释原因”的入口意图 |
| 甘特任务详情 | 资源派工 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`query_date`、`period_preset`、`scope_type`、`resource_id`、`batch_id` 可选 | 当前资源、当前方案、写入状态 | 任务没有资源对象 | 资源派工自动选中对应视角和资源；模拟/候选方案显示不可写 |
| 甘特任务详情 | 计划和现场实际 | `version`、`plan_role=adopted`、`date_from`、`date_to`、`batch_id` | 正式采用方案、批次、日期范围 | 当前方案不是正式采用方案 | 非正式方案入口禁用，并显示“计划和现场实际只复盘正式采用方案，请切换到正式采用方案后查看” |
| 资源派工任务明细 | 报表中心 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`query_date`、`period_preset`、`scope_type`、`resource_id` 可选 | 当前视角、资源、方案、日期 | 没有查询结果 | 报表入口卡按同一上下文生成 |
| 资源派工现场记录 | 计划和现场实际 | `version`、`plan_role=adopted`、`date_from`、`date_to`、`query_date`、`period_preset`、`batch_id`、`scope_type`、`scope_id` 可选 | 正式采用方案、批次、资源 | 当前方案不是正式采用方案 | 只有正式采用方案能进入复盘页；复盘行能回到资源派工任务 |
| 报表中心资源负荷 | 资源派工 | `version`、`plan_role`、`scenario_id`、`date_from`、`date_to`、`query_date`、`period_preset`、`scope_type`、`resource_id` | 最忙资源、当前方案、日期 | 无资源行 | 点击“查看排班”后资源对象不丢 |
| 报表中心超期清单 | 甘特图 | `version`、`plan_role`、`scenario_id`、`start_date`、`end_date`、`batch_id`、`view=machine/operator` | 超期批次、方案、范围 | 无甘特数据 | 甘特进入后自动保留仅超期或定位对象 |
| 计划和现场实际 | 资源派工 | `version`、`plan_role=adopted`、`date_from`、`date_to`、`batch_id`、`scope_type`、`resource_id` 可选 | 正式采用方案、批次、资源、日期 | 无现场记录 | 回到资源派工后同一任务仍可定位，并继续显示正式采用方案 |

如果某个目标页只能通过 URL 传 `scenario_id`、`plan_role`、`scope_type` 等内部参数，这些参数可以存在于 URL 或隐藏域；但页面上必须用“正式采用方案”“模拟预览”“人员视角”“设备视角”等中文业务词解释。

第一版里，`overdue_report` 和 `delay_diagnosis` 都落到现有 `/reports/overdue` 路由。区别不靠 URL 路径判断，而靠 `WorkbenchLink.target_page` 和按钮文案判断：`overdue_report` 表示“看超期清单”，`delay_diagnosis` 表示“解释为什么晚”。两者都要保留版本、方案、模拟预览、日期和批次上下文，不能因为同路由就漏掉参数。

`execution_review` 是正式采用方案的只读复盘入口。URL 可以带 `plan_role=adopted` 作为明确口径，但不能带非 adopted 的 `plan_role` 或 `scenario_id`；当前上下文不是正式采用方案时，入口必须禁用并给中文原因。

## 4. 通用页面骨架

所有工作台相关页面建议统一成下面的顺序：

```text
[页面标题 + 主要动作]
[上下文条：版本 / 方案 / 范围 / 对象 / 写入状态]
[首屏风险或结论：用户先知道要看什么]
[主工作区：表格 / 甘特 / 卡片 / 列表]
[详情区：点中某条后固定显示完整解释]
[次要区：导出、说明、历史、技术过程]
```

通用规则：

- 首屏只放每天高频使用的信息，不把所有筛选和说明都塞在最上面。
- 计划员页面可以信息密一些，但要有稳定网格、横向滚动和固定最小宽度。
- 现场记录页面要简单：任务卡、大按钮、少字段。
- 每个新增区都要设计空状态、加载失败状态、数据不足状态。
- 颜色只表达状态：蓝色主动作，绿色正常，黄色提醒，红色风险，灰色说明。
- 卡片只用于状态、方案、异常、任务、报表入口，不做大卡套小卡。
- 宽屏优先左右布局，窄屏改成上下堆叠；按钮允许换行，不允许文字挤出。

## 5. 首页值班台

### 5.1 目标

首页不再只是“统计数字 + 常用入口”。它要回答一个问题：今天我先处理什么？

### 5.2 首屏布局

```text
[首页标题：计划员值班台]
[上下文条：最新版本 / 当前方案 / 计划范围 / 数据更新时间]
[风险卡 4-5 张：待排 / 已排 / 超期 / 最近版本 / 现场情况待确认或资源风险]
[左右两栏]
  左：今日待处理，最多 6 条
  右：最近排产结果，说明采用方案、风险、下一步
[二屏：常用工作区]
```

### 5.3 风险卡

| 卡片 | 主数字 | 副文案 | 点击入口 | 状态 |
| --- | --- | --- | --- | --- |
| 待排批次 | 待排数量 | 还有 X 个批次没有进入计划 | 批次管理或执行排产 | warning |
| 已排批次 | 已排数量 | 最新版本已覆盖 X 个批次 | 甘特图 | ok |
| 超期批次 | 超期数量 | 有 X 个批次晚于交期 | 超期清单 / 延期说明 | danger |
| 资源高负荷 | X 个资源 | 能安全算出的受影响批次；算不了就说明数据不足 | 资源负荷 / 资源派工 | warning |
| 最近版本 | v12 或 -- | 结果：成功 / 部分成功 / 失败 | 排产分析 | notice |
| 现场情况待确认 | X 条 | 已到计划开始时间的任务暂未收到/录入现场情况 | 资源派工现场事实区 | warning |

风险卡和今日待处理可以指向同一类问题，但职责不同：风险卡是总数入口，让用户知道整体严重程度；今日待处理是按严重度挑出来的前 6 条具体事项，让用户直接处理。比如“现场情况待确认”卡显示共有 X 条，今日待处理只显示最急的那几条。

没有数据时不要只显示 `0`。例如：

- “还没有排产版本，先执行一次排产后再查看甘特和报表。”
- “当前没有必须马上处理的排产风险，可以查看甘特确认任务安排。”

### 5.4 今日待处理

最多展示 6 条，按严重程度排序。每条必须包含：

- 风险类型：晚交、资源高负荷、方案待复核、现场情况待确认、基础数据缺口。
- 标题：一句人话，例如“3 个批次会晚于交期”。
- 影响：告诉用户会影响什么，例如“最晚批次 B202605-018 晚 14 小时”。
- 证据：来自哪个版本、哪个范围、哪个对象。
- 动作：一个明确按钮，例如“查看为什么晚了”“看资源占用”“打开方案对比”。
- 处理状态：未查看、已查看、已处理、暂不处理。第一版如果不落库保存这些状态，要明确显示为“实时生成”，不要让用户以为系统会记住处理结果。

示例：

| 类型 | 标题 | 影响 | 动作 |
| --- | --- | --- | --- |
| 晚交 | 3 个批次会晚于交期 | 最晚批次 B202605-018 晚 14 小时 | 查看为什么晚了 |
| 资源高负荷 | M-03 本周接近满载 | 利用率 96%，影响 4 个批次，最晚 B202605-018 | 看资源占用 |
| 方案待复核 | 有 2 套方案可对比 | 建议先看推荐方案和代价 | 打开方案对比 |
| 现场情况待确认 | 5 个任务暂未收到/录入现场情况 | 派工后还没有能说明现场进展的记录 | 打开资源派工现场事实区 |
| 数据缺口 | 2 个批次工艺信息不完整 | 排程结果可信度会下降 | 去工艺页补资料 |

### 5.5 最近排产结果

现有首页已经有最近排产，但内容偏指标。建议改成“排产结果摘要”：

- 采用方案：正式采用方案 / 重点工序优先。
- 结果状态：成功 / 部分成功 / 失败。
- 推荐理由：例如“超期批次数更少，总拖期更短”。
- 代价：例如“换型次数增加 2 次，M-03 更忙”。
- 下一步：查看甘特图、查看排产分析、查看延期说明、进入资源派工。

### 5.6 常用工作区

放到首屏下方，不抢“今日待处理”的位置。建议分组：

- 排产作业：执行排产、批次管理、工作日历。
- 排产结果：排产分析、甘特图、资源派工。
- 风险复盘：超期清单、资源负荷、计划和现场实际。
- 基础资料：工艺、设备、人员、物料。

## 6. 排产分析行动入口

### 6.1 目标

排产分析页不要先让用户看技术过程。它要先回答：

- 当前版本能不能让计划员继续处理？
- 系统推荐看哪套方案？
- 有哪些风险需要先复核？
- 下一步该去甘特、资源派工，还是超期清单？

### 6.2 页面顺序

现状 include 顺序是版本选择、概览、warnings、诊断、指标、方案对比、优化过程。建议改成：

```text
[页面标题：排产优化分析]
[版本选择 + 上下文条]
[首屏行动摘要：当前版本状态 / 今日最需要看的风险 / 空状态]
[推荐方案卡]
[三方案摘要卡]
[延期 / 诊断行动卡]
[指标卡]
[方案对比表]
[优化过程和趋势图]
```

### 6.3 首屏行动摘要

内容：

- 当前版本：第几版、排产时间、结果状态。
- 当前方案：正式采用或对比参考。
- 风险摘要：超期批次、失败工序、资源高负荷、数据缺口。
- 下一步入口：看甘特、看资源派工、看超期清单。

没有选中版本时：

- 显示“请选择一个排产版本查看分析结果。”
- 给“去执行排产”和“查看排产历史”入口。

### 6.4 推荐方案卡

位置：三方案摘要和指标表之前。

卡片字段：

- 推荐结论：例如“建议优先看重点工序优先方案”。
- 推荐原因：用中文列 2-3 条，例如“超期批次数更少”“总拖期更短”。
- 代价：例如“换型次数更多”“M-03 负荷更高”。
- 影响面：优先展示已能安全计算的受影响批次数、最晚超期时长、换型次数、资源压力和数据缺口；算不了的项目用中文说明，不硬编。
- 适用提醒：例如“如果本周设备 M-03 不能加班，需要再看资源派工”。
- 动作：查看该方案甘特、查看资源派工、查看超期清单。

不能第一眼显示内部评分作为主结论。评分可以留在明细表或内部字段，不作为业务主语言。

### 6.5 三方案摘要卡

固定展示三类角色：

| 方案 | 身份说明 | 重点指标 |
| --- | --- | --- |
| 正式采用方案 | 已经写入正式排产结果 | 超期批次、总拖期、总工期、换型次数 |
| 原算法代表方案 | 对比参考，不能直接派工 | 与正式方案的差值：超期批次、总拖期、换型次数；资源压力能算就显示，算不了就说明 |
| 重点工序优先代表方案 | 对比参考，不能直接派工 | 与正式方案的差值：超期批次、总拖期、换型次数；资源压力能算就显示，算不了就说明 |

每张卡都要显示“可派工 / 仅对比 / 模拟预览”的中文状态，避免用户误把参考方案当成正式计划。

方案对比要有“差值”意识。大白话说，不只告诉用户“这套方案更好”，还要告诉用户“比正式采用方案好在哪里、差在哪里、代价是什么”。第一版可以用表格数字表达，不做复杂基线甘特叠线。

### 6.6 延期和诊断行动卡

放在指标卡之前。每张诊断卡按这个口径写：

- 已确认事实：例如“B202605-018 计划完成时间晚于交期 14 小时”。
- 可能线索：例如“M-03 在本周负荷较高，任务等待空档”。
- 证据缺口：例如“缺少物料齐套数据，不能判断是否由物料导致”。
- 建议动作：查看超期清单、定位甘特、查看资源派工。

### 6.7 技术过程后置

优化过程、趋势图、详细指标继续保留，但放在用户已经看到推荐和风险之后。它们服务于复核，不抢第一屏。

## 7. 甘特工作台

### 7.1 目标

甘特图是计划员查排程结果的核心页。第一版不是编辑器，而是只读工作台：

- 看时间安排。
- 看任务详情。
- 看资源负荷。
- 点风险后知道下一步去哪。

### 7.2 首屏布局

```text
[标题：甘特图（设备视图 / 人员视图）]
[上下文条：显示范围 / 版本 / 方案]
[高频工具条：视图 / 日期范围 / 版本 / 方案 / 仅超期]
[主工作区]
  宽屏：
    左/中：甘特图，第一版不新增左侧任务简表
    右：任务详情区，固定宽度约 320px
  窄屏：
    甘特图
    任务详情区
[第二阶段增强：甘特资源负荷摘要，最忙设备 Top 5 + 最忙人员 Top 5]
[折叠区：配色、复杂筛选、说明、图例]
```

硬布局规则：

- 第一版不新增左侧任务简表或资源树，避免把甘特图挤窄。
- 甘特主区最小高度建议 420px；如果数据为空，空状态也占稳定高度，避免页面跳动。
- 宽屏下任务详情区建议宽度 320px 左右，不随字段内容撑开。
- 第一版只保留去资源负荷报表或资源派工的上下文链接；Top 资源负荷摘要第二阶段再放到甘特主区下方。
- 如果首屏高度不足，优先保证用户能看到甘特主区顶部和“点击甘特条查看任务详情”的详情区空态。

### 7.3 高频工具条

第一屏外露只保留高频控制：

- 设备视图 / 人员视图。
- 上周 / 本周 / 下周。
- 起止日期。
- 版本。
- 方案。
- 仅超期。

放到折叠区：

- 时间粒度：月、周、日、小时等。
- 仅外协。
- 高亮关键工序。
- 工序关系线。
- 配色方式。
- 批次筛选。
- 资源筛选。
- 说明文字。

如果首屏空间紧张，优先保留版本、方案、日期、视图、仅超期，其他放折叠。时间粒度虽然高频，但它会占用下拉空间，默认可以跟配色放在折叠区顶部。

### 7.4 甘特主区

甘特主区继续使用现有本地 `frappe-gantt` 相关静态文件和项目已有 JS。

交互规则：

- 点击任务条：填充右侧或下方任务详情区。
- 点击超期待办跳入甘特：自动打开仅超期筛选，并高亮对应批次或任务。
- 点击资源高负荷跳入甘特：自动筛选对应设备或人员。
- 第一版禁用拖动和拉伸交互，不出现保存、采用、提交正式计划入口；如果页面保留禁用态“模拟调整”按钮，必须明确写“页面编辑流程完成后开放”，不能让用户误以为当前可编辑。
- 页面继续显示“当前为查看模式”。

### 7.5 任务详情区

未选中时：

```text
点击甘特条查看任务详情
```

选中后显示：

| 字段 | 说明 |
| --- | --- |
| 批次 | 业务批次号 |
| 图号 / 名称 | 零件或产品信息 |
| 工序 | 工序序号和名称 |
| 计划时间 | 开始、结束、交期 |
| 计划和实际小结 | 计划开始、实际开始、开工偏差、计划结束、实际结束、完工偏差；没有现场记录时显示缺口 |
| 资源 | 设备、人员、班组 |
| 状态 | 正常、超期、外协、关键工序、现场状态 |
| 延期提示 | 已确认事实 + 可能线索 + 数据缺口 |
| 下一步 | 查看为什么晚了、查看排产分析、查看资源派工、打开计划和实际 |

禁止显示 `op_id`、`schedule_id`、`source_table`、`scenario_id`。

### 7.6 资源负荷摘要（第二阶段增强）

第二阶段放在甘特附近，不只放报表页。第一版不强制显示 Top 摘要，只保留跳转到资源负荷报表或资源派工的入口。

第二阶段只做 Top 摘要，不做复杂直方图：

| 项 | 内容 |
| --- | --- |
| 最忙设备 Top 5 | 设备名、负荷小时、任务数、利用率、状态色 |
| 最忙人员 Top 5 | 人员名、排班小时、任务数、利用率、状态色 |
| 数据缺口 | 没有可用工时或日历时显示“利用率暂时算不了” |
| 容量来源 | 工作日历、班次、是否扣除停机；算不出来时显示具体缺口 |
| 入口 | 去资源派工、去资源负荷报表、查看这个资源的时间轴负荷 |

阈值建议先写死在 feature-design 里确认：

- 利用率 >= 90%：红色，接近满载。
- 75% <= 利用率 < 90%：黄色，需要关注。
- 利用率 < 75%：绿色，正常。
- 算不出利用率：灰色，数据不足。

## 8. 延期说明和超期清单

### 8.1 目标

超期清单不只是告诉用户“晚了多少”，还要告诉用户：

- 晚在哪里。
- 当前能确认什么。
- 可能线索是什么。
- 还缺什么数据。
- 下一步去哪查。

### 8.2 首屏布局

```text
[标题：延期说明 / 超期清单]
[上下文条：版本 / 方案 / 截至时间]
[异常总览：晚交 / 资源高负荷 / 停机影响 / 数据缺口]
[主列表：按严重程度排序的超期批次]
[详情区：点击一条后展示事实、线索、缺口、建议动作]
```

### 8.3 主列表字段

| 字段 | 说明 |
| --- | --- |
| 类别 | 已排超期 / 未排超期 |
| 批次 | 批次号和图号 |
| 交期 | 客户或计划交付时间 |
| 计划完成 / 截至时间 | 用于判断超期的时间 |
| 超期时长 | 天或小时 |
| 建议先复核 | 工序、资源、停机窗口或基础数据 |
| 可能线索 | 资源高负荷、前序拖延、停机重叠、数据缺口 |
| 证据等级 | 证据充分 / 证据一般 / 证据不足 |
| 下一步 | 定位甘特、查看资源派工、查看计划和实际 |

### 8.4 详情区文案

详情区固定五段：

1. 已确认事实
   例如：“这个批次计划完成时间晚于交期 14 小时。”
2. 建议先复核
   例如：“建议先看第 30 工序和设备 M-03 的排班。”
3. 可能线索
   例如：“M-03 本周负荷较高，相关任务等待空档。”
4. 证据缺口
   例如：“当前没有物料齐套数据，不能判断是否由物料导致。”
5. 建议动作
   例如：“可以先定位甘特、查看资源派工，或者打开计划和现场实际核对现场情况。”

如果当前只能确认本批次超期，不能判断连带影响，详情区要明说：“暂时只能看到本批次影响，不能判断对其他批次的连带影响。”如果能算出牵连批次，则显示“可能牵连的批次 / 订单”入口。

不能写：

- “主要根因已确认”。
- “物料一定不足”。
- “现场一定做慢了”。
- “AI 已经自动判断原因”。

## 9. 资源派工和现场记录分层

### 9.1 目标

资源派工现在承担很多事情：看任务、看日历、看甘特、由计划员代录现场记录、导出、看计划和实际。第一版不拆页面也可以，但视觉上必须分清三条线：

1. 计划员看排班。
2. 计划员代录现场事实。
3. 计划员或管理者看计划和现场实际复盘。

### 9.2 首屏布局

```text
[标题：资源派工]
[动作：查看计划和实际 / 打开报表中心 / 导出资源派工 / 去执行排产]
[上下文条：视角 / 查询对象 / 区间 / 版本 / 方案 / 写入状态]
[查询条件：视角、资源、区间、版本、方案]
[摘要：任务数 / 总工时 / 超期任务 / 跨班组 / 外协未分配 / 现场情况待确认]
[分组标签]
  看排班：任务明细 / 日历矩阵 / 甘特图
  代录现场事实：现场记录
```

双车道必须能被测试断言，不能只靠视觉感觉。实现时建议把 tab 分成两个独立容器：

```text
[计划员查看]
  [任务明细] [日历矩阵] [甘特图]

[现场事实]
  [现场记录]
  提示：计划员在这里代录实际开工和完工
```

后续测试可以断言页面存在“计划员查看”“现场事实”两个分组标题，现场记录 tab 位于现场事实分组内，且分组旁有“计划员在这里代录实际开工和完工”这类中文提示。

### 9.3 计划员看排班

任务明细表继续保留，但列分组要更清楚：

- 计划信息：开始、结束、批次、图号、工序、计划资源。
- 资源关系：查询对象、对应资源、班组关系、来源。
- 执行信息：现场状态、最近异常、影响资源。
- 下一步：查看甘特、查看计划和实际、查看现场记录。

### 9.4 现场记录

现场记录使用任务卡，不使用宽表作为主入口。

现场事实区首屏先提供快速筛选：

- 今日任务。
- 待开工。
- 待完工。
- 现场情况待确认。
- 我的任务。后续用户已拍板短期不做现场人员登录填报，因此第一版隐藏这一项，不显示假用户。

任务卡第一版字段最多：

- 批次。
- 图号。
- 工序。
- 设备。
- 人员。
- 计划开始。
- 计划结束。
- 当前现场状态。
- 实际开始。
- 实际结束。
- 开工偏差、完工偏差。

动作第一版只放：

- 开工。
- 完工。
- 查看记录。

开工和完工弹窗必须包含：

- 反馈人，第一版可空，不能默认写假用户、系统用户或本机用户；为空时最多显示“未填写反馈人”，不阻断保存和报表。
- 实际时间，默认值可以辅助填写，但用户要能看懂。
- 备注，可选。
- 中文确认提示，例如“确认记录这道工序已经开工？”。

Excel 导入仍然属于现场事实写入通道，但它不能抢现场记录首屏。第一版页面里：

- 现场记录页签首屏只显示任务卡和开工、完工、查看记录。
- Excel 模板下载和 Excel 直接导入放到“批量维护”折叠区，默认收起；短期不新建导入预览或二次确认控件。如果历史页面残留任何预览/确认入口，也不能在非正式方案下开放。
- 批量维护区也必须显示同一条写入状态：“当前方案可写现场记录”或“当前只是预览，不能写现场记录”。

每张任务卡要有可展开的“执行记录流水”，至少显示实际开始、实际结束、备注、来源（手填或导入）和记录时间；反馈人可空，空时显示“未填写反馈人”，不能阻断保存。

暂停、继续、报异常、撤销、审批、扫码、消息推送全部作为后续能力，不在第一版按钮里假装可用。误点处理第一版不做撤销按钮，先通过计划员复核或后台修正处理。

### 9.5 写入护栏

- 只有正式采用方案且后端允许时，现场事实写入才可用。
- 模拟预览、候选方案、历史方案显示“只能查看，不能写现场记录”。
- 写入护栏必须覆盖所有通道：开工按钮、完工按钮、手填、Excel 模板下载、Excel 导入、对应 API 和页面上的 `data-*` 写入 URL。
- 非正式采用方案下，前端不下发可用的导入 URL，相关控件禁用，并显示“只能查看，不能写现场记录”；后端也必须拒绝写入。
- 按钮可用性不由前端自己猜，继续以后端 `available_actions` 和 `can_write_feedback` 为准。
- 手填或 Excel 导入成功后，任务卡、任务明细、资源派工甘特都要同步刷新，不能只刷新一块。
- 不可写原因必须拆成中文：当前方案不可写、当前任务状态不可写、后端动作不可用、数据缺口。不能只显示“不可写”。短期不新增多人账号权限。
- 短期不新建 Excel 导入预览或二次确认。Excel 继续直接导入，导入后显示新增、失败、跳过数量和错误提示；如果历史页面残留任何预览/确认入口，也不能在非正式方案下开放。
- Excel 导入成功后必须返回汇总：成功多少条、失败多少条、跳过多少条，并提示已经刷新哪些页面区域。

### 9.6 计划和现场实际复盘

“查看计划和实际”不是写现场记录。它是复盘入口。

这个页面第一版只复盘正式采用方案。原因很简单：现场实际记录来自真实执行，只能对照已经下发执行的正式计划；模拟预览、候选方案、对比参考方案没有真实现场事实，不能进入复盘页。非正式方案下，“查看计划和实际”入口要禁用，并显示“计划和现场实际只复盘正式采用方案，请切换到正式采用方案后查看”。

复盘页首屏建议：

- 上下文条：版本、日期、批次范围。
- 方案口径：固定显示“正式采用方案”，并说明模拟预览和对比参考方案不在这里复盘现场事实。
- 摘要：任务数、未开工、生产中、已完工、异常或偏差。
- 主列表：计划开始、实际开始、开工偏差、计划结束、实际结束、完工偏差、计划资源、实际资源、现场情况状态。
- 每行入口：回到资源派工任务、查看现场记录、定位甘特、查看延期说明。

资源派工不是线性流程的最后一站。它有两条出口：

- 如果用户想核对执行偏差，点“查看计划和实际”进入复盘页。
- 如果用户想看整体风险，点“打开报表中心”，报表中心再进入超期、资源负荷、计划和现场实际或停机影响。

## 10. 报表中心

### 10.1 目标

报表中心不要只是“报表列表”。它要成为风险入口页：用户看完某个数字后，知道该去哪里处理。

### 10.2 首页布局

```text
[标题：报表中心]
[上下文条：最新版本 / 方案 / 时间范围 / 更新时间]
[风险摘要：超期批次数 / 最忙资源 / 现场情况待确认]
[报表入口卡]
  超期清单：看哪些批次晚了，为什么晚，下一步去哪
  资源负荷：看哪些设备或人员太忙，跳资源派工或甘特
  计划和现场实际：看计划和执行偏差，跳现场记录或派工
  停机影响：看停机窗口影响哪些任务
[口径说明：每张表适合回答什么问题，也说明不能证明什么]
```

每张入口卡都要写清楚“能回答的问题”和“不能证明的事情”。例如停机影响报表如果没有停机数据，只能说“当前没有停机记录或尚未维护停机数据”，不能推断“没有停机影响”。

### 10.3 报表明细操作列

报表中心入口卡只解决“从哪里进”。真正避免死胡同，要在明细表里补操作列。

| 明细页 | 新增操作列 | 按钮文案 | 必带参数 |
| --- | --- | --- | --- |
| 超期清单 | 下一步 | 查看为什么晚了 / 定位甘特 / 查看资源派工 | `version`、`plan_role`、`scenario_id`、`batch_id`、`date_from`、`date_to` |
| 资源负荷：设备表 | 下一步 | 查看排班 / 定位甘特 / 查看相关超期 | `version`、`plan_role`、`scenario_id`、`scope_type=machine`、`resource_id`、`date_from`、`date_to` |
| 资源负荷：人员表 | 下一步 | 查看排班 / 定位甘特 / 查看相关超期 | `version`、`plan_role`、`scenario_id`、`scope_type=operator`、`resource_id`、`date_from`、`date_to` |
| 计划和现场实际 | 下一步 | 回资源派工 / 定位甘特 / 查看现场记录 | `version`、`plan_role=adopted`、`batch_id`、`resource_id` 可选、`date_from`、`date_to`；固定正式采用方案口径，不传 `scenario_id` |
| 停机影响 | 下一步 | 定位甘特 / 查看受影响任务 / 查看资源派工 | `version`、`plan_role`、`scenario_id`、停机 `date_from`、停机 `date_to`、资源对象可选 |

导出 Excel 是次要动作，不要放成唯一显眼动作。

“计划和现场实际”明细页是一个例外：它不承接模拟预览、候选方案和对比参考方案，只看正式采用方案。后续测试不要要求它携带 `scenario_id` 或非 adopted 的 `plan_role`；正确断言是 URL 最多携带 `plan_role=adopted`，页面明确显示“正式采用方案”，且非正式方案入口被禁用并给中文原因。

## 11. 跨页流程设计

### 11.1 首页到超期解释

```text
首页：今日待处理“3 个批次会晚于交期”
  -> 超期清单：保留 version、plan_role、scenario_id、date range
  -> 点击批次
  -> 详情区显示事实、线索、缺口、建议动作
  -> 定位甘特或查看资源派工
```

### 11.2 首页到方案对比

```text
首页：今日待处理“有 2 套方案未复核”
  -> 排产分析：保留 version、plan_role、scenario_id
  -> 推荐方案卡
  -> 三方案摘要
  -> 查看方案甘特或资源派工
```

### 11.3 甘特到资源派工

```text
甘特：点击 M-03 上的超期任务
  -> 任务详情区
  -> 查看资源派工
  -> 资源派工自动带入 version、plan_role、scenario_id、date range、query_date、period_preset、scope_type=machine、resource_id=M-03
  -> 如果是模拟预览或对比参考方案，资源派工显示“只能查看，不能写现场记录”
```

### 11.4 资源派工到报表、计划和现场实际

```text
资源派工：任务卡或任务明细
  -> 查看计划和实际：只在正式采用方案下可用；复盘页保留 version、plan_role=adopted、date range、query_date、period_preset、batch_id、scope_type/scope_id 可选
  -> 打开报表中心：报表中心保留 version、plan_role、scenario_id、date range、query_date、period_preset、scope_type、resource_id 可选
  -> 复盘页每行可回到资源派工或甘特
```

### 11.5 报表到计划和现场实际

```text
报表中心：计划和现场实际
  -> 复盘页：只进入正式采用方案口径，保留 version、plan_role=adopted、date_from、date_to、batch_id 可选
  -> 选择偏差行
  -> 回资源派工、定位甘特或查看现场记录
```

### 11.6 报表回到工作台

```text
报表中心：资源负荷 M-03 96%
  -> 资源负荷详情
  -> 查看 M-03 排班
  -> 资源派工或甘特定位同一版本、方案和时间范围
```

## 12. 响应式和视觉规则

### 12.1 宽屏

适合计划员日常电脑，优先目标宽度 1280px 以上：

- 首页：风险卡一行，待处理和最近排产左右两栏。
- 分析页：推荐方案卡在上，三方案卡横排，诊断卡网格。
- 甘特页：第一版做甘特和任务详情左右布局，甘特主区最小高度 420px，详情区约 320px；资源负荷 Top 摘要第二阶段再放到下方二屏。
- 资源派工：查询条件网格，任务明细宽表横向滚动，现场记录任务卡网格。
- 报表页：入口卡 2-4 列，宽表横向滚动。

### 12.2 中窄屏

1024px 左右：

- 详情区放到甘特下方。
- 查询条件减少列数。
- 卡片改 2 列。
- 宽表继续横向滚动，不硬挤。
- 第一版甘特页顺序固定为：简化工具条、甘特横向滚动区、任务详情、折叠筛选说明；第二阶段再在任务详情后追加资源负荷摘要。

### 12.3 小屏

768px 以下：

- 所有左右布局改上下堆叠。
- 按钮允许换行。
- 任务卡优先展示关键字段，更多字段放详情。
- 甘特图保持横向滚动，不把时间轴压成不可读。
- 资源派工顺序固定为：查询条件、摘要、分组标签、当前页签内容；Excel 批量维护仍默认收起。

## 13. 第一版明确降级或暂不做

- 不做甘特拖拽、拉伸、保存、采用、提交正式计划。
- 不做复杂资源负荷直方图；Top 资源摘要放到第二阶段，不进第一版验收。
- 不做批次级、资源级方案变化大明细，先保留跳转入口和空态。
- 不做完整 MES。
- 不做暂停、继续、报异常、撤销、审批、扫码、消息推送；mockup 里的这些按钮第一版不得照抄。
- 不做 AI 自动改计划、一键修复、自动换设备并采用。
- 不做外部 BI、大屏、数字孪生、实时 IoT。

第二阶段可评估，但第一版不强行做：

- 折叠式任务简表：让表格行和甘特条互相高亮。
- 保存视图、恢复默认、清空筛选、共享视图。
- 方案 / 基线甘特叠线对比。
- 甘特模拟沙盒：允许拖动做临时模拟，但不直接写正式计划。
- 甘特 Top 资源摘要：在甘特附近显示最忙设备、最忙人员和容量来源。
- 异常、停机、偏差闭环：属于后续 MES 执行异常能力，不塞进本次 APS 工作台最小闭环。
- 管理者复盘视图或更多角色分工；现场人员登录视图短期继续不做，除非未来产品口径重新拍板。

## 15. 验收清单

### 15.1 页面内容验收

- 首页首屏能看到今日待处理，最多 6 条。
- 首页每条待处理都有标题、影响、证据、动作入口。
- 首页资源高负荷项优先说明能安全算出的受影响批次；如果只能拿到利用率，就说明受影响批次暂时不能判断。
- 分析页先显示推荐、风险和诊断行动，再显示技术过程。
- 分析页方案对比显示与正式采用方案的差值和推荐代价。
- 甘特页点击任务后有稳定详情区，不只靠弹窗。
- 第二阶段做甘特资源负荷摘要时，甘特附近显示 Top 资源压力，无法计算时显示数据缺口。
- 第二阶段做资源负荷摘要时，显示容量来源，包含工作日历、班次、停机扣除情况或数据缺口。
- 资源派工里“看排班”和“计划员代录现场事实”视觉分开。
- 现场记录首屏只有任务卡和开工、完工、查看记录；Excel 批量维护默认收起且受同一写入护栏控制。
- 现场记录不可写时显示明确中文原因，不只显示“不可写”。
- Excel 不做导入前逐行预览；直接导入后显示成功、失败、跳过数量和错误提示。
- 报表中心和报表明细能跳回甘特、资源派工或延期说明。

### 15.2 上下文验收

- 首页跳甘特、分析、资源派工、报表时不丢版本。
- 跨页链接按第 3.4 章矩阵断言版本、方案、模拟预览、日期、批次和资源对象不丢。
- 顶层导航存在“计划工作台”或等价的一跳作业入口，不能只靠页面内部按钮。
- 对比参考方案和模拟预览不会出现现场记录写入入口。
- 现场记录的开工、完工、手填、Excel 模板下载、Excel 导入、对应 API 和页面上的 `data-*` 写入 URL 都不会在非正式采用方案下开放。
- 去甘特时明确设备视图或人员视图。
- 去资源派工时明确人员、设备或班组视角。
- 页面正文、表格、详情区、按钮文案、导出公开列和对外 payload 只显示中文业务名，不显示内部字段；URL 和隐藏域是传参例外。

### 15.3 视觉和浏览器验收

- 关键页面在宽屏、中窄屏、小屏下不重叠。
- 按钮文字不挤出，不遮挡后续内容。
- 宽表可以横向滚动，不把页面撑坏。
- 甘特图不是空白，任务条和详情区不互相遮挡。

| 资源派工到报表 | “打开报表中心” | `version`、`plan_role`、`scenario_id`、日期、资源对象可选 | 报表入口卡保持同一上下文 |
| 报表到计划和现场实际 | 报表中心“计划和现场实际” | `version`、`plan_role=adopted`、日期、`batch_id` 可选 | 复盘页是只读对账，能回资源派工和甘特 |
| 非正式方案到计划和现场实际 | 甘特、资源派工、报表里的复盘入口 | `plan_role`、`scenario_id`、方案中文名 | 入口禁用，显示“计划和现场实际只复盘正式采用方案，请切换到正式采用方案后查看” |
| 现场记录写入护栏 | 现场记录页签和批量维护区 | 正式/模拟/候选/历史方案 | 非正式采用方案下开工、完工、手填、Excel 模板下载、Excel 导入、对应 API 和 `data-*` 写入 URL 都不可用 |
| 首页定位目标页 | 首页任一待处理项 | 批次或资源对象 | 目标页自动定位或高亮同一批次 / 资源；如果无法定位，显示中文原因 |

几何路径以 `tests/ui_geometry_contract_data.py` 最终注册的真实路径为准。本稿列出的路径要作为目标清单，但实现时仍要用真实 Flask 路由核对一次，避免 `/reports/` 和 `/reports` 这类尾斜杠差异造成假失败。

## 16. 用户指南需要同步的说法

后续功能落地后，用户指南要用大白话说明：

1. 早上打开系统，先看首页“今日待处理”。
2. 看到晚交，先点“查看为什么晚了”，不要只看总拖期。
3. 看到方案待复核，先看推荐方案卡，再看三方案摘要。
4. 看到资源过载，去甘特或资源派工看具体设备和人员。
5. 现场记录只能写正式采用方案；模拟预览和对比参考只能看。
6. 报表不是最后一站，看完报表可以回到甘特或资源派工继续处理。
