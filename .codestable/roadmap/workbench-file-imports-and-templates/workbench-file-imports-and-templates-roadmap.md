# 工作台文件导入导出补全与模板统一

## 1. 背景

工作台现在有 9 张可导入的表，分属 5 个文件家族：批次、现场报工、物料、资源四类（工种、设备、人员、供应商，其中工种按自制与外协两个类别分别下载和导入）、工艺两类（工艺路线、工序工时）。全部走"上传预检 → 确认写入"两步，整批原子提交，导入模式一律是增量更新。

2026-09-18 旧路由层整体删除时，挂在旧页面上的三张导入表连带失去了文件入口：

| 旧模板 | 现状 |
|---|---|
| 人员设备关联.xlsx | 只能在人员详情页逐人勾选"可操作设备"（`web/routes/workbench/operator_machine_permissions.py:62-65`） |
| 工作日历.xlsx | 只剩日历页的单日编辑和按日期范围批量改（`frontend/workbench/app/ResourceCalendar.jsx:64-73`） |
| 人员专属工作日历.xlsx | 工作台完全不接受写入（`web/routes/workbench/calendars.py:9-10` 明示不收人员标识），旧库数据只是继续被排产读取 |

对现场的影响：几十人对几十台设备的授权关系要逐人在详情页点，第一次建资料成本很高；请假、加班、临时只排急件这类个人日历安排没有任何写入口。

另有两处历史遗留同时要收口：启动时仍会生成 11 张旧模板到 `templates_excel/`（`web/bootstrap/factory.py:217-233`，条目定义在 `core/services/common/excel_template_defaults.py`），没有任何路由下发且列头与现行合同不符；系统使用说明第 1 章（`static/docs/scheduler_manual.md:147-625`）教的仍是旧路由层的"批量维护卡片"那套，其总表列出 10 张模板（正反两张关联表合并成一行）。

三张表补回后共 12 张可导入表。本 roadmap 同时把 12 张的模板形态统一为"一份文件、两张工作表"，并重写用户文档。

## 2. 范围与明确不做

### 本 roadmap 覆盖

- 人员设备关联（界面称"可操作设备"）的文件导入、导出、模板下载，入口在人员列表页
- 全局工作日历的文件导入、导出、模板下载，入口在日历页
- **全局日历一致性校验的前置修复**，见 4.4，这是现存缺陷，不修则日历文件导入不可用
- 个人工作日历的工作台写入能力（服务、路由、人员详情页编辑面板，含按日期范围清除）与文件导入导出
- 共享文件弹窗新增两个向后兼容的扩展点，让日历家族能用日期范围而不是三档勾选
- 12 张导入表的模板统一为"第一张数据表加第二张填写说明表"，枚举列加下拉
- 四个读取器统一为"读第一张工作表，其余忽略并提示"
- 系统使用说明第 1 章按工作台现行合同重写，新增导出表列含义一节
- 退役 `templates_excel/` 启动期生成与旧 Excel 页说明视图模型
- 模板表头、填写说明、用户文档三者一致性的门禁

### 明确不做

- **设备人员关联（反向列序表）**：和人员设备关联是同一份关系，只是前两列对调。旧说明书专门写过"不要混用两张表的列顺序"的提醒，保留一张反而更不容易出错。
- **通过文件删除记录**：全部 12 张表的文件导入一律只做增量更新，文件里没有的记录不动。删除通道走界面：解除设备授权在人员详情页，清除全局日历配置用日历页已有的范围维护，清除个人日历配置用第 3 条 feature 新增的个人日历范围清除。理由见 4.3。
- **清空本类数据后重导**：工作台现有全部文件家族只支持增量更新模式，新家族沿用。
- **改动现有日历的单日与范围维护的界面**：只修 4.4 那条校验缺陷，字段、文案、交互都不动。
- **导出专用表的回导**：计划、候选、报表、校准、实际甘特、系统日志这些只导出不导入的表继续只读，只在文档里补列含义。
- **把 Excel 当数据库备份**：沿用现有合同，参考列不恢复系统时间与既有授权关系。
- **班次档案与设备组的文件导入**：旧系统也没有模板，继续走目录编辑器。
- **Win7 真机打包与发布验证**：不在本 roadmap 范围。

## 3. 模块拆分（概设）

```
工作台文件导入导出补全与模板统一
├── 模块 A：人员设备关联文件家族（新增）
├── 模块 B：日历文件家族与个人日历写入能力（新增，含一处现存缺陷的前置修复）
├── 模块 C：模板与填写说明生成（改造 12 张表）
└── 模块 D：用户文档与旧件退役（改造）
```

**为什么 A 和 B 分开**：人员设备关联是关系表，主键是两个编号的组合，没有日期与时间列；日历是按日期的配置表，有日期、时间、效率这些专属校验，个人日历只是全局日历多一个人员维度。把两者的列定义与取值校验塞进同一个模型文件会得到一个低内聚的大文件。现有 5 个家族本来就是各自独立实现字节编解码（`facts/file_codec.py`、`material/file_codec.py`、`process/file_codec.py` 三份互不共享），新增两个独立家族符合现状架构。共享的是规则而不是代码，规则一致性由 4.5 与 4.11 的契约加测试保证。

### 模块 A · 人员设备关联文件家族

- **职责**：把"谁能操作哪台设备"这张关系表接进现有"预检 → 确认"文件体系，并接上人员列表页入口。
- **承载的子 feature**：`wbfile-operator-machine`
- **触碰的现有代码**：新增 `core/models/workbench_relation_file.py`、`core/services/workbench/relation_files/`、`web/routes/workbench/relation_files.py`、`frontend/workbench/app/RelationFileContract.js`；底层写入复用 `core/services/personnel/operator_machine_service.py` 的 `add_link / update_link_fields`；前端复用 `ResourceFileActionFlow` 并为它新增两个扩展点。

### 模块 B · 日历文件家族与个人日历写入能力

- **职责**：修掉全局日历的一致性校验缺陷，为两张日历表提供文件能力，并补齐个人日历在工作台里缺失的写入服务与编辑界面。
- **承载的子 feature**：`wbfile-calendar-consistency-fix`、`wbfile-work-calendar`、`wbfile-operator-calendar-editing`、`wbfile-operator-calendar-file`
- **触碰的现有代码**：修 `core/services/workbench/resource/calendars.py` 的 `_check_proposed`；新增 `core/models/workbench_calendar_file.py`、`core/services/workbench/calendar_files/`、`web/routes/workbench/calendar_files.py`、`core/services/workbench/resource/operator_calendars.py`、`frontend/workbench/app/CalendarFileContract.js` 与 `OperatorCalendarPanel.jsx`；底层写入复用 `core/services/scheduler/calendar/admin.py`。

### 模块 C · 模板与填写说明生成

- **职责**：把"模板等于表头加单元格批注"改成"模板等于数据表加填写说明表"，统一 12 张表的说明来源，并让读取器接受用户回传带说明表的文件。不改任何行级业务校验。
- **承载的子 feature**：`wbfile-template-unification`
- **触碰的现有代码**：5 个写入器与 4 个读取器的工作表判定。

### 模块 D · 用户文档与旧件退役

- **职责**：把用户看到的文字收敛到一处事实源，清掉会误导用户的旧模板文件与旧页面说明。
- **承载的子 feature**：`wbfile-manual-and-legacy-retirement`
- **触碰的现有代码**：`static/docs/scheduler_manual.md`、四份旧 Excel 页说明视图模型、`web/bootstrap/factory.py:217-233`、`core/services/common/excel_templates.py` 与 `excel_template_defaults.py`。

## 4. 模块间接口契约（架构层详设）

本节是各子 feature design 的硬约束输入。要改先回 `cs-roadmap update`。

### 4.1 两个新文件家族的 HTTP 路由

现有 `/api/workbench/v1/imports/<kind>/preview` 已由资源家族占用，其 kind 校验走 `action_kind()`（`core/models/workbench_resource_action.py:11-17`），该白名单同时服务资源实体的批量删除路由，新家族**不得**扩它。改用独立前缀，形状照抄工艺家族：

```
模块 A：/api/workbench/v1/relation-files/operator_machine/{preview,confirm,template,export-preview,export}
模块 B：/api/workbench/v1/calendar-files/<kind>/{preview,confirm,template,export-preview,export}
        <kind> ∈ ("work_calendar", "operator_calendar")
```

kind 一律用下划线，与资源家族既有的 `op_type` 一致，使 URL 段、前端 kind、`operation` 前缀、会话存储命名空间四处同名。

**请求形状**（严格相等校验，多一键少一键都 `invalid_input` 400）：

```
preview:   multipart, files == {"file"}（恰好 1 个），form == {"format","mode"}
           format ∈ ("csv","xlsx")；mode == "upsert"
confirm:   JSON, 顶层 == {"request_key","write_token","input"}，input == {"preview_ref"}
export:    query == {"export_ref","format"}
template:  query == {"format"}
```

**export-preview 请求体两个家族不同**：

```
模块 A（人员页有列表和勾选，沿用资源家族语义）：
  必填 {"selection","scope","snapshot_ref"}，可选 {"refs","page_size"}
  selection ∈ ("all","filtered","selected")；"refs" in body ⟺ selection == "selected"
  scope 允许键与 core/models/workbench_resource_action.py:22 完全一致
  即 {"query","status","category","sort","direction","column_filters"}，服务端忽略排序键但必须接受
  这一条是硬性的：共享 contract 的 listContext 总会带 sort 与 direction（ResourceMaterialContract.js:65-67），
  收窄键集会让"当前筛选结果"这一档必然 400

模块 B（日历页没有列表也没有勾选，三档选择无意义）：
  必填 {"range","snapshot_ref"}，可选 {"scope","page_size"}
  range == {"start_date","end_date"}，均为 YYYY-MM-DD，起止同日合法，跨度上限 3 年
  operator_calendar 额外可选 scope.operator_refs（数组，省略或空数组表示全部人员）
  snapshot_ref 绑定的是该日期范围的状态指纹，不是月视图指纹，需新增一个按范围的读快照入口
```

**preview 与 export-preview 的响应**必须满足共享 contract 的校验，否则前端直接判为不完整：

```
preview data：{preview_ref, expires_at, operation, commit_policy:"atomic", summary, rows,
               can_confirm, write_context, columns, scope, file_sha256, format, mode,
               template_version, instructions}
               operation = "<kind>.import"
export-preview data：{export_ref, expires_at, row_count, formats, selection | range}
               formats 必返且为 ("csv","xlsx") 的子集，前端下载前会检查当前格式在不在里面
               模块 A 回显 selection，模块 B 回显 range
confirm 回执：{"ok":true,"result":"committed"|"unchanged","data":{"rows":[...],"summary":{...}},
               "receipt_ref","replayed":bool}
               data.summary 必须存在，否则前端只显示"已查到上次操作的完成结果"而不是确认成功
```

**错误码**：`invalid_input` / `entity_not_found` / `constraint_conflict` / `stale_write` / `snapshot_stale` / `request_key_conflict` / `storage_failure`。模块 B 若采用日历现有的进程内预检存储，还会出现容量超限的 `preview_capacity` 503（`web/routes/workbench/calendars_preview.py:19-20,38-40`），选型见 4.6。行级错误对象固定 `{row, field, code, message}`。

**响应头**：模板与导出都带 `X-Workbench-Row-Count` 与 `Cache-Control: no-store`；导出另带 `X-Workbench-Snapshot-Ref`、`X-Workbench-As-Of`。

### 4.2 文件列目录与表描述协议

资源家族 `core/models/workbench_resource_file.py:9-48` 现有的集合是 `IMPORT_ROW_LIMIT` / `TEMPLATE_VERSION` / `WRITABLE` / `READONLY` / `LABELS` / `MULTI_CODES` / `JSON_FIELDS` / `NUMERIC_FIELDS` / `NULLABLE` / `RELATIONS` / `INSTRUCTIONS`，加 `file_columns(kind)` 与 `public_columns(kind)` 两个函数。

新家族沿用其中的 `WRITABLE` / `READONLY` / `LABELS` / `NUMERIC_FIELDS` / `NULLABLE` / `IMPORT_ROW_LIMIT = 2000` / `TEMPLATE_VERSION = 1` 与两个函数；不需要 `MULTI_CODES` / `JSON_FIELDS` / `RELATIONS`；新增资源家族没有的四个集合：

```
REQUIRED:    Dict[str, Tuple[str, ...]]   # 必填列，资源家族靠读取器硬编码，新家族按 kind 声明
ENUMS:       Dict[str, Tuple[str, ...]]   # 枚举列的中文取值，模板下拉的唯一来源
DATE_FIELDS: FrozenSet[str]
TIME_FIELDS: FrozenSet[str]
```

三张表的列定义。可写列的列名与枚举值逐字沿用旧模板（`core/services/common/excel_template_defaults.py:29,120,132`）；只读参考列是新增概念，其中"人员姓名"旧模板里叫"姓名"，这里为与"设备名称"对仗改用全称：

| kind | 可写列 | 只读参考列 | 必填 |
|---|---|---|---|
| operator_machine | 工号、设备编号、技能等级、主操设备 | 人员姓名、设备名称 | 工号、设备编号 |
| work_calendar | 日期、类型、可用工时、效率、允许普通件、允许急件、说明 | 班次开始、班次结束 | 日期 |
| operator_calendar | 工号、日期、类型、班次开始、班次结束、可用工时、效率、允许普通件、允许急件、说明 | 人员姓名 | 工号、日期 |

全局日历的班次开始与结束设为只读参考：旧的全局日历模板没有这两列，工作台界面也不暴露，但库里有值且会参与 4.4 的一致性校验，导出时带出来供用户核对。个人日历这两列可写，因为旧的个人日历模板本来就有，"假期加班填班次结束反推工时"是它的真实用法。

**预检行的键集**。共享预检组件对行结构有硬要求（`ResourceMaterialContract.js:31-37`、`ResourceMaterialPreview.jsx:39-49`）：`row / business_code / action / result / before / after / changes / errors / requires_confirmation / reference_count` 必须齐全，`reference_count` 即使无意义也要返回 0。两张日历表的主键不是单一编号，`business_code` 的取值必须定死：全局日历用日期文本，个人日历用"工号 / 日期"的拼接串，不能留空（留空会显示成"编号无效"）。

**表描述协议**。模块 C 的模板生成器对 12 张表一视同仁，每个家族的列目录模块必须导出一个统一形状的描述函数，这是模块 C 唯一依赖的入口：

```python
def table_descriptor(kind: str) -> Dict[str, Any]
# {"table_id", "display_name", "sheet_name", "file_stem",
#  "columns": [{"key","label","required","readonly","value_hint","error_hint","enum","nullable"}],
#  "general_rules": Tuple[str, ...], "sample_rows": Tuple[Tuple[Any, ...], ...], "row_limit": int}
```

现有 5 个家族也要补上这个函数，由 `wbfile-template-unification` 统一完成。

**个人日历的行数提示**：个人日历只需要填有特殊安排的日期，正常上班的日子不填。这条必须出现在模板说明表与用户文档里，否则用户按"每人每天一行"填写，一年就会超出 2000 行上限。

### 4.3 写入语义：一律增量更新，不做删除

三张新表与现有 9 张表一致，文件导入只做增量更新：文件里出现的记录新增或更新，**文件里没有出现的记录一律不动**，任何情况下都不会因为"文件里没写"而删除数据。

这条推翻了一个看起来更省事的做法。人员设备关联在界面上是"按人整表保存"（`core/services/workbench/resource/operator_machine_permissions.py:46-117`），把这个语义搬到文件导入会得到"按工号分组整表替换"，即文件里列了某工号就重建该工号的全部授权。三个问题：用户只想加一台设备却会删光其他授权；与全部 11 张现有表不一致；旧系统也没有这一档语义（它是更新已有、只导新增、全表清空重建三种）。

因此模块 A 的确认逻辑自己实现增量写入，底层调用 `OperatorMachineService.add_link(..., preserve_unchanged=True)` 与 `update_link_fields`，**不复用** `WorkbenchOperatorMachinePermissions.confirm` 的整表替换路径。

**原子性可以保证，但有两个坑**。`add_link` 内部自带事务（`operator_machine_service.py:322`），在外层事务里退化为保存点，异常向外抛，由 `WorkbenchCommandService` 的写事务整体回滚，第 5 行失败前 4 行不会落库。坑在于：一是底层抛出的业务异常经统一映射后是整批级错误，没有行号，所以行级错误必须全部在预检阶段产出，确认阶段只做文档比对；二是底层的报错文案含被词表禁用的词（如 `:316` 的"无需重复添加"），而 `core/services/personnel` 不在文案扫描范围却会原样透给用户，模块 A 要在自己的边界上把这类文案转成合规说法。

**主操唯一的连带影响必须在预检算准，并在确认时用当前值而不是预检快照值**。这是本模块最容易写错的地方：

- `add_link` 与 `update_link_fields` 在写入"是主操"时会调 `_clear_primary`（`:328-334`），把该人其他设备的主操标记改为否。
- 文件的主操列可以留空，但 `update_link_fields` 要求必须传入该项。**缺列时的取值必须在写入时刻从库里现读，不能用预检时的快照值**。反例：文件两行，第一行把设备甲设为主操，第二行只改设备乙的技能等级且主操列留空，而库里设备乙当前是主操。按行序写入时第一行已经把乙翻成否，第二行若仍传预检时读到的"是"，会把甲又翻回否，最终结果与预检承诺相反。
- **结果为不变的行完全不调用底层写入**，否则会对当前主操行重复写入并两次推高版本号。
- 同一个人的多行按"主操为是"的行最后写。
- 预检时，凡"库里当前是主操、且在文件中出现但主操列留空"的行，结果要标成更新（是变否），不能标成不变。
- 设为主操的那一行要带一条行级说明，写明确认后哪台设备将不再是主操，同时 `requires_confirmation` 置真。
- 同一人在文件里出现多行主操为是，预检直接拒绝。现成判定逻辑可参考 `core/services/personnel/operator_machine_import_helpers.py:67-70`。
- 判定"当前是否主操"必须经过归一化（`operator_machine_normalizers.py:63-77`），否则库里的历史脏值会被漏算。

预检行结构为此新增一个可选字段 `notes: List[str]`，前端在附注行渲染，没有该字段的家族行为不变。

### 4.4 全局日历一致性校验的前置修复（阻塞项）

**这是一处现存缺陷，不修则日历文件导入不可用。** 复审时实测确认（内存库装载 `schema.sql` 后走 `CalendarAdmin` 与 `WorkbenchCalendarService`）：

| 操作 | 结果 |
|---|---|
| 首次把某天存成 8 小时工作日 | 成功，库里自动派生出班次起止 08:00 到 16:00 |
| 把同一天改成 10 小时 | **被拒**，提示"按原班次起止算出 8 小时，和你填的 10 小时对不上" |
| 只改效率（对照组） | 成功 |
| 把某天存成休息后再改回上班 8 小时 | **被拒**，提示"这一天没改的项会被规则改写" |

成因：`core/services/scheduler/calendar/admin.py:98-115` 在保存工时时会把推导出的班次结束写进库；之后任何只改工时的修改，`core/services/workbench/resource/calendars.py:168-181` 的 `_proposed` 会把库里旧的班次起止与新工时合并，再由 `:186-189` 判定工时与班次起止不符而拒绝；休息转工作则触发 `:190-193` 的"未改项被规则改写"。

影响范围：单日编辑与范围批量维护走同一条校验链（`apply` 在 `:214` 调 `_proposed`，`_proposed` 在 `:181` 调 `_check_proposed`），所以两条路径都中。现有测试只覆盖了带显式夜班的行，没有覆盖"界面保存过的普通工作日改工时"这个最常见的场景。

**修复方向**：一致性校验只应针对用户显式给出的班次起止。修 `_check_proposed`，当本次修改没有显式提供班次起止时，把由工时派生出的班次起止视为派生值排除在两项比较之外；显式提供时保持现有严格校验。修复必须补测试覆盖上面四种场景，且不得放宽"显式填了班次起止又填不一致工时"这一真实冲突的拒绝。

**日历文件导入依赖这条修复**：年度日历回导必然大量触发上述两种场景，而提交策略是整批原子，一行被拒整批不能确认。

这一缺陷独立于本 roadmap 存在，建议同时按问题修复流程单独立项留痕，但修复动作放在本 roadmap 第 1 条执行，作为日历文件导入的前置。

### 4.5 取值规则：日期、时间、枚举、清除标记

- **日期列**同时接受文本与 Excel 日期单元格，行为必须与 `core/services/common/excel_validators.py:58-84` 的批次日期校验等价：接受日期与日期时间对象、接受两种分隔符的文本、拒绝带时间的文本、拒绝不存在的日期。新家族自行实现而不直接调用该函数，因为它的错误文案含被词表禁用的词且所在目录不在扫描范围；必须有测试锁住两者对同一输入给出相同判定。
- **时间列**接受 `HH:MM` 文本与 Excel 时间单元格，秒必须为零。
- **枚举列**取值：技能等级 `初级 / 普通 / 熟练`；主操设备、允许普通件、允许急件 `是 / 否`；类型 `工作日 / 假期`。落库映射分别在 `core/services/common/normalization_matrix.py:43-58`、`:38-41`、`:28-36`，存储取值在 `core/models/enums.py:140` 与 `:131`。历史脏值只在"与原值相同"时放行。
- **清除标记 `\N`** 语义与现有家族一致：只能清除可空列的值，不能删除整行。日历的"类型"列不可清除，填 `\N` 直接拒绝该行并提示改用界面的范围清除。所有用户可见文本里出现 `\N` 时必须带"（大写）"说明。
- **默认值**沿用领域层（`core/services/scheduler/calendar/admin.py:117-162`）：类型留空按工作日；工时留空工作日 8.0、假期 0.0；效率留空工作日 1.0、假期取排产配置里的假期效率；允许普通件与急件留空按是。
- **假期能否有工时必须定死**。领域层允许假期带工时（这正是旧模板"假期加班"的用法），但工作台的界面输入模型会把休息强制成 0 工时且两个优先级为否（`core/models/workbench_calendar.py:74-82`），而公开投影又会把"假期且有工时"显示成工作日（`web/routes/workbench/calendars_projection.py:17-19`）。三处口径不一致。本 roadmap 的裁决：**文件导入允许假期带工时**，因为旧模板支持且现场有假期加班的真实需求；相应地，文件家族不复用界面的输入模型，直接走领域层构造，并在 4.15 的一致性清单里记明"文件能存的假期加班，在单日弹窗里原样保存会被改写成工作日"这一已知差异，由第 2 条 feature 决定是同步修界面还是在文档里写明。
- **类型留空时的默认要按日期判定**。`_proposed` 对库里没有行的日期会先取该日期的默认规则（周末是假期且两个优先级为否），再合并文件给的项。所以周六只填 4 小时会存成"假期 4 小时且不可排产"。这个行为要么定死并写进说明表，要么在预检里显式提示，不能让用户自己撞。

### 4.6 导出范围、预检存储与并发守卫

**导出范围**：模块 A 沿用资源家族的三档范围，界面复用现有单选组。模块 B 用日期范围，起止日期两个输入框加一个"当前整月"快捷按钮，个人日历再加人员范围，默认全部人员。跨度上限 3 年。

**预检存储选型**。日历现有的进程内预检存储有 32 份、约 73000 天的容量上限，超出返回 `preview_capacity` 503；资源家族的上下文存储无上限但会把上传的文件字节在内存里留 15 分钟。模块 B 必须二选一并写进 design：选前者要把 `preview_capacity` 加进错误码集合并在前端给出可操作提示，选后者要评估 16 MB 文件驻留内存的影响。模块 A 直接沿用资源家族的做法。

**并发守卫**。现有文件家族的真正守卫是"确认时重跑预检并逐字节比对文档"加"写令牌绑定预检意图哈希"，而不是单一版本号。因此新家族的预检文档必须嵌入足够的事实，否则预检后的并发改动会漏检：

- 模块 A 的预检文档至少要嵌：涉及的每个人员的身份编号与版本号、每台设备的身份编号与版本号、以及**这些人员当前的全部授权原始行**（因为主操连带会改到文件里没提的行）。缺最后一项，别人在预检后改了主操就检不出来。
- 模块 B 的日历没有版本号求和机制，只有逐日的身份修订号加确认时全量重算。按日期范围的读快照指纹需要新增，4.1 的 `snapshot_ref` 才有东西可绑。
- 注意人员设备关联的变化会通过触发器同时推高人员与设备两个实体的版本号（`schema.sql:860-868`），所以关联导入后人员列表与设备列表的读快照都会失效，这是正确行为。

### 4.7 预检与确认的性能约束

- **预检不得按行取实体快照**。资源家族的单实体快照函数每次要十几到几十次查询，2000 行逐行调用会产生数万次查询。新家族必须先对文件里出现的编号去重，再用批量映射一次性解析（可参考 `data/repositories/operator_machine_repo.py:48-61` 的批量接口与 `core/services/workbench/facts/` 下的分块映射），人员、设备、现有关联各取一次全量或分块映射。
- **日历预检的配置读取要提到循环外**。假期行的默认效率来自排产配置，逐行读会产生每行一次配置查询。
- **确认阶段可接受逐行写入**。底层每行约四到六次查询，2000 行在单机 SQLite 上可接受，现有界面路径已是同量级。

### 4.8 模板文件结构

XLSX 模板与导出文件固定两张工作表：

```
第 1 张 数据表    sheet 名取自表描述协议
                 第 1 行表头加粗、冻结首行、自动筛选
                 枚举列加下拉
                 模板不含示例数据行
第 2 张 说明表    sheet 名固定 "填写说明"
                 表头 ["列名","必填","能填什么","会报错的情况"]，逐列一行
                 其后追加"通用规则"分节与 2 至 3 行完整示例
```

说明表内容由统一生成器从表描述协议产出，不允许各家族各写一份说明文字。单元格批注保留但收敛为一句示例值。批次模板现在会往数据表写一行示例（写出逻辑 `core/services/workbench/batch/file_codec.py:94-101`，示例值由路由从旧模板定义取来），这一行移入说明表，数据表留空。

CSV 没有第二张工作表的位置，只输出表头行，与现状一致；说明由前端弹窗提示与用户文档承载，文案与说明表同源。

导出文件同样带说明表，让"导出改完再回导"的用户能看到规则；回导时第二张表按 4.9 被忽略。这会让既有验收记录里"导出文件只有一张数据表"的描述过时，相关断言需在该条 feature 内同步更新。

### 4.9 读取器对附带工作表的处理

现状三种行为并存：物料、资源、工艺要求恰好一张工作表，多一张整份拒绝；批次读第一张并发提示；报工直接解析第一张不检查数量。

统一为**最宽松的那一档**：读第一张工作表作为数据表，其余工作表一律忽略；存在其余工作表时在预检结果里追加提示。不采用"只忽略填写说明表、其余拒绝"的收紧方案，那会让批次与报工从允许多表变成拒绝多表，用户手里第二张表放着自己备注的现有文件会突然导不进去。

其余字节级规则一律不变，各家族保持各自现状，两处差异要特别注意：

- **布尔拒绝不是全家族规则**。只有批次的数量列、报工的单元格、工艺路线显式拒绝布尔值，物料与资源的解码器不做这个判定。
- **写出方式分两派**。资源、物料、工艺用只写工作簿加临时文件加写出器清理的 openpyxl 3.0.10 写法；批次与报工用普通工作簿加内存缓冲。新增说明表时各自沿用本家族的写法。

### 4.11 入口位置与表选择层

| 页面 | 变化 |
|---|---|
| 人员列表页 | 工具栏按钮数量不变，点"导入"或"导出"后先选表：人员清单 / 可操作设备 |
| 日历页 | 工具栏新增"导入""导出"两个按钮，点击后先选表：工作日历 / 个人工作日历 |

| 其他资源页 | 只有一张表，选择层不渲染，行为逐字节不变 |

**为什么用表选择层而不是每张表一对按钮**。上一版打算照工艺页平铺，实测行不通。按现有令牌估算，1280 宽度下资源工作区工具栏可用内宽约 958 像素，左侧搜索与筛选已占 580 到 610 像素；人员页若平铺六个带表名的按钮需要约 704 像素，必然换行，连只改文案的物料页都会从一行变两行。日历页的工具栏在两栏网格的左列里，可用内宽只有约 664 像素，现有五个控件已占约 450 像素，再加四个按钮会变成两到三行。

同时要纠正上一版一个空判据：上一版说"以 1280 档的几何检查结果为准"，但人员页与日历页根本不在界面证据的视图矩阵里（矩阵里的基础资料视图默认落在物料页），而七项几何检查没有一项测量工具栏行数。这个判据永远不会触发，不能作为决策依据。

表选择层是一个轻量组件：宿主在打开导入或导出时，若该页有多张表则先渲染选择层，选定后再渲染既有弹窗流程；只有一张表时直接透传。它不改弹窗流程组件内部，也不改其他资源页的行为。

**用词统一**。上一版用的"设备授权"与现有界面冲突：界面上这个对象叫"可操作设备"（`OperatorMachinePermissions.jsx:73`、`ResourceForms.jsx:32,196`），而"设备授权"在现有界面专指只读的历史授权（"既有设备授权（只读）"、参考列"原设备授权（只读）"）。叫"导入设备授权"等于在导入那个页面明说不导入的东西。统一用"可操作设备"，表的显示名也用它，文件名用"可操作设备清单"。实测这些文案不命中词表禁用词。

图标只用已注册的键：导入 `file-input`，导出 `file-output`，日历 `calendar-days`（没有 `calendar`）。不需要新增图标。

会话存储键是每命名空间一个，同页两张表不会互相覆盖。恢复态读取对坏数据是抛错而不是返回空，且宿主不捕获，多三个键就多三处"一条坏记录卡住整页"的面，新家族要在读取处加容错。

**日历页弹窗的请求协议**。日历页没有列表查询，弹窗需要的生产数据标记与读快照编号必须由日历页从月视图结果里取出传入，否则弹窗会显示"尚未读取生产资料"且确认按钮被锁死，导出预检也会因缺少快照编号而被拒。日历页要传的是 `{refs: [], scope: {source, snapshot_ref}, month, onCommitted}`，其中前两项取自月视图响应的元数据，`onCommitted` 接月视图的重新读取，否则导入成功后月历不刷新。实现方式用现有的适配器能力协议（宿主已挂好的 `openImport`、`openExport`、`supports`），由 `renderCalendar` 多传一个基础适配器，不发明新的回调形状。

### 4.13 个人日历面板的写入契约

个人日历面板是本 roadmap 唯一没有任何前端先例的组件，它的写入通道在现有传输层里不存在，不定义就做不出来：现有意图校验只认人员加设备权限、全局日历、资源增删改、文件导入五类，日历适配器的命令只接受全局日历的三个动作，后端也明示不收人员标识的日历写入。

契约照抄"编辑可操作设备"这条已跑通的链路：

```
意图形状   {kind: "operator", action: "calendar_upsert" | "calendar_delete" | "calendar_range_clear",
            ref: <人员编号>}
           kind 保持 operator 有两个必要作用：一是让意图校验的现有人员分支可扩展，
           二是让保存后的刷新逻辑（ResourceWorkspace.jsx:219-242 按 intent.kind 查节点）能正常工作
路由       POST /api/workbench/v1/entities/operator/<ref>/calendar/{preview,confirm}
           形状照 machine-permissions 的两段式，请求体与回执字段同构
能力声明   人员详情的写上下文能力里新增 operator.calendar，
           否则界面侧的阻塞判定没有依据（先例是 operator.machine_permissions）
前端改点   resource-api.js:104-105 的人员分支加新动作
           resource-api.js:157-163 的命令映射加分支，指向 entities/operator/<ref>/calendar/confirm
           ResourceForms.jsx:182,195-196 加按钮与回调
           ResourceWorkspace.jsx:294-297 加渲染分支与动作排除表
```

**面板必须提供按日期范围清除**。这是 4.3"不做文件删除"能成立的前提：全局日历有日历页的范围清除兜底，个人日历现在没有任何删除入口，界面上也明写"人员专属日历不变"。若只做单日编辑，用户导错一年的个人日历需要逐日清理，唯一的批量出路是删人让数据级联消失。范围清除的交互照 `CalendarRangeDialog.jsx:72` 的"清除配置，恢复默认"那一档。

**可复用与必须新写的清单**：离开保护、日历字段编辑组件、日历契约的标记与草稿函数可复用；个人表可写的班次起止两项现有字段组件没有，要扩展；月历网格是页面内联结构不是独立组件，要抽出或复制；单日对话框硬绑全局日历的路径、命令与阻塞判定，不参数化不能用；月视图与单日响应的校验函数校验的是全局日历的形状，个人日历响应要么同形要么另写校验。

**个人日历会整体绕过班次轮换**。排产引擎读到个人日历行时不再叠加班次档案，界面必须把这一点告诉用户，否则设了个人日历的人当天班次表静默失效。

### 4.14 预检展示

预检明细复用 `ResourceMaterialPreview`，它已提供五态汇总条、按结果筛选的下拉、修改前后两列对比、错误与需确认的附注行、每页 20/50/100 的客户端分页，日历一年三百多行由现有分页承载。

需要的改动与注意点：

- **渲染 `notes`**。附注行当前只在有错误或需确认时渲染（`:45`），条件要并上 `notes` 非空。`notes` 的类型校验由新 contract 自己做，共享校验不检查未知字段，传错类型会渲染出空值。
- **去掉硬编码的设备权限提示**。"设备权限需在人员详情设置"在源码里有三处：`ResourceMaterialPreview.jsx:35`、`ResourceFileContract.js:64`、以及后端的 `core/models/workbench_resource_file.py:47`（它是通用规则文案，会进模板说明表，且在文案扫描范围内）。三处一起改。没有测试断言这句话，但它出现在五个资源页的导入弹窗里，界面证据会变。
- **结果标签取自全局而非 contract**（`:32-33,42`），这也是要求新 contract 与共享 contract 同形的原因之一。
- **其他硬编码**：表头"关联数"对日历无意义但必须返回 0；文件行的副说明写死"按编号增量更新"，对按日期键的表不准确；弹窗标题是"批量导入 · 表名"，与工具栏按钮文案要对齐。这些在新家族落地时一并处理。

### 4.15 界面与文件两个入口的一致性

人员设备关联和个人日历都有界面与文件两个入口，必须能存同一个集合。已查到的现存不一致，在第 1 条与第 3 条 feature 内收口：

- **取值措辞冲突**：界面用"初级 / 普通 / 熟练"和"主操设备 是 / 否"；资源文件的显示映射把技能等级只认一个值显示为"普通"，主操显示为"主要 / 非主要"。统一采用界面那套中文，并修正资源文件的显示映射。
- **变化结构冲突**：界面的每项变化是两元数组，文件家族是带修改前后两个键的对象。新家族一律用对象形式，界面那处不动。
- **资格过滤会让导入成功的授权进不了资源池**。排产的资格服务会丢掉"人员已声明技能且不含该设备工种"的关联，而现有的关联问题提示只报脏值不报这种情况。文件预检必须复现这个判定并提示，否则用户以为导入没生效。
- **假期带工时的口径差异**见 4.5，要么同步修界面，要么在文档里写明。

此外要由共享校验保证并有测试锁住：可选设备的集合与过滤条件（界面走选择器接口、文件走编号解析，必须同源）、人员停用时能否编辑、主操唯一约束及其连带、取值域、错误文案。测试必须覆盖"界面能存的文件也能存，界面存不了的文件也存不了"。

### 4.17 模板与文档的一致性门禁

用户文档第 1 章里每张表的列说明表格由工具从表描述协议生成并写入标记区间，不由人手写。门禁跑生成并与文件内容比对，不一致就失败并提示重新生成。散文段落人工撰写，不进门禁。这样做而不是"人写文档、测试解析表格比对"，是因为后者格式微调就会误报。

另外两项：模板说明表的行数与列名必须与列目录逐项相等；模板下拉的取值必须能被归一矩阵解析回合法枚举。

## 6. 排期思路与验证约定

### 排期

第 1 条是缺陷修复，独立且小，放最前，因为它阻塞第 3 条且本身就值得先修。

第 2 条选可操作设备作最小闭环，它是三张表里对首次建资料影响最大的一张，而且前端的四处接线、两个共享扩展点、表选择层都随它落地，后面几条才能复用。

第 3 到第 5 条是日历。全局日历在前，因为个人日历的行校验与取值规则是它的超集，只多一个人员维度。个人日历拆成界面编辑与文件导入两条：它是唯一在工作台既没有服务、也没有任何可照搬界面、写入通道还要从零定义的一张，界面编辑本身也有独立价值。

第 6 条模板统一必须等前面列目录定稿，否则会返工。第 7 条文档收尾放最后，旧模板退役也放这里，避免中途删掉后用户既看不到旧模板也拿不到新模板。

**依赖的真实强度**：第 2 条对第 1 条无依赖，可并行；第 3 条对第 2 条只是前端复用。真正的硬依赖是第 3 条对第 1 条、第 4 和第 5 条对第 3 条、第 6 条对前面的列目录、第 7 条对第 6 条。不建议并行推进，因为多条都要改同一批前端宿主文件。

**风险最高的两条**是第 4 条和第 6 条：前者没有任何前端先例且要新定义一套写入通道；后者横跨 12 张表，且要改一个被五个页面共用的弹窗组件。

### 验证约定

用户已明令禁止跑全量质量门禁。各子 feature 按"受影响专项测试加定向浏览器验证"收口。以下每条都可能让这个约束失效或让验证失真：

- **新测试与探针的命名决定门禁规模。** 日常门禁按改动路径匹配必跑组的范围（`scripts/run_daily_quality_gate.py:362`）；改动路径不命中任何必跑组时会给出"在已知必跑范围之外"的理由（`:407`）并标记为跑全部必跑组（`:430,745`），耗时远超定向测试。新探针要么命名成能被现有 `resource*probe.cjs` 匹配，要么把新模式加进注册表对应组的范围。新测试必须先 `git add`，注册表用 `git ls-files --error-unmatch` 判断跟踪状态（`tools/test_registry.py:177`）。
- **前端改动必须重建并提交产物。** 构建结果是跟踪文件，日常门禁不校验它与源码是否同步，但浏览器车道和界面证据门禁会校验。只改源码不重建会出现测试在旧产物上跑通、实际界面没变的假验证。
- **浏览器验证不在日常门禁里。** 要显式跑 `scripts/run_browser_test_lane.py --only <相关>`。运行前确认 Chromium 109 存在于 `/tmp/aps-chromium109-assessment/runtime/`（`tests/workbench/test_live_browser.py:20`），该路径会被系统定期清空，备份压缩包在 `~/.cache/aps-chromium109-assessment/`，缺失时测试直接失败而非跳过。
- **改共享弹窗组件会波及五个资源页**，它们的浏览器探针与界面证据都要重采。第 2 条的验证必须包含"现有五个家族的导出范围交互逐字节不变"。
- **界面证据会因任何前端改动失效**，该门禁默认不启用（`scripts/run_daily_quality_gate.py:714`），只在显式传入证据目录时才检查。注意人员页与日历页不在证据矩阵里，七项几何检查也不测量工具栏，界面拥挤问题只能靠人工核图。
- **跨层改动要手动补跑**类型检查门禁与债务台账检查。
- **只有工作区干净且在最终提交上跑过要求的检查，才能称为干净工作区证明。**

## 7. 观察项

- **全局日历的一致性校验缺陷**已由第 1 条纳入修复，但它是独立于本 roadmap 的现存缺陷，建议同时按问题修复流程立项留痕，便于追溯"从什么时候开始改不了工时"。
- **批量解除可操作设备没有通道**。按 4.3 的增量更新语义文件不能删关系，界面只能逐人操作，设备页既无入口也看不到谁有授权。更麻烦的是现有行为不一致：有授权的设备被批量删除时会因引用计数被拒，单条删除却会放行并由外键级联静默清掉授权。是否需要一个按设备解除全部人员的入口，以及是否要统一这两种删除的口径，建议另行裁决。
- **三处旧导入代码的去留**：两处关系导入函数与个人日历行校验函数在生产代码里无调用方，但各有测试在调用（`tests/excel_data_io/test_excel_source_row_num_preserved.py:14,43`、`tests/calendar_maintenance/test_excel_operator_calendar_cross_midnight.py:27,39`），退役时要连测试一起处置；只有个人日历的批量导入函数是全仓库无调用。它们的批量预检模式（父表集合、文件内主操唯一）恰是新家族要的，可考虑提取为共享纯函数而不是直接删。
- **日历页看不到谁有特殊安排**。个人日历做完后，计划员在日历页仍只能看到全局日历。是否需要汇总视图，建议等用起来再定。
- **确认失败的对外语义可能误导**。底层非业务异常会被统一包成不确定结果，用户看到"可能已生效"，但数据其实已回滚。这是现有全家族的共同行为，本 roadmap 不改，但文件批量下更容易撞到。
- **四份旧 Excel 页说明视图模型**描述的是已退役的旧页面与旧列头，目前仍随说明书页提供给用户。第 7 条会重写，整体删除还是改写为工作台版，在该条 design 时确认。
- **两份旧审计报告会失去基线**：它们记录的是旧 11 张模板的结论，第 7 条完成后建议标注过时或归档。
- **架构文档需补两个新家族**，落地后由 `cs-arch` 处理，不在本 roadmap 内改。

## 8. 修订说明

- 2026-09-21 起草。
- 2026-09-21 深度复核后第一次修订，八处：写入语义改为增量更新不删除；日历取消文件删除语义；家族从一个拆为两个；读取器统一方向改为放宽而非收紧；补上日历用日期范围导出；kind 统一用下划线；个人日历入口移位；文档一致性门禁改为工具生成。
- 2026-09-21 三轨复审（定向核对加后端盲审加前端盲审）后第二次修订。定向核对了 146 条断言，改正其中 18 条引用与措辞偏差；两轨盲审提出 6 个阻塞问题，全部采纳：
  1. **新增第 1 条 feature 修全局日历校验缺陷**（4.4）。复审实测发现：某天存成 8 小时后改成 10 小时会被拒，休息转工作也会被拒，单日编辑与范围维护两条路径都中。这是现存缺陷，年度日历回导必然大量触发，不修则日历文件导入不可用。
  2. **补全主操连带的写入规则**（4.3）。原稿只说"设为主操的行带说明"，漏了确认阶段缺列取值必须现读、不变行不得调用底层、同人多行的写序三条；不补会出现最终主操与预检承诺相反。
  3. **共享弹窗必须加扩展点**（4.10）。原稿称日历家族"只传配置就能复用"，实际导出范围被写死成三档单选，日期范围没有插槽。改为新增两个向后兼容的可选扩展点，并把该组件列入改动清单。
  4. **补全个人日历面板的写入契约**（4.13）。原稿只说"服务、路由、界面全部新写"，实际现有传输层对未知意图是硬拒绝，面板保存会直接报错。现定义意图形状、路由、能力声明与四处前端改点。
  5. **入口改为表选择层**（4.11）。按现有令牌估算，平铺按钮在 1280 宽度下人员页与日历页都必然换行，日历页可能三行；而原稿"以几何检查为准"是空判据，这两页不在证据矩阵且几何检查不测量工具栏。同时把"设备授权"改为与界面一致的"可操作设备"。
  6. **撤回"构建顺序解不开"的论断**（4.10）。工艺页就是页面直接渲染弹窗的先例，日历页组件也可以挪位置。仍选择宿主装配，但理由改为与资源家族一致及探针加载方式，如实表述为选择而非约束。
  另补：模块 A 的导出范围键集必须与现有白名单一致否则必然被拒；补预检文档要嵌入的事实、预检性能约束、假期带工时的口径裁决、预检存储选型、资格过滤对齐项；修正传输层放行的确切位置与漏改表现。
