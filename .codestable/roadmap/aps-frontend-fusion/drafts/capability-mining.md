## 域：execution-facts

**摘要**：现场事实链路已是"读写双 fail-closed"的成熟能力：写侧 OperationExecutionFeedbackService（499 行）经两层纵深把事件钉死在 schedule/adopted/无scenario 身份上，DB 层 CHECK 约束兜底；读侧 ExecutionFactProvider 故意毒化 op_id-only 入口，只允许带完整 7 字段计划身份的 scope 读取。消费方已覆盖：首页值班台（现场情况待确认）、甘特任务详情区（已接通，实际开完工三字段从 facts_by_op_id_for_plan_rows 一路流到 gantt_popup.js）、执行复盘报表（走同源 state 聚合口）、资源派工页（state 口）、重排/模拟转正护栏（snapshot+guardrails）。明确未接的是周计划（页面+Excel 导出，纯计划字段）和批次详情页（BatchOperations 行无 schedule 身份）。最近的融合机会：甘特条 progress 仍硬编码 0、甘特条无现场状态着色、周计划缺现场状态列——三者所需事实都已在同一函数或同一服务内一线之遥。

### 缺口与阻塞

- 非 adopted 身份（候选/模拟/历史方案）按设计永远无现场事实：schema.sql:184-191 三条 CHECK（source_table='schedule'、effective_plan_role='adopted'、scenario_id IS NULL）使事件物理上写不进去——任何'给对比方案显示现场进度'的前端诉求接不了，且不应试图放宽（写侧 operation_execution_feedback_service.py:366-375 与 :472-476 两层 fail-closed 同向钉死）。
- 批次详情页（scheduler_batch_detail.py:217）的数据源是 BatchOperations 行，不带 schedule_id/version 身份，而 provider 的 op_id-only 入口被故意毒化（execution_fact_provider.py:92-96 raise）——想接事实必须先额外查 adopted 计划行，这是融合机会 4 的成本来源，不是可以绕过的坑。
- 周计划输出行在 _split_by_day 按天拆分后丢失 op_id（gantt_week_plan.py:65-73 输出仅 7 个中文键）——事实标签必须在拆分前注入，事后按行回填无钥匙可查。
- gantt_service.py 已 495/500 行，贴着单文件门禁——周计划融合的任何新逻辑都必须落在 gantt_week_plan.py（119 行）侧，gantt_service.py 只能容纳一行级改动。
- 双 UI 镜像树人肉双写：templates/scheduler/gantt.html 与 web_new_test/templates/scheduler/gantt.html 双份同构（守卫已 DROP），改甘特模板必须双写；week_plan.html/batch_detail.html 无镜像副本（web_new_test/templates/scheduler/ 仅 5 个文件），只改 V1 即可但动手前仍须复查。
- execution_review 报表走的是 OperationExecutionState 聚合口（execution_review.py:192 get_execution_state_for_scopes）而非 ExecutionFactProvider——两口同源（都经 aggregate_states_by_scopes，operation_execution_state_aggregation.py:36）但返回类型不同（State 含异常明细标签，Fact 含 schedule 身份），新融合点选口时不可混用字段名。

## 域：utilization-capacity

**摘要**：利用率存在两套已实锤的口径：报表链（ReportEngine.utilization → compute_utilization，分母=日历容量 Σshift_hours×efficiency 的全局单值 cap_hours）与首页风险卡链（algo 评估器 _util_avg，分母=内部排程 makespan 时间跨度），同名"利用率"分子分母全不同。week_plan 没有第三套口径——它只做日切分+时段文本，无任何工时数值计算。日历能力齐备：CalendarEngine 支持 operator 级日历覆盖（policy_for_datetime(operator_id=...)），机器级日历无数据来源；甘特假期数据来自 build_calendar_days（逐日 CalendarService.get）。做"甘特下方资源×日桶负荷条带"所需的零件几乎全在：日桶切分 split_by_day、窗口裁剪 overlap_seconds、行过滤 is_internal_source、逐日日历 build_calendar_days、甘特契约 build_gantt_contract 与前端 SVG layer 模式 gantt_holidays.js 均可直接复用；唯一要新增的是一个按 (resource_id, date) 聚合的纯函数 + 契约字段 + 一个新 JS 文件。两个硬坑：gantt_service.py 已 495 行（500 行门禁仅剩 5 行余量，新逻辑必须放新文件）；build_calendar_days 输出不含 efficiency，分母若取"日容量"需补字段。
