# 智能排产系统（APS）架构总入口

> 状态：CodeStable 现状索引
> 创建日期：2026-04-27

## 1. 项目简介

本项目是面向 Win7 x64 离线单机与共享数据场景的本地 APS 智能排产系统。系统目标是在目标机不安装 Python、不依赖外网的前提下，完成基础资料维护、Excel 导入导出、批次排产、结果查看、报表导出、备份恢复和现场交付。

当前开发与打包基线保持在 Python 3.8，并继续服从 Win7 兼容边界。应用收口为单一生产与开发宿主入口 `app.py`（导出无模块导入副作用的 `create_app()` 与 `main()`；旧 `app_new_ui.py`、`start_new_ui.bat` 与 `ui_mode` 运行时字段已退役）。正式交付时，目标机通过绿色便携包（或显式维护安装器）和本地 Chrome 109 浏览器运行时离线访问 APS 工作台页面。

## 2. 核心概念 / 术语表

- APS：围绕批次、工序、设备、人员、日历、齐套约束和排产策略组织的智能排产系统。
- 界面：`/workbench` 与 `/workbench/trial` 已挂载主数据、工艺、批次、排产候选、正式计划、试调、执行、报表、校准、值班台和系统维护的真实服务。旧 HTML 页面层、旧视图模型及旧 URL 跳转/410 占位规则（`legacy_blueprints.py`）均已退役，当前仅保留工作台页面入口 `web/routes/workbench/pages.py`、说明书页 `web/routes/workbench/manual_page.py` 和系统运行时接口 `web/routes/workbench/system_runtime.py`；工作台入口接入不等于全站终验或 Win7 发布完成。当前边界和证据见 `workbench-shell.md`。
- Win7 交付边界：目标机不要求安装 Python，页面和静态资源随应用本地交付，依赖升级必须考虑 Python 3.8 与 Win7。

## 3. 子系统 / 模块索引

- `core/`：核心领域、算法、基础设施、服务与插件运行框架。
- 基础层当前依赖方向为 `infrastructure → models → shared → core.errors`（允许跳层指向更低层）：零依赖应用错误合同在 `core/errors.py`（旧 `core/infrastructure/errors.py` 垫片已于 2026-09-20 删除，全仓直接引用 `core.errors`）；Schema 声明集中在 `core/infrastructure/*_schema.py`（含 `core_schema.py`，永久身份触发器生成逻辑统一收敛于 `workbench_metadata_schema.py` 的 `identity_triggers()`，另含 `workbench_plan_identity_write_guard.py` 的写入守卫触发器），通过 `python -m tools.generate_schema_sql --write` 唯一生成 `schema.sql`，并由 `migration_state.py` / `schema_structure.py` 校验 `CURRENT_SCHEMA_VERSION = 45` 结构与恢复数据契约（旧 `core/infrastructure/migrations/` 增量迁移链、child 兼容转出及历史归档兼容投影模块均已退役，低版本或残缺库直接抛出 `MigrationContractError` 阻断启动，归档事实严格按当前 `schema / columns / tables / revisions` 契约核验；`core/infrastructure/migration_common.py` 仅保留基础设施层 `fallback_log` 辅助函数）。

## 5. 已知约束 / 硬边界

- 面向用户默认使用简体中文。
- Win7 x64、Python 3.8、离线交付是长期约束。
- 页面正文、普通 HTML 属性、导出、文件名、提示语、帮助文档和公开 JSON 不能直接展示 `scenario_id`、`source_table`、`candidate_id` 这类程序内部字段；服务端内部可以继续用这些字段对齐同一套计划。跨页传播只用永久公开引用（`plan_ref`、`candidate_ref`、`task_ref` 等）和进程内签发的读/写绑定 token（`snapshot_ref`、`write_token`，由 `web/public_token_registry.py` 持有 `ReadBinding`/`WriteBinding`），不把内部字段放进公开链接或隐藏字段。
- 报表和工作台页面同样不能在正文、按钮、普通 HTML 属性、导出列或公开 payload 里展示 `op_id`、`schedule_id` 这类工序内部定位字段；需要跨页定位时优先使用批次、设备、人员、日期这些业务对象。
- 非正式方案、候选方案、试调方案和历史正式方案不能下发现场记录写入入口、Excel 导入地址或模板下载地址。后端校验仍是最后防线，但页面层也要避免让用户看到“好像能写”的入口。
- 工作台报表导出继续只展示中文业务字段，不展示 `op_id`、`schedule_id`、`state_revision`、`execution_snapshot_revision` 等内部追踪字段。公开列与导出列由 `core/services/workbench/report/`（`columns.py`、`exports.py`）决定，路由在 `web/routes/workbench/reports.py` 与 `reports_catalog.py`，`core/services/report/` 只提供 xlsx 导出器与计算件（旧 `core/services/scheduler/resource_dispatch_excel.py` 与 `tests/resource_dispatch/test_resource_dispatch_public_output_contract.py` 已退役）。
- 质量门禁入口仍以仓库现有 `scripts/run_quality_gate.py` 为准。
- 旧 `.limcode/plans/`、`.limcode/review/` 里有大量历史上下文，迁移初期不得批量删除或搬动。

## 6. 排产工序图分析现状

- `core/services/scheduler/graph/` 是排产工序图的内部分析模块，当前负责把已整理好的待排工序转成图节点、构建同批次前后工序边、校验 DAG / 环、计算拓扑顺序、关键路径和节点指标，并导出普通 dict 摘要。
- `graph_analysis_mode=on` 是当前默认模式，依赖 `requirements-optimizer-lite-win7.txt` 中锁定的 `networkx==3.1`。`graph_analysis_mode=off` 仍是显式关闭模式；关闭时排产主链不启用图增强，也不会在 `result_summary` 里写 `graph_analysis`。例外是分件排产：只要有工序带 `piece_id`，业务准备（`core/services/workbench/run/input.py`）就会构造 `piece_scope` 与显式前置边 `predecessors` 并固定 `dispatch_mode="sgs"`，统一经 `core/services/scheduler/run/schedule_candidate_runner.py` -> `core/services/scheduler/run/schedule_graph_report.py:prepare_schedule_graph_for_dispatch` 按 `solver_input.predecessors` 固定以 `on` 语义启用分件 DAG ready context 与 SGS，不受 off/report 配置影响。
- `graph_analysis_mode=report` 与 `on` 共用同一图准备入口：`core/services/scheduler/run/schedule_candidate_runner.py` 把 `prepare_schedule_graph_for_dispatch`（`core/services/scheduler/run/schedule_graph_report.py`）作为 `graph_prepare` 交给 `schedule_shared_optimizer.py`，在共享搜索开始前调用一次；它只读取 `SolverInput` 的 `config`、`algo_ops`、`to_schedule`、`batches`、`seeds.frozen_op_ids`、`seeds.seed_results`、`predecessors` 与 `SolverResources` 的 `resource_pool`，图报告判断、错误投影和采样投影都收在该文件。report 模式不生成 ready context（只有 `on` 且是 DAG 才启用），只产出 `graph_analysis_public` / `graph_analysis_diagnostics`，随每个业务代表 `CandidatePlan` 返回 `core/services/workbench/run/compute.py`（旧 `schedule_orchestrator.py` 已退役），由运行结果与选中方案写入摘要。
- report 模式只把公开小摘要写进 `result_summary["algo"]["graph_analysis"]`，把采样诊断写进 `result_summary["diagnostics"]["graph_analysis"]`；结果摘要随运行结果的 `summary` 保存（`WorkbenchRunReceipts.result_json`）。正式采用写入 OperationLogs/ScheduleHistory 的只是采用审计，不含 `algo` 摘要；任何保存位置都不包含完整 nodes、edges、node_metrics、topological_order 或 raw 对象。
- `graph_analysis_mode=on` 当前已经接入 PR-5 ready 队列、PR-6 图评分和 GraphReady 专用候选池：可用 DAG 会在 optimizer 前生成 plain `graph_ready_context`，SGS 候选集合只从图 ready 工序里取；当 `graph_critical_weight`、`graph_impact_weight`、`graph_downstream_weight` 任一大于 0 时，图模块会计算 full `node_metrics`，在 service 层预先转成 `graph_priority_key_by_op_id`，算法层只拼普通 tuple，不反向依赖 scheduler service。生产 GraphReady 候选池保留 v1 九组图权重，并可通过 `objective_aware_portfolio` 生成 v2 目标感知候选；v2 只改 ready 排序键，仍由正式 SGS 解码，空交期按 no-due 特征后置，非空非法交期一律 fail-loud。`on + 有环 + graph_block_on_cycle=yes` 会在共享搜索前的图准备阶段直接失败（`schedule_graph_report.py` 抛 `ValidationError`），不产生候选；`on + 有环 + graph_block_on_cycle=no` 会继续旧 SGS 逻辑，但 public 摘要会写明图增强和图评分未启用。候选方案链路通过 `core/services/scheduler/run/schedule_candidate_runner.py` 的 `run_candidate_comparison` 执行单次共享优化（`optimize_shared_schedule`，协同 MultiStart、LocalSearch、GRASP/IG 与图 Profile/Repair/IG），由工作台 `workbench/run/` 发布 1—3 份实际业务代表（各目标 winner 可指向同一永久候选，安排正文保存在 `WorkbenchRunCandidateTasks`，查询直接消费 `decision-read-v1` 投影；旧 3/5/7 档多轮独立权重试跑与旧代表三方案页面切换已退役）。

## 8. 重排执行事实快照现状

- `core/services/scheduler/execution/execution_snapshot.py` 负责把一批工序的执行状态版本整理成可复算快照。快照包含 `execution_snapshot_revision`、`execution_snapshot_op_ids` 和 `execution_snapshot_op_count`。
- 工作台排产在 `core/services/workbench/run/` 受理与预检共享的 `PreparedBusinessInput` 源头一次捕获执行事实（台账状态只有 `unreported`/`started`/`partial`/`complete`）：已完工工序保留真实时间作为执行 seed 并从待排输入剔除；已开工未完工工序标为受保护，剩余数量须先在现场记录确认，否则阻断重排。
- 候选比较、多起点、局部搜索、优化器和图排程 ready queue 复用同一批执行 seed；执行 seed 的来源标记为 `execution_fact`，和冻结窗口 seed 分开。
- 正式采用排产候选（`core/services/workbench/run/`）或试调方案（`core/services/workbench/trial/`）前，在写事务中按同一批工序复算执行快照，经统一安排约束验证与 `execution_ledger_guard.py` 核对固定工序、已完工工序和下游时间（试调采用在同事务内单次评估返回结构化结论，不再重复双跑验证器）；现场状态变化时拒绝采用并返回中文冲突提示，不写 `Schedule`、`ScheduleHistory` 或版本号（旧 `schedule_input_collector.py`、`schedule_persistence.py`、`schedule_execution_persistence_guard.py` 与 `ScheduleAdjustmentScenario` 已退役）。
- 执行快照字段是开发和测试追溯信息，不直接给普通用户看；页面和普通接口只返回中文消息、名称、预览或查看链接等用户需要的信息。
