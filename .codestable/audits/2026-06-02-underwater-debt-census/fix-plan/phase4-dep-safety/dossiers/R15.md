## 7) 收口行为差异及所需 parity 测试

**新旧两路逐分支对边界值的等价性分析**(以「provider 收口到 `parse_operation_event_time`」为假想路径):

| 输入边界 | 旧 `_parse_execution_time`(provider:85) | 新 `parse_operation_event_time`(event:75) | 等价? |
|----|----|----|----|
| `None` / 空串 / 纯空白 | `if not text: return None` → **None** | `if not text: raise ValueError("event_time is required")` → **raise** | ❌ **不等价**(关键反例!) |
| `datetime` 对象 | 旧:`str(value)` 后 strptime,多半解析失败 → **None** | 新:`value.replace(microsecond=0)` → **datetime** | ❌ 不等价 |
| 合法 `2026-06-05 10:00:00` | strptime → datetime | strptime → datetime | ✅ 等价 |
| 用 `/` 分隔 `2026/06/05` | 旧 `replace("/","-")` 后解析 → datetime | `_event_time_text:72` 做**同款** `replace("/","-").replace("T"," ").replace("：",":")` → datetime | ✅ 等价(已核 `event:71-72` 与 provider:88 归一化字节同) |
| 坏值 `"abc"` | 循环 strptime 全失败 → **None** | 全失败 → **raise ValueError** | ❌ **不等价**(P5 核心:None vs raise) |

**结论**:provider 从「空→None / 坏→None」到「空→raise / 坏→raise」是**双重语义跃迁**,绝非平移。这正是 owner 须裁的点(§4 分叉 2):
- 「空→raise」会破坏 provider 现合法语义(现场允许「还没开始/还没结束」即 actual_start/end 为空 → 现 None,改 raise 会把正常空时间炸成错误)→ **此分支必须保 None**。
- 「坏→raise」才是 P5 想要的 loud 升级,但要确认 `:52/53` 下游接得住。

**所需 parity 测试(收口前必须先写,钉死三处各自的 required/optional 矩阵)**:
1. provider:`_parse_execution_time(None/""/" ")` → 必须仍 **None**(optional 不变);`("乱码")` → 按 owner 裁定(None 保持 or raise)钉死,不能含糊。
2. support:`_parse_feedback_datetime("")`/`(乱码)` → 必须 **raise** 且消息为「反馈时间格式不正确,请检查后再提交。」、details 带 field —— 防 R17 删键/未来重构改坏对外契约。
3. state_builder:`_parse_time(None/"")` → **None**;`(乱码)` → **raise**(loud,现状)。
4. 跨处一致性断言:同一坏值字符串,三处行为按各自 required/optional 规约,**禁止再被某次重构统一成一种**(钉住「三处语义本就不同」是 R15 的真相)。
