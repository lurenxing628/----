## 7) 收口行为差异 + parity 测试

本债**不收口**(仅注释),原则上无新旧两路 parity 问题。但必须回答一个**对抗性诱惑**:既然 repo 侧已有 `validate_current_official_execution_scope`(operation_execution_scope.py)做强校验(§8 冲突 B),为何 service.py:471-473 写死**不能删/不能改透传**?——这是后续最可能被"统一掉"的点,故给出三路 parity 反例,证明三道闸**逐分支不等价、必须并存**:

| 输入场景 | ② 硬拒 :368-374 | ②.5 写死 :471-473 | ③ repo validate :241 | ③' schema CHECK :190-192 | 删写死后果 |
|---|---|---|---|---|---|
| 正常 adopted/schedule | 放行 | 落 schedule/adopted/None | 放行(同值) | 通过 | 行为相同(此分支等价) |
| context.source_table=candidate_rows(上游被绕过,硬拒漏判) | 若漏拒 | **写死强制改回 schedule** → 安全落库 | 放行(已被写死改回) | 通过 | **删写死=raise ValueError→AppError(DB_INTEGRITY)→合法操作变用户报错;或若 repo 也被绕过则脏数据落库** |
| context.scenario_id=scenario-x(硬拒漏判) | 若漏拒 | **写死强制 None** → 安全 | 放行 | 通过 | **删写死 → scenario 预览态现场事件落库 → 污染重排护栏** |

**关键反例(None vs raise 不等价)**:
- 删写死改透传 → **合法 adopted 请求**走到 repo validate(:241)/schema CHECK(:190-192):若 context 任一字段因上游 normalize 漂成非规范值,会触发 `ValueError`→`AppError(DB_INTEGRITY_ERROR)`,**正常用户操作变 500/报错**(可用性事故)。
- 删写死且 repo 也被某债"统一简化"掉 validate → 仅剩 schema CHECK 兜底,且 schema.sql:**284** 另有 `CHECK(source_table IN ('schedule','candidate_rows'))` 的**另一张表**,若事件误写到那张表则 candidate_rows **不被拒**→ 脏数据**静默落库**(数据完整性事故)。
- 故 :471-473 与 repo validate **不是冗余**,是「拒 vs 消毒」两种不等价行为的纵深:硬拒/validate 是 raise(loud),写死是 coerce-to-safe(silent-but-safe),覆盖"上游绕过"这一硬拒覆盖不到的分支。
