## 7) 收口行为差异及 parity 测试

R13 是直删类，不涉新旧两路收口，但 **删字段前必须确认它与 `schedule_version` 不构成独立语义**，否则删错=静默丢观测面：

回盘证据链：
- `_latest_events_by_scope`(:163-170) 用 `operation_execution_scope_from_event(event)`(:169) 给事件分桶。
- `operation_execution_scope.py:89-90`：scope 的 `schedule_version/schedule_id` **正是从 event 的同名字段派生**（`getattr(event, "schedule_version")`）。
- 故 `_fact_from_state` 里 :56 `last_event_schedule_version = int(latest.schedule_version)` 与 :62 `schedule_version = int(scope.schedule_version)` 在 **latest 事件存在时取值完全相同**（同一 event 的同一字段）。差异仅在 **latest is None** 时：`last_event_*=None` 而 `scope.schedule_version` 恒为正整数（scope 由 plan_rows 构造，必有身份）。

**结论：`last_event_*` ≈「该 op 有无执行事件」的布尔信号被编码成「事件的 schedule 身份 or None」**。它与 `schedule_version`（计划身份，恒有值）语义不同——前者反映「事件侧记录的 schedule」，后者反映「读取请求的 plan scope」。在当前数据流二者数值恒等（事件按 scope 分桶），但 **None 分支携带「无事件」信息**。

parity 反例（删字段会丢的信息）：
- op 无任何执行事件时：`last_event_schedule_version=None`（可区分「没事件」），`schedule_version=2`（计划身份）。删字段后，「该 op 有无 latest 事件」这一信号从 ExecutionFact 面上消失。
- 但 **生产侧 0 消费者读这个 None 信号**（§8 证），所以实际无人依赖该区分 → 直删安全。reschedule:196 `==1` 只验证「有事件时取到事件 schedule」，未验证 None 分支语义。

所需 parity 测试（若走路 B 保留字段，钉「我是故意的」）：补一条断言「无事件 op 的 `last_event_schedule_version is None` 且 `schedule_version is not None`」以固化二者差异——scope_read_contract:108 已部分覆盖（`scoped_fact.last_event_schedule_version is None`），可作为 parity 锚点。
