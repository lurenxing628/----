## 7) 收口行为差异及所需 parity 测试

**逐分支等价性**:三处对 int 化 / `<=0` 排除 / 去重逻辑**完全等价**;唯一非等价分支=**输出顺序**。反例与影响:

- **反例(顺序)**:输入 `[3, 1, 2, 1]` →
  - snapshot `positive_op_ids` = `[1, 2, 3]`(`sorted`)
  - provider `_positive_op_ids` / repo `_positive_ids` = `[3, 1, 2]`(插入序,去重后)
- **各消费点对顺序敏感度(实测)**:
  - snapshot :87-90 把 ids 顺序拼进 payload 再 sha256(:91)→ **指纹强依赖排序**;若把 snapshot 改成不排序版,指纹值变 = 破坏快照修订稳定性(灾难,§8)。⇒ canonical 实现**必须保 sorted**。
  - provider :145 `missing = [op_id for ... if op_id not in out]`,:147 `raise ...op_id={missing[0]}`→ 顺序仅影响 **loud raise 错误消息里第一个 op_id 值**,不影响是否报错。若 provider 收到 sorted 版,`missing[0]` 可能从 `[3]`→`[1]`,**对外可见的报错文案变**。⇒ 需 parity 断言或 owner 接受文案变更。
  - repo :408-420 `_batch_ids_by_op_ids`:ids 喂 SQL `IN (...)` 并落 `out[id]` dict → **顺序完全无关**;收 sorted/不收都不影响结果。
- **所需 parity 测试(收口前必补)**:
  1. `positive_op_ids` 黄金用例:空/None、含 0 与负数、含非 int(`"x"`/`None`)、重复 → 锁定 `[1,2,3]` 排序输出(钉住指纹依赖)。
  2. provider 收口 parity:对同一输入,`_positive_op_ids`(收口后)与历史不排序版在 **集合相等** 上等价;若改 `missing[0]` 文案则显式断言新文案(loud raise 不得变成静默)。
  3. repo:若保留私有版,补"顺序无关 + 与 canonical 集合等价"契约测试,作为「故意分叉」的守卫。
