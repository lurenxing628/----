# APS 前端工作台设计差距审计

## 审计范围

本轮只做只读审计，不改前端实现。对比对象是：

- `.codestable/roadmap/aps-frontend-workbench/drafts/2026-05-31-aps-frontend-page-design-spec.md`
- `.codestable/roadmap/aps-frontend-workbench/aps-frontend-workbench-roadmap.md`
- `.codestable/roadmap/aps-frontend-workbench/aps-frontend-workbench-items.yaml`
- 当前首页、排产分析、甘特、资源派工、报表中心、延期解释、计划和现场实际、相关 JS/CSS/测试
- 既有高层审计：`.codestable/audits/2026-05-31-aps-frontend-layout-gap/`

用户要求最多同时 16 个 SubAgent，本轮实际使用 12 个 SubAgent，按页面和风险面拆分：文档一致性、导航路由、首页、排产分析、甘特、资源派工、报表、跨页链接、写入护栏、数据服务、CSS/浏览器约束、测试门禁。12 个结果均已回收并关闭。

## 总体结论

当前项目已经有很多“原材料”：候选方案三角色、延期诊断事实/线索、资源负荷报表、计划和现场实际、现场记录事件、Gantt 只读模式、非正式方案后端拒写护栏。问题不在“完全没有功能”，而在“这些功能还没被组织成计划员每天能顺着做事的工作台”。

大白话说：现在像一组分散的页面，设计稿想要的是一条工作路线。用户应该从首页看到今天先处理什么，点到分析看哪个方案更稳，点到甘特看任务和资源，再点到资源派工或报表继续处理；但当前很多入口还是裸链接、参数名不统一、风险摘要没聚合、报表看完不容易回到处理页。

用户在 2026-05-31 补充了一个重要口径：短期内系统本质上仍是“计划员一个人操作，其他人把现场情况汇报给计划员”，所以不把它当成多人车间终端来做。基于这个口径，本审计里原先提到的“反馈人必填”和“Excel 导入预览”不再作为短期阻塞项；它们改成明确的短期不做范围。

剩下最需要先拍板的是两类问题：

- 设计稿和现状直接打架：现场记录第一版是否隐藏暂停/异常、非正式方案是否只跳正式复盘还是直接禁用入口、非正式方案页面是否仍下发写入 URL。
- 需要新增功能，不是挪布局能解决：统一 WorkbenchLink、首页今日待处理、现场情况待确认统计、方案影响面、停机影响任务级明细、资源容量来源说明。

## 能不改功能就先做的范围

- 顶层导航把“首页”升级为“计划工作台”，并把已有分析、甘特、资源派工、报表入口收成更清楚的工作菜单。
- 首页首屏骨架改成“上下文条 + 风险卡 + 今日待处理占位 + 交接摘要”，其中基础版本、最近范围、待排、已排、超期可以先用现有数据。
- 排产分析页先把推荐卡、三方案摘要、诊断行动卡提前到指标卡之前，并补更清楚的空状态。
- 甘特页先补稳定高度、空态、右侧详情容器，并把“仅超期”这类高频筛选提出来。
- 资源派工页先把 tab 分成“计划员查看”和“现场事实”两个可测试分组，Excel 批量维护继续走直接导入，不做预览。
- 报表中心卡片补“能回答什么 / 不能证明什么”，并给已有报表行补最小回跳按钮。

## 必须新增功能的范围

- 新建统一的 `WorkbenchPlanContext` / `WorkbenchLink` 生成层，处理 `version`、`plan_role`、`scenario_id`、日期、批次、资源对象的参数翻译。
- 首页新增工作台聚合：今日待处理 Top、资源高负荷、现场情况待确认、方案待确认、证据说明和动作链接。
- 排产分析新增影响面：受影响批次数、最晚超期、最忙资源利用率、数据缺口，并处理历史 summary 被裁剪后的补水。
- 资源派工新增现场快速筛选、任务卡偏差字段、执行流水来源/记录时间、导入回执；Excel 预览短期不做。
- 第一版报表和延期解释先补回跳入口、保守说明和“能回答 / 不能证明什么”；停机影响任务级明细、牵连批次/订单影响面、现场事实接入延期诊断放到第二阶段增强。
- 测试门禁新增 workbench 流程测试、浏览器几何路径和质量门禁注册。

## 不能直接按设计稿硬做的点

- 反馈人必填：用户已明确短期不做，因为当前是计划员单人操作，不需要引入多人反馈人模型。
- Excel 预览：用户已明确短期不做，因为当前是计划员自己维护导入，不需要增加预览确认流程。
- 现场动作：设计稿第一版只要开工、完工、查看记录；当前页面和测试已经包含暂停、异常等字段。
- 非正式方案复盘入口：设计稿倾向禁用并说明原因；当前测试锁的是跳正式采用方案复盘且不带 `plan_role/scenario_id`。
- 容量说明：当前资源利用率主要按工作日历粗算，停机影响是另一套报表，不能直接宣称“已扣除停机”。

## 建议推进顺序

1. 先做 `workbench-context-link-contract`：统一链接参数。它是首页、分析、甘特、资源派工、报表全部串起来的地基。
2. 再做 `workbench-nav-entry`：先让计划员从顶层能一跳进入计划工作台和关键页面。
3. 然后做 `dashboard-workbench-risk-todos`：把首页变成真正的值班台。
4. 接着做第一版后续页面：分析页行动层、甘特详情区、资源派工执行入口分层、报表回跳和流程回归。
5. 最后做第二阶段增强：延期解释接现场事实、甘特资源负荷摘要、停机任务级明细和牵连批次/订单影响面。
